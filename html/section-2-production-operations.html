Section 2: Production Operations

Section 1 taught you the built-in Kubernetes primitives: Pods, Deployments, Services, ConfigMaps, Secrets, Volumes, and the workload controllers from Lab 6. Those objects are enough to run a simple application, but real production clusters require more: controlled HTTP routing, standardised packaging, visibility into what the cluster is doing, and a reliable way to ensure that what runs in production matches what the team agreed on in code review. Section 2 covers the ecosystem tools that sit on top of Kubernetes to solve those problems. Each lab starts by explaining the tool conceptually before you use it, because knowing why a tool exists is more durable knowledge than any sequence of commands.

  • Lab 7: Route external HTTP traffic into the cluster with the Gateway API.
  • Lab 8: Package, version, and template your application with Helm charts.
  • Lab 9: Add observability with Prometheus and Grafana for metrics and dashboards.
  • Lab 10: Adopt GitOps so the running cluster continuously matches Git, using Argo CD.
INFO: Custom Resource Definitions (CRDs) Kubernetes ships with a fixed set of built-in object types: Pod, Deployment, Service, ConfigMap, and so on. A Custom Resource Definition (CRD) is a mechanism that lets any tool teach the cluster a brand-new object type. Once a CRD is installed, you manage its objects with the exact same commands you already know: kubectl apply, kubectl get, kubectl describe, kubectl delete. The Gateway API (Lab 7) adds the Gateway and HTTPRoute types. Argo CD (Lab 10) adds the Application type. Kyverno (Lab 15) adds ClusterPolicy. All of these are CRDs. When you see an unfamiliar kind: in a YAML file, it is almost always a custom resource. A piece of software called a controller watches those objects and continuously drives the cluster toward the state they describe. You already saw this watch-and-reconcile pattern with Deployments in Section 1; everything in Section 2 is the same idea applied to new, richer object types.

10. Lab 7: HTTP Routing with the Gateway API

A Service (Section 1) gives a stable virtual IP to a group of pods and distributes TCP connections across them. That is all it does. Real HTTP applications need more: send /api requests to one microservice and /web requests to another; route traffic by hostname (app.example.com vs admin.example.com); terminate TLS so pods do not need certificates; redirect HTTP to HTTPS. This is called Layer 7 (L7) routing, and it requires a proxy that understands the HTTP protocol, not just TCP.

History: From Ingress to Gateway API

The first Kubernetes answer to L7 routing was the Ingress object, introduced around 2016. Ingress was always a partial solution: its specification was too minimal, so every controller (nginx, Traefik, HAProxy) interpreted it slightly differently and added proprietary annotations. The most widely used implementation, community ingress-nginx, reached end of life in March 2026 and receives no further releases, bug fixes, or CVE patches. The Kubernetes Security Response Committee has stated plainly that running it past EOL leaves clusters exposed. The Ingress API itself is effectively frozen.

The modern, actively developed replacement is the Gateway API: a set of CRDs maintained by the Kubernetes SIG-Network team that provides a richer, role-separated, standardised model for L7 routing. This lab teaches the Gateway API directly.

WARNING: ingress-nginx is End of Life The community ingress-nginx controller reached end of life in March 2026. It receives no further releases, no bug fixes, and no CVE patches. Do not use it in new setups. If you have inherited Ingress resources, use the ingress2gateway CLI to migrate them to Gateway API automatically. If you must keep the legacy Ingress API temporarily, choose a maintained controller: Traefik, HAProxy Ingress, or the F5/NGINX-Inc kubernetes-ingress (different from community ingress-nginx).

Gateway API Object Model

The Gateway API splits the responsibilities that Ingress crammed into one object across three distinct CRDs:

  1. GatewayClass: declares which controller implementation handles gateways of this class. Think of it like selecting a printer driver: it says "use Traefik" or "use Istio" without coupling the Gateway or Route objects to the specific product. The platform team creates one GatewayClass per controller.
  2. Gateway: the actual entry point, owned by the platform or infrastructure team. It defines which port to listen on, which protocol (HTTP, HTTPS, TCP), and which namespaces are allowed to attach HTTPRoutes. One Gateway can serve traffic for many applications.
  3. HTTPRoute: owned by the application team. It says "requests to this hostname and this URL path should go to this backend Service." Application teams can create and modify HTTPRoutes without touching the Gateway, and without needing cluster-admin access.

This role separation is the main reason the Gateway API replaced Ingress. Platform teams control the entry point; development teams control their own routing rules. Neither group needs to modify the other's objects.

Traefik as the Gateway Controller

Traefik is a modern, actively maintained reverse proxy and load balancer with native Gateway API support. It is deployed inside the cluster as a Deployment (managed via its own Helm chart), watches GatewayClass, Gateway, and HTTPRoute objects, and configures itself accordingly. When you apply an HTTPRoute, Traefik detects it within seconds and begins routing traffic as specified. Unlike the old ingress-nginx, Traefik is under active development with regular security updates.

Step 4: Create the Gateway and HTTPRoutes

Save as demo-gateway.yaml:


# Gateway: the entry point, owned by the platform team.
# This tells Traefik to open a listener on port 80 and accept HTTP traffic.
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: demo-gateway                # referenced by HTTPRoutes in their parentRefs field
  namespace: default
spec:
  gatewayClassName: traefik         # which controller handles this gateway ("traefik" GatewayClass)
  listeners:
  - name: http                      # listener name, referenced in HTTPRoute parentRefs
    protocol: HTTP                  # this listener handles plain HTTP (not HTTPS)
    port: 80                        # listen on port 80 inside the cluster
    allowedRoutes:
      namespaces:
        from: Same                  # only HTTPRoutes in the same namespace can attach here
                                    # use "All" to allow routes from any namespace
---
# HTTPRoute for app1: send /app1 requests to the app1 Service.
# This object is owned by the app1 team; they do not need to modify the Gateway.
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: app1-route
  namespace: default
spec:
  parentRefs:
  - name: demo-gateway              # attach to the Gateway defined above
    namespace: default
    sectionName: http               # attach specifically to the "http" listener
  hostnames:
  - "demo.local"                    # this route only matches requests with Host: demo.local
  rules:
  - matches:
    - path:
        type: PathPrefix            # match any URL path that starts with /app1
        value: /app1
    backendRefs:
    - name: app1                    # forward matching requests to the "app1" Service
      port: 5678                    # the port on the Service (not the container port directly)
---
# HTTPRoute for app2: send /app2 requests to the app2 Service.
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: app2-route
  namespace: default
spec:
  parentRefs:
  - name: demo-gateway
    namespace: default
    sectionName: http
  hostnames:
  - "demo.local"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /app2
    backendRefs:
    - name: app2
      port: 5678

Advanced Features to Know About

  1. Header-based routing: HTTPRoute rules can match on specific HTTP headers, not just paths. Useful for A/B testing or routing mobile vs desktop traffic.
  2. Traffic weighting (canary deployments): a single HTTPRoute rule can split traffic across multiple backendRefs with a weight field. For example, 90% to stable and 10% to canary. This is how progressive delivery works without a dedicated service mesh.
  3. TLS termination: add a https listener to the Gateway referencing a Kubernetes Secret containing a TLS certificate and key. Combine with cert-manager to provision and renew Let's Encrypt certificates automatically.
  4. Redirects and rewrites: HTTPRoute supports filters to redirect HTTP to HTTPS, rewrite URL paths before forwarding to the backend, or add/remove headers.

11. Lab 8: Packaging with Helm

A real application deployed to Kubernetes is rarely a single YAML file. A typical microservice might need a Deployment, a Service, a ConfigMap, a Secret, a ServiceAccount, an RBAC Role, a PodDisruptionBudget, and an HorizontalPodAutoscaler. That is already eight files, and the values inside them differ between dev, staging, and production. Maintaining eight environment-specific YAML files per service, across dozens of services, leads to copy-paste drift, configuration errors, and manual rollbacks.

Helm is the standard package manager for Kubernetes. It solves these problems by packaging all the YAML templates for an application into a single versioned unit called a chart, with all the environment-specific values extracted into a separate configuration file. One command installs the whole application; one command upgrades it; one command rolls it back.

Helm Concepts

  1. Chart: the package. A directory (or a .tgz archive) containing templated Kubernetes manifests, a Chart.yaml with metadata, a values.yaml with default configuration, and optionally a NOTES.txt with post-install instructions.
  2. Repository: a server hosting charts. You add a repository with helm repo add, like adding an apt or npm source. Charts can also be stored in OCI registries (ghcr.io, ECR).
  3. Values: the configuration that customises a chart. A values.yaml file provides defaults; you override specific values with a -f my-values.yaml file or --set key=value on the command line. The same chart produces dev, staging, and prod deployments from different value files.
  4. Release: one installed instance of a chart in a cluster. Each release has a unique name and a revision history. You can install the same chart multiple times with different names and values.
  5. Template: a Kubernetes manifest with Go template placeholders. {{ .Values.replicaCount }} becomes the actual value from your values file at render time. {{ .Release.Name }} is the release name. {{ .Chart.Version }} is the chart version.

Chart Directory Structure

The layout below shows the standard files and folders that make up a Helm chart.


mychart/
  Chart.yaml          # chart metadata: name, version, appVersion, description
  values.yaml         # default configuration values for all templates
  charts/             # dependency charts (subcharts) are placed here
  templates/          # the actual Kubernetes YAML templates
    deployment.yaml   # typical Deployment template using {{ .Values.* }} placeholders
    service.yaml      # Service template
    _helpers.tpl      # reusable template fragments (labels, names, selectors)
    NOTES.txt         # printed to stdout after helm install completes
  .helmignore         # files to exclude when packaging (like .gitignore)

How Templates Work

A template uses Go template syntax with values injected from your values file. For example:


# In templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-app          # becomes "my-nginx-app" if release is named "my-nginx"
  labels:
    chart: {{ .Chart.Name }}-{{ .Chart.Version }}   # e.g. "nginx-1.2.3"
spec:
  replicas: {{ .Values.replicaCount }}   # pulled from values.yaml or --set flag
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    spec:
      containers:
      - name: app
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"


# In values.yaml (defaults that get substituted into the template above)
replicaCount: 1

image:
  repository: nginx
  tag: "1.27-alpine"

helm template my-release ./mychart renders the final YAML locally without applying it to the cluster. This is the foundation of shift-left scanning: pipe the rendered output to Trivy (Lab 11) in CI before any manifest reaches the cluster.

Secrets and Helm

WARNING: Never Put Secrets in values.yaml Helm values files are stored in Kubernetes as Secrets in the release namespace, but they are base64-encoded, not encrypted. Anyone with kubectl get secret access in that namespace can decode them. Never put passwords, API keys, or TLS private keys in values.yaml or in --set flags that appear in shell history. Use sealed-secrets (encrypts secrets in Git) or external-secrets-operator (fetches secrets from Vault, AWS Secrets Manager, GCP Secret Manager) alongside Helm instead.

12. Lab 9: Observability (Metrics, Prometheus, Grafana)

You cannot operate a system you cannot see. Observability is the practice of understanding a system's internal state from its external outputs. Without it, you are debugging production outages with no data, guessing at causes, and reacting to user complaints instead of catching problems proactively. The industry converged on three complementary signals, called the three pillars of observability:

  1. Metrics: numeric time-series data. Examples: CPU usage percentage, HTTP request rate, memory consumption, error count per second. Metrics are cheap to store and excellent for dashboards, alerts, and capacity planning. The trade-off: they tell you something is wrong, not exactly what.
  2. Logs: discrete text records of events. Examples: "user 123 logged in at 14:32", "database query took 450ms", "connection refused to redis:6379". Logs tell you exactly what happened at a specific time. The trade-off: they are expensive to store and search at scale.
  3. Traces: the recorded path of a single request through multiple services. A trace shows which service was slow, which database query took longest, and where an error originated in a chain of microservice calls. The trade-off: they require instrumentation in every service.

This lab focuses on metrics, which is where every cluster's observability journey starts. Logs (Loki) and traces (Tempo, OpenTelemetry) are the natural extensions covered at the end.

Prometheus Architecture

Prometheus is the de facto metrics database for Kubernetes, and a CNCF graduated project. Its architecture differs from traditional monitoring systems in one important way: it uses a pull (scrape) model. Prometheus calls an HTTP endpoint (/metrics) on each monitored target at a regular interval (typically every 15 or 30 seconds) and stores the data. Targets do not push data to Prometheus; Prometheus fetches it. This makes it easier to detect when a target has gone silent.

Time-Series Data Model

Every Prometheus metric is identified by a name and a set of key-value labels:


# Format: metric_name{label1="value1", label2="value2"} numeric_value [timestamp]

http_requests_total{method="GET", status="200", namespace="default"} 14253
http_requests_total{method="POST", status="500", namespace="default"} 7
container_cpu_usage_seconds_total{pod="web-0", container="nginx", namespace="default"} 0.045

Labels are what make Prometheus powerful: you can filter, aggregate, and group metrics by any label combination using PromQL.

Basic PromQL Examples

The queries below show common PromQL expressions for inspecting CPU, memory, and request metrics.


# Current CPU rate per container over the last 5 minutes
rate(container_cpu_usage_seconds_total[5m])

# Total HTTP requests per second, summed by namespace
sum(rate(http_requests_total[5m])) by (namespace)

# Average memory usage across all pods in the "default" namespace
avg(container_memory_usage_bytes{namespace="default"})

# 95th percentile response latency (requires histogram metric type)
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))

# Number of pods not in Running state (useful for alerting)
count(kube_pod_status_phase{phase!="Running"}) by (namespace)

Exporters: Adapters for Non-Native Systems

An exporter is a small process that reads metrics from a system that does not speak Prometheus natively and exposes them in Prometheus format at a /metrics HTTP endpoint. The kube-prometheus-stack installs several automatically:

  1. node-exporter: hardware and OS metrics for each node: CPU, memory, disk I/O, network throughput, filesystem usage. Deployed as a DaemonSet.
  2. kube-state-metrics: Kubernetes object state metrics: number of pods by phase, deployment replica counts, PVC bound status, job completion counts. It exposes the state of the Kubernetes API, not the nodes themselves.
  3. cAdvisor: container resource metrics built into the kubelet: CPU and memory per container. Already present in every node; Prometheus scrapes it directly.

ServiceMonitor: Telling Prometheus to Scrape Your App

How does Prometheus know which pods to scrape? The kube-prometheus-stack uses a CRD called ServiceMonitor. A ServiceMonitor selects Services by label and tells Prometheus which port to scrape on them. The Prometheus operator watches for ServiceMonitor objects and updates Prometheus's scrape configuration automatically. You do not edit Prometheus config files by hand. 


# Example ServiceMonitor: tell Prometheus to scrape the "my-app" Service on port "metrics"
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: my-app-metrics                  # name of the ServiceMonitor
  namespace: monitoring                 # must be in the Prometheus operator's namespace
  labels:
    release: kps                        # MUST match the Helm release label; Prometheus operator
                                        # uses this label to find relevant ServiceMonitors
spec:
  selector:
    matchLabels:
      app: my-app                       # select Services with this label
  namespaceSelector:
    matchNames:
    - default                           # which namespaces to look for Services in
  endpoints:
  - port: metrics                       # which named port on the Service to scrape
    interval: 30s                       # scrape every 30 seconds
    path: /metrics                      # the path to scrape (standard Prometheus path)

Loki and Tempo: Completing the Picture

Metrics show you something is wrong. Logs show you what happened. Traces show you where in the request chain it broke. The Grafana ecosystem provides all three:

  1. Loki: a log aggregation system designed for Kubernetes. Fluent Bit (from Lab 6's DaemonSet example) ships logs to Loki; Grafana queries and visualises them with LogQL. Loki is cheaper to operate than Elasticsearch because it does not index log content, only labels.
  2. Tempo: a distributed tracing backend. Applications instrumented with OpenTelemetry SDKs send traces to Tempo; Grafana shows them alongside metrics and logs. Grafana's "Explore" view links a spike in error rate (metric) directly to the traces and logs from that time window.

13. Lab 10: GitOps with Argo CD

In Section 1, every change to the cluster was made by running kubectl apply from a terminal. This works for learning but fails at production scale for several reasons: there is no audit trail of who changed what and why; the live cluster can silently drift from whatever YAML files exist on a developer's laptop; rebuilding a cluster from scratch after a disaster requires someone to remember all the commands they ran; and there is no review gate before a change takes effect.

GitOps fixes all of these problems with one rule: Git is the single source of truth for all desired cluster state. The cluster must always match what is in a specific Git repository and branch. Every change is a Git commit, meaning it is automatically recorded, peer-reviewed via a pull request, and revertible with git revert. A software controller continuously compares the live cluster to Git and corrects any difference, whether that difference was caused by a deployment, a manual kubectl command, or a node crash.

The GitOps Control Loop

The diagram below shows how Argo CD continuously reconciles the cluster against the desired state declared in Git.

Why GitOps Matters

  1. Audit trail: every cluster change is a Git commit with author, timestamp, and message. No more mystery about who deployed what. git log shows the full history.
  2. Peer review: cluster changes go through pull requests just like application code. Senior engineers review and approve production changes before they are merged.
  3. Disaster recovery: rebuilding a destroyed cluster is a single command pointing Argo CD at the Git repository. The cluster converges to the correct state automatically.
  4. Drift prevention: if anyone runs kubectl scale deployment --replicas=5 by hand, Argo CD detects that the live cluster differs from Git and reverts it. The cluster cannot silently drift.
  5. Separation of duties: CI builds and tests code, then updates an image tag in Git. Argo CD handles all kubectl operations against the cluster. No CI system needs cluster credentials.

Argo CD Key Concepts

  1. Application CRD: the primary object you create. It says: "watch this Git repository at this path, deploy its contents into this cluster and namespace, and keep it in sync." Argo CD watches Application objects and runs a reconciliation loop for each one.
  2. Project: an Argo CD object that restricts which Git repositories and destination clusters an Application is allowed to use. It is the RBAC layer for GitOps: the platform team can grant developers permission to deploy to dev but not prod.
  3. Sync: the act of making the live cluster match the Git state. Can be triggered manually or set to automatic. A sync runs kubectl apply (or kustomize build | kubectl apply, or helm upgrade) under the hood.
  4. Self-heal: when syncPolicy.automated.selfHeal: true, Argo CD automatically reverts any live cluster change that differs from Git. Within about 60 seconds of a manual kubectl change, Argo CD detects and corrects the drift.
  5. Prune: when syncPolicy.automated.prune: true, resources deleted from Git are also deleted from the cluster. Without prune, orphaned resources accumulate.
  6. Drift: when the live cluster state differs from the Git state. Argo CD shows drift visually in its UI and marks the Application as OutOfSync.

Argo CD vs Flux

Both Argo CD and Flux are CNCF-graduated GitOps controllers that implement the same core loop. The main practical differences: Argo CD has a richer web UI and a more feature-complete CLI (argocd) that makes it easier to explore during learning. Flux is more lightweight, with no UI by default, and is preferred by teams that want a minimal control plane. Both are production-grade. This lab uses Argo CD because its UI makes the GitOps concepts visible and inspectable.

  # This finalizer ensures Argo CD deletes all managed resources when the Application is deleted.

      prune: true                       # delete cluster resources that were removed from Git
    syncOptions:
    - CreateNamespace=true              # create the destination namespace if it does not exist

GitOps Repository Structure

Real-world GitOps repositories follow naming conventions to manage multiple environments cleanly. The most common pattern is base/overlays using Kustomize: 


gitops-repo/
  apps/
    guestbook/
      base/                   # common configuration shared by all environments
        deployment.yaml
        service.yaml
        kustomization.yaml
      overlays/
        dev/                  # dev-specific overrides (fewer replicas, debug image)
          kustomization.yaml
          replica-patch.yaml
        staging/
          kustomization.yaml
          replica-patch.yaml
        prod/                 # prod-specific overrides (more replicas, resource limits)
          kustomization.yaml
          replica-patch.yaml

You create one Argo CD Application per environment, each pointing to a different overlay path.

App of Apps Pattern

When a cluster runs dozens of applications, managing dozens of Argo CD Application objects becomes its own problem. The App of Apps pattern solves this: create one root Application whose source is a Git directory containing the Application YAML files for all other applications. Argo CD recursively manages everything. Adding a new application to the cluster becomes a Git commit to the root app directory. 


gitops-repo/
  apps/                        # root Application watches this directory
    guestbook-app.yaml         # Application CRD for the guestbook
    prometheus-app.yaml        # Application CRD for kube-prometheus-stack
    traefik-app.yaml           # Application CRD for Traefik
    my-service-app.yaml        # Application CRD for your own service

CI/CD Integration Pattern

In a GitOps workflow, the CI pipeline builds and tests the application but does not apply anything to the cluster directly. Instead:

  1. CI builds the container image and pushes it to a registry with a new tag (e.g. git-abc1234).
  2. CI updates the image tag in the GitOps repository (a values.yaml or kustomize patch) and opens a pull request.
  3. A human (or automated approval for dev) merges the pull request.
  4. Argo CD detects the new commit and syncs the cluster to the updated image tag.

No CI system ever runs kubectl apply. No CI system needs cluster credentials stored as secrets. Argo CD handles all cluster operations from inside the cluster itself.
