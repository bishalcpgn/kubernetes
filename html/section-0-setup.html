Section 0: Setup

Section 0 prepares your local Kubernetes lab environment. Before you deploy workloads or troubleshoot cluster behavior, you will install the core command-line tools, start a Minikube cluster, verify that kubectl is talking to the right cluster, and learn the daily commands you will use throughout the rest of the guide.

  • Confirm your machine has the required CPU, memory, Docker, curl, and shell tools.
  • Install kubectl, the command-line client for the Kubernetes API.
  • Install and start Minikube as a safe local Kubernetes cluster.
  • Understand kubeconfig, contexts, and how kubectl chooses a cluster.
  • Verify the full setup and learn the common fixes for early setup mistakes.

0. Prerequisites and Minikube Installation

Before writing a single line of Kubernetes YAML, you need a working local cluster and the command-line tool to talk to it. This section walks you through every step from a fresh Linux machine to a fully running Kubernetes cluster on your laptop, explaining what each command does and why it is needed. By the end of this section you will understand not just how to set things up, but what is actually running on your machine.

Why do you need a local cluster at all?

Kubernetes runs in data centers, cloud providers, and edge devices. But experimenting directly on a production or shared cluster is expensive and risky. A local cluster on your laptop gives you a safe, free, isolated environment where you can break things, learn from errors, and rebuild in seconds. Everything you learn here transfers directly to any real cluster.

0.0 What You Are Actually Installing

Two tools are required (labelled A and B below). Understanding what each one does prevents a lot of early confusion.

kubectl: The Kubernetes Command-Line Client

kubectl (pronounced "cube-control", "cube-C-T-L", or "cube-cuttle" ) is the official command-line interface for Kubernetes. It is a single binary that does one job: it translates your commands into HTTPS requests and sends them to a Kubernetes API server.

When you type kubectl get pods, kubectl reads a configuration file called kubeconfig (located at ~/.kube/config by default), finds the address of the API server and the credentials to use, constructs an HTTPS GET request to the API server's /api/v1/namespaces/default/pods endpoint, and then formats the JSON response into the table you see in your terminal. kubectl itself does not run any containers or make any scheduling decisions. It is purely a client that speaks the Kubernetes API.

Minikube: A Local Kubernetes Cluster in a Container

Minikube is a tool that creates a fully functional Kubernetes cluster on your local machine, intended for learning and development. By default it uses Docker as its "driver", which means it starts a Docker container and runs the entire Kubernetes control plane and a worker node inside that container.

Minikube also manages a few extra conveniences: it installs a CNI (Container Network Interface) plugin for pod networking, it can enable add-ons like an Ingress controller or the Kubernetes Dashboard, and it provides the minikube tunnel command to emulate LoadBalancer services on your laptop.

Minikube is for learning and development only

Minikube runs a single-node cluster. In production you always have at least three control-plane nodes (for high availability) and separate worker nodes. Minikube intentionally collapses everything into one machine so you can run it on a laptop. The Kubernetes concepts and commands are identical, but do not use Minikube to run real workloads.

0.1 Prerequisites Check

Before installing anything, verify your environment meets the minimum requirements.

Hardware Requirements

  1. CPU: at least 2 cores available (4 recommended). Kubernetes control-plane components are not heavy, but later labs add Prometheus, Argo CD, Calico, and Falco, all of which need headroom.
  2. RAM: at least 4 GB free for Minikube (8 GB recommended for the full lab series). If your machine has 8 GB total, close other applications while running labs.
  3. Disk: at least 20 GB free. Container images accumulate quickly.
  4. Network: internet access during installation (images are pulled from Docker Hub and gcr.io).

Check Docker

Docker must be installed and running, and your user must be in the docker group so that Minikube can create containers without sudo.

iCheck Docker is installed
docker --version
iiCheck the Docker daemon is running
docker info
# If this errors: sudo systemctl start docker
iiiVerify Docker can run a container
docker run --rm hello-world
# Expect: "Hello from Docker!"
ivAdd your user to the docker group
sudo usermod -aG docker $USER
# Log out and back in, or run: newgrp docker
Why does Minikube need Docker without sudo?

Minikube runs as your regular user and spawns Docker containers to create the cluster. If Docker requires root privileges, Minikube cannot create the cluster node container. Adding your user to the docker group delegates container management permissions to your user without requiring every command to use sudo.

Check curl and other utilities

These commands confirm the download and checksum tools used later in this section are present.

iCheck curl is installed
curl --version
iiCheck sha256sum is installed
sha256sum --version
iiiInstall curl if missing
sudo apt-get install -y curl         # Debian/Ubuntu
sudo dnf install -y curl             # Fedora/RHEL

Operating System Notes

This guide uses Linux (x86-64)

All installation commands below target Linux on x86-64 (also called amd64). If you are on a different platform, use the appropriate alternative:

  1. macOS (Intel or Apple Silicon): install both tools with Homebrew: brew install kubectl minikube. Homebrew automatically picks the right architecture.
  2. Windows 10/11: use WSL2 (Windows Subsystem for Linux) with an Ubuntu distribution, then follow the Linux instructions inside WSL2. Alternatively, use winget install Kubernetes.kubectl and winget install Kubernetes.minikube in PowerShell.
  3. Linux ARM64 (Raspberry Pi, AWS Graviton, Apple M-series in a VM): replace amd64 with arm64 in all download URLs below.

Once installed, all kubectl and minikube commands in this guide are identical regardless of your operating system.

0.2 Install kubectl

kubectl is distributed as a single static binary. There is no package to install, no dependency to resolve. You download the binary, verify it, and move it to a directory in your PATH.

Download, Verify, and Install

These commands download the kubectl binary, verify its checksum, and install it into your PATH.

iFind the latest stable kubectl version
KUBECTL_VERSION=$(curl -L -s https://dl.k8s.io/release/stable.txt)
echo "Will install: $KUBECTL_VERSION"
iiDownload the kubectl binary
curl -LO "https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/linux/amd64/kubectl"
iiiDownload the SHA-256 checksum file
curl -LO "https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/linux/amd64/kubectl.sha256"
ivVerify the download integrity
echo "$(cat kubectl.sha256)  kubectl" | sha256sum --check
# Expected: "kubectl: OK". If you see FAILED, re-download both files
vInstall the binary into /usr/local/bin
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
viClean up the downloaded files
rm kubectl kubectl.sha256
viiVerify the kubectl client version
kubectl version --client --output=yaml
What to expect from "kubectl version --client --output=yaml"

You should see YAML output containing major, minor, gitVersion, and other build metadata. If you see "command not found", either the binary is not in /usr/local/bin or that directory is not in your PATH. Run echo $PATH to check.

Version skew: kubectl vs. API server compatibility

The official Kubernetes support policy states that kubectl must be within one minor version of the cluster API server. For example, a v1.30 kubectl can manage clusters running v1.29, v1.30, or v1.31. Using a very old kubectl against a new cluster may cause missing fields or unexpected errors. The install command above always fetches the current stable release, so you will almost never hit this issue in a fresh setup.

Optional: Enable Shell Completion

Shell completion lets you press Tab to auto-complete resource names, flags, and subcommands. This becomes invaluable when working with long resource names. It is optional but highly recommended.

iEnable bash completion
echo 'source <(kubectl completion bash)' >> ~/.bashrc
source ~/.bashrc
iiEnable zsh completion
echo 'source <(kubectl completion zsh)' >> ~/.zshrc
source ~/.zshrc
# Test: type "kubectl config " and press Tab twice

0.3 Install Minikube

Like kubectl, Minikube ships as a single static binary: download it, install it into your PATH, and verify the version.

Download and Install

These commands download and install the Minikube binary and verify the version.

iDownload the Minikube binary
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
iiInstall the binary to /usr/local/bin
sudo install minikube-linux-amd64 /usr/local/bin/minikube
iiiClean up the download
rm minikube-linux-amd64
ivConfirm Minikube is installed
minikube version
# Expected: "minikube version: v1.3x.x" (or similar)

Minikube drivers: Docker vs. others

Minikube supports several "drivers" that determine how it creates the cluster node. The most common options are:

  1. docker (recommended for this guide): runs the cluster node as a Docker container. Fast to start, no VM overhead, works on Linux, macOS, and Windows/WSL2.
  2. virtualbox: creates a real VirtualBox VM. Slower but gives stronger isolation.
  3. kvm2: uses KVM/QEMU virtualization on Linux. Good isolation, faster than VirtualBox.
  4. none: runs Kubernetes components directly on the host (Linux only, requires root). Used in CI/CD pipelines.

For all labs in this guide, use the docker driver unless you have a specific reason not to.

0.4 Starting Minikube

Starting Minikube for the first time does several things: it creates a Docker container, downloads a Kubernetes node image, boots all control-plane components inside that container, configures networking, and writes connection credentials to your kubeconfig file. This first start can take 2-5 minutes on a fast connection.

The Start Command, Flag by Flag

The annotated command below starts Minikube, with each flag explained inline.

# Minimal start: Docker containers act as the cluster node substrate.
minikube start --driver=docker

# Recommended start for this guide. Later labs (Prometheus, Argo CD, Falco)
# need more headroom than the default, so ask for it up front:
#   --cpus=4                     4 CPU cores for the Minikube node
#   --memory=4096                4096 MB (4 GB) of RAM for the node
#   --disk-size=20g              20 GB of virtual disk for images and volumes
#   --kubernetes-version=stable  latest stable Kubernetes version
minikube start \
  --driver=docker \
  --cpus=4 \
  --memory=4096 \
  --disk-size=20g \
  --kubernetes-version=stable
Resource allocation matters a lot

If you give Minikube too little memory, pods in later labs (especially Prometheus with its many components, Argo CD, and Falco) will remain in Pending state forever because no node has enough allocatable memory to schedule them. If a pod is stuck in Pending and kubectl describe pod <name> shows "Insufficient memory", you need to delete and recreate your Minikube cluster with more RAM: minikube delete && minikube start --cpus=4 --memory=6144

What Happens Internally During minikube start

Here is a step-by-step breakdown of what Minikube does when you run the start command:

  1. Driver initialization: Minikube tells Docker to create a new container named minikube using a base image called kicbase (Kubernetes-in-Container base). This image is pre-built by the Minikube team and contains everything needed to run Kubernetes components.
  2. Image pull: If the kicbase image is not cached locally, Docker downloads it from Docker Hub. This is the main reason first startup takes a while.
  3. Container start: Docker starts the minikube container with special flags that allow it to run containers inside itself (this is called "Docker-in-Docker" or DinD). The container is started with elevated privileges so that containerd can run inside it.
  4. Kubernetes bootstrap: Inside the container, Minikube runs kubeadm, the official Kubernetes cluster bootstrapping tool. kubeadm starts etcd, then the API server, then the controller manager, then the scheduler, and finally configures the kubelet.
  5. CNI plugin installation: A Container Network Interface plugin (by default, kindnet) is installed to provide pod-to-pod networking. Without a CNI plugin, pods cannot communicate with each other.
  6. kubeconfig update: Minikube writes a new entry into your ~/.kube/config file containing the API server address, a client certificate, and a client key. It also sets the "current context" to minikube so that kubectl automatically connects to your new cluster.
  7. Readiness check: Minikube polls the API server until all system pods in the kube-system namespace are running, then prints the "Done!" message.

Expected Output During Start

The sample below shows the output a successful minikube start prints, step by step.

* minikube v1.33.x on Linux (amd64)
* Using the docker driver based on user configuration
* Starting control plane node minikube in cluster minikube
* Pulling base image v0.0.xx ...
* Creating docker container (CPUs=4, Memory=4096MB) ...
* Preparing Kubernetes v1.30.x on Docker xx.x.x ...
  - Generating certificates and keys ...
  - Booting up control plane ...
  - Configuring RBAC rules ...
* Configuring bridge CNI (Container Networking Interface) ...
* Verifying Kubernetes components...
  - Using image gcr.io/k8s-minikube/storage-provisioner:v5
* Enabled addons: storage-provisioner, default-storageclass
* Done! kubectl is now configured to use "minikube" cluster and "default" namespace by default

Checking Minikube Status After Start

These commands confirm the cluster is up and the node and system pods are healthy.

iCheck Minikube status
minikube status
# Expected: host: Running · kubelet: Running · apiserver: Running · kubeconfig: Configured
iiCheck the node from kubectl's perspective
kubectl get nodes -o wide
# minikube   Ready   control-plane   ...   192.168.49.2   <none>
iiiCheck all system pods are running
kubectl get pods -n kube-system
# All pods (etcd, kube-apiserver, kube-controller-manager, kube-scheduler,
# coredns, kube-proxy, storage-provisioner) should show Running
If STATUS shows "NotReady" or pods are "Pending"

Wait 60-90 seconds and check again. Some pods take time to pull their images and start. If after 3 minutes the node is still "NotReady", run minikube logs to see what went wrong. Common causes are insufficient Docker permissions, not enough memory allocated, or Docker not running.

0.5 Understanding kubeconfig

The kubeconfig file is the bridge between kubectl and a cluster. It stores all the information kubectl needs to connect to one or more clusters: API server addresses, authentication credentials (certificates, tokens), and named groupings called "contexts".

Where kubeconfig Lives

By default, kubectl looks for its configuration at ~/.kube/config. This is a YAML file that Minikube automatically created and populated when you ran minikube start. 

kubectl config view
# Or view the raw file directly (contains sensitive certificate data)
# cat ~/.kube/config

The Structure of kubeconfig

A kubeconfig file has three main sections: clusters, users, and contexts. 

apiVersion: v1
kind: Config

# clusters: defines the API server addresses and their CA certificates
clusters:
- cluster:
    certificate-authority: /home/user/.minikube/ca.crt   # CA cert to trust
    server: https://192.168.49.2:8443                     # API server address
  name: minikube                                          # a name for this entry

# users: defines authentication credentials
users:
- name: minikube
  user:
    client-certificate: /home/user/.minikube/profiles/minikube/client.crt
    client-key: /home/user/.minikube/profiles/minikube/client.key

# contexts: bind a cluster + user + namespace together under a name
contexts:
- context:
    cluster: minikube     # which cluster entry to use
    user: minikube        # which user entry to use
    namespace: default    # default namespace when none is specified
  name: minikube

# current-context: which context kubectl uses by default
current-context: minikube
Why this three-part design?

The cluster/user/context split lets a single kubeconfig file hold credentials for many clusters. You might have a "minikube" context for local development, a "staging" context pointing to a cloud cluster, and a "prod" context for production. You switch between them with kubectl config use-context <name> without editing the file manually.

Working With Contexts

These commands show and switch the active kubeconfig context and set a default namespace.

iShow the current context
kubectl config current-context
# Output: minikube
iiList all available contexts
kubectl config get-contexts
# The active context is marked with *
iiiSwitch to the minikube context
kubectl config use-context minikube
ivShow cluster info
kubectl cluster-info
# Kubernetes control plane is running at https://192.168.49.2:8443
vSet the default namespace
kubectl config set-context --current --namespace=default

0.6 Verifying the Full Setup

Run these verification commands in order. Each one confirms a different layer of your setup.

iCheck the kubectl client version
kubectl version --client --output=yaml
iiConfirm kubectl can reach the API server
kubectl version
# You should see both clientVersion and serverVersion
# If serverVersion is missing, kubectl cannot reach the cluster
iiiConfirm the node is Ready
kubectl get nodes -o wide
ivConfirm all system pods are healthy
kubectl get pods -A
# All pods should be Running: etcd, kube-apiserver, kube-controller-manager,
# kube-scheduler, coredns, kube-proxy, storage-provisioner
vRun a smoke test pod
kubectl run smoke-test --image=nginx:alpine --restart=Never
kubectl get pod smoke-test --watch
# Watch until STATUS changes from ContainerCreating to Running (Ctrl+C to stop)
viClean up the test pod
kubectl delete pod smoke-test
You are ready to proceed if...

kubectl get nodes shows minikube Ready, and kubectl get pods -A shows all pods in Running state, and your smoke-test pod reached Running before you deleted it. If any of those conditions are not met, see the troubleshooting section below.

0.8 Common Beginner Mistakes and How to Fix Them

Mistake 1: "permission denied" when running Docker commands

Symptom: minikube start fails with "permission denied while trying to connect to the Docker daemon socket".

Cause: Your user is not in the docker group.

sudo usermod -aG docker $USER
# Log out and log back in, or run:
newgrp docker
# Then retry: minikube start --driver=docker ...

Mistake 2: Pods stay in "Pending" state forever

Symptom: You deploy something and it never starts. kubectl describe pod <name> shows "0/1 nodes are available: Insufficient memory".

Cause: Minikube was started with too little memory.

# Delete the existing cluster and recreate with more resources
minikube delete
minikube start --driver=docker --cpus=4 --memory=6144

Mistake 3: kubectl commands go to the wrong cluster

Symptom: You get an error like "the server doesn't have a resource type" or commands seem to affect a different cluster than expected.

Cause: kubectl is pointed at a different context.

kubectl config current-context
# Switch back to minikube
kubectl config use-context minikube

Mistake 4: "Unable to connect to the server" after a reboot

Symptom: kubectl commands fail with "Unable to connect to the server: dial tcp: connect: connection refused".

Cause: Minikube does not start automatically after a reboot. The cluster node container was stopped.

minikube status
# If it shows "host: Stopped", simply start it again:
minikube start
# This is much faster the second time because the node image is already cached.

Mistake 5: kubectl version shows a very old client version

Symptom: kubectl version shows a client version from several years ago.

Cause: You have an old kubectl installed from a system package manager, and it shadows the one you just installed.

which -a kubectl
# Check which one is being used
type kubectl
# If the system version takes precedence, ensure /usr/local/bin comes first in PATH:
export PATH="/usr/local/bin:$PATH"
# Add this line to ~/.bashrc for permanence.

0.9 Useful Minikube Day-to-Day Commands

This cheat sheet collects the Minikube commands you will reach for most often during the labs.

minikube start
minikube stop                          # suspend, preserves state
minikube delete                        # destroy the cluster entirely
minikube dashboard                     # open the web UI in a browser
minikube addons list                   # browse available add-ons
minikube addons enable ingress         # enable an add-on by name
minikube ip                            # get the node IP address
minikube tunnel                        # expose LoadBalancer services locally
minikube ssh                           # shell into the Minikube node
minikube logs --file=minikube.log      # capture startup logs to a file
