14. DevSecOps Security Theory

Security is not something you bolt on at the end. The old model had developers write code, testers test it, and a security team review it just before shipping, by which point a finding could mean redesigning a whole feature. DevSecOps moves security into every stage instead, from the first line of code to the running production system.

This section is the conceptual foundation for all seven security labs that follow. Read it carefully. Every concept introduced here maps directly to a tool or lab exercise.

What DevSecOps Means

The word is a contraction of Development, Security, and Operations. The idea is simple: the three groups that used to work in silos now share responsibility for security outcomes. Developers write secure code and scan their own pull requests. Platform engineers configure admission controls and RBAC. Operations teams monitor runtime behavior. No single team "owns" security; every team contributes to it.

In practice, DevSecOps means that every stage of your pipeline has a security gate:

  1. Code stage: linters and static analysis catch insecure patterns in the IDE.
  2. Build stage: Trivy scans images for CVEs; secret scanners catch leaked credentials.
  3. Registry stage: images are signed with Cosign, and an SBOM (Software Bill of Materials, a machine-readable inventory of every component and version inside the image) is attached as an attestation.
  4. Deploy stage: admission controllers (PSA, Kyverno) reject non-compliant workloads before they run.
  5. Runtime stage: Falco watches kernel syscalls and alerts on suspicious behavior in real time.

The Shift-Left Principle

Imagine a timeline that reads left to right: Write Code on the far left, Running in Production on the far right. "Shifting left" means moving security checks as far left as possible, as early as possible.

Here is a concrete example. Suppose a developer writes a container that runs as the root user (UID 0).

  1. In the IDE. A plugin flags it as you type. Fix time: 30 seconds, one line adding USER 1001 to the Dockerfile.
  2. In CI. Trivy fails the build. Fix time: 10 minutes to read the finding, push, and re-run.
  3. At admission. Pod Security Admission rejects the Pod on kubectl apply. Fix time: 30 minutes to 2 hours, because now a manifest and a redeploy are involved.
  4. At runtime. Falco spots privilege escalation in a live container. Fix time: days, plus incident response and possibly customer notification. The container may already be exploited.

The cost of fixing a security problem grows exponentially the further right it is caught. Shift left.

Defense in Depth: Why You Need Every Layer

No single security control is sufficient. This is called the principle of defense in depth: you layer multiple independent controls so that if one fails, another catches the threat. Here is why each layer alone is not enough:

  1. Scanning alone. Trivy only knows about published CVEs. A zero-day will not appear, and a spotless image can still be deployed with a terrible configuration.
  2. Admission control alone. It blocks bad Pods at deploy time but cannot see what a good Pod does once it is running.
  3. Runtime detection alone. By the time Falco fires, the attacker is already inside. Detection limits damage; it does not prevent the breach.
  4. RBAC alone. It guards the API server, not the network. A compromised container can still reach every other service.

This is why this training tier has seven labs: you need all the layers working together.

The Attack Surface of a Kubernetes Cluster

A Kubernetes cluster has many places an attacker can try to exploit:

  • Image vulnerabilities: outdated packages with known CVEs in your container images.
  • Misconfigurations: containers running as root, privileged mode, excessive capabilities, no seccomp.
  • Excessive RBAC: ServiceAccounts with cluster-admin or wildcard permissions that an attacker can abuse.
  • Lateral movement: once inside one Pod, an attacker tries to reach other services inside the cluster because there are no NetworkPolicies blocking them.
  • Supply chain: a malicious or tampered image slips into the registry and gets deployed.
  • Runtime exploits: a container escape, privilege escalation, or cryptominer running inside a container.
  • Secrets exposure: hardcoded credentials, unencrypted Secrets, or overly-permissioned Secret access via RBAC.

Admission Control: The API Server Gateway

When you run kubectl apply -f pod.yaml, the request travels through the following chain before the object is stored in etcd and a Pod is scheduled:

A webhook is simply an HTTP callback. When a resource is submitted, the API server sends an HTTP request to the webhook server (for example, the Kyverno Pod) with the resource payload. The webhook server responds with "allow" or "deny" (for validating webhooks) or "allow + modified object" (for mutating webhooks).

The key insight: admission control happens before the Pod runs. If a policy rejects a Pod, it never gets scheduled. This is far better than detecting a bad Pod after it is already running.

Kyverno (Lab 15) and Pod Security Admission (Lab 12) both operate as admission controllers. The Kubernetes API server ships with PSA built in. Kyverno is installed as a separate Helm chart and registers itself as a ValidatingWebhookConfiguration and MutatingWebhookConfiguration automatically.

Pod Security Standards: The Three Profiles

Pod Security Standards (PSS) define three fixed security profiles for Pods. They replaced the older PodSecurityPolicy (PSP) resource, which was deprecated in Kubernetes 1.21 and removed in 1.25. PSS is enforced by the built-in Pod Security Admission (PSA) controller.

Privileged: No Restrictions

The privileged profile applies no restrictions whatsoever. A Pod in a privileged namespace can use hostPID, hostNetwork, hostIPC, mount any host path, run as root, use any Linux capability, disable seccomp, and run in fully privileged mode. This profile exists for system components that genuinely need it, such as CNI plugins, storage drivers, and certain monitoring agents. It should never be used for application workloads.

Baseline: Blocks the Most Dangerous Configurations

The baseline profile prevents the most obviously dangerous configurations while remaining compatible with most containerized applications. The fields it inspects live in the Pod spec and in securityContext, the block where a Pod or a container declares its security settings. Baseline specifically blocks:

  1. spec.hostProcess: true (Windows host process containers)
  2. spec.hostNetwork: true (Pod uses the node's network namespace)
  3. spec.hostPID: true (Pod can see all host processes)
  4. spec.hostIPC: true (Pod can access host IPC namespace)
  5. securityContext.privileged: true (full host access)
  6. Dangerous capabilities: NET_ADMIN, SYS_ADMIN, SYS_PTRACE, and others
  7. hostPath volumes (mounting arbitrary host directories)
  8. Non-default AppArmor profiles
  9. proc mount types other than Default

The baseline profile is a good starting point for most teams. It catches the egregious misconfigurations without requiring you to redesign your applications.

Restricted: Maximum Security

The restricted profile is the most secure. It enforces everything in Baseline plus:

  1. Volumes are restricted to specific safe types (ConfigMap, Secret, emptyDir, projected, downwardAPI, PVC)
  2. allowPrivilegeEscalation must be false
  3. The container must not run as root: runAsNonRoot: true
  4. All Linux capabilities must be dropped: capabilities.drop: [ALL]
  5. A seccomp profile must be set: RuntimeDefault or Localhost

Most well-designed applications can run under Restricted. The main challenge is images that are built to run as root (such as stock nginx). For those, you use a rootless variant (such as nginxinc/nginx-unprivileged).

RBAC: Role-Based Access Control

Kubernetes RBAC controls who can do what to which resources via the API server. It is built on four object types, which split cleanly into two pairs: two that describe permissions, and two that hand those permissions to somebody.

  1. Role: a list of allowed verbs on allowed resources, valid inside one namespace.
  2. ClusterRole: the same list, but valid across the whole cluster, and the only kind that can cover cluster-scoped resources such as Nodes.
  3. RoleBinding: grants a Role (or a ClusterRole) to a subject inside one namespace.
  4. ClusterRoleBinding: grants a ClusterRole to a subject across every namespace.

A permission object on its own does nothing. Nobody has any access until a binding connects a role to a subject, which is why the two pairs always appear together. Lab 13 builds all four by hand.

The four RBAC objects and how they combineOptional depth

Subjects are the entities that can take actions:

  1. User: a human operator, identified by their TLS certificate CN or OIDC token. Kubernetes does not manage users natively; they come from an external system.
  2. Group: a collection of users. For example, system:masters is the built-in group that maps to cluster-admin.
  3. ServiceAccount: the identity that a Pod runs as. Created as a Kubernetes object in a namespace. This is what applications use to call the API server.

Verbs are the actions that can be performed:

  1. get: read a single named resource
  2. list: list all resources of a type
  3. watch: stream changes to resources (needed for controllers)
  4. create: create a new resource
  5. update: replace an existing resource
  6. patch: partially modify an existing resource
  7. delete: delete a resource
  8. deletecollection: delete many resources at once

The principle of least privilege means granting only the verbs and resources that a subject actually needs. A monitoring agent that only reads Pod metrics should have get and list on pods only, not create or delete, not access to secrets.

Role vs ClusterRole: a Role is namespace-scoped; it only applies within one namespace. A ClusterRole is cluster-wide. A RoleBinding binds a subject to a Role or ClusterRole within a namespace. A ClusterRoleBinding binds cluster-wide.

Network Security: East-West Traffic

North-south traffic is traffic that enters or leaves the cluster (user requests coming in, responses going out). This is what people usually think of when they think of firewalls.

East-west traffic is traffic between services inside the cluster: Service A calls Service B, and a frontend calls its database. This traffic matters just as much as north-south traffic, and teams overlook it far more often.

How a default-deny policy is built upOptional depth

By default, Kubernetes uses a "default-allow-all" network model: any Pod can reach any other Pod on any port. This is dangerous. If an attacker compromises one Pod (perhaps by exploiting a web application vulnerability), they can immediately begin scanning every other Pod in the cluster, reaching databases, internal APIs, and management endpoints that should never be reachable from a frontend Pod.

NetworkPolicies (Lab 14) address this by letting you define explicit allow rules. The secure model is "default-deny-all, then explicitly allow only the traffic that is required." This is the network equivalent of RBAC's least-privilege principle.

Critically: NetworkPolicies are only enforced if your CNI plugin supports them. The default Minikube CNI (kindnet) silently ignores NetworkPolicies. You must use Calico, Cilium, or another policy-capable CNI for them to have any effect. This is a common source of confusion.

Supply Chain Threats

The supply chain is everything that happens between a developer writing code and that code running in production. Supply chain attacks target the pipeline itself rather than the running application.

  1. Malicious base images. A typosquatted Docker Hub image (ubunut for ubuntu) ships a backdoor into every build that pulls it.
  2. Dependency confusion. An attacker publishes a public package under one of your internal package names, and your build resolves it in preference to the real one.
  3. Compromised build systems. An attacker with CI access injects code after review has passed, so the source looks clean and the artifact is not.
  4. Registry tampering. A mutable tag such as :latest is repointed at a different image after you approved it.

The tools for supply chain security are Cosign (signing), SBOMs (inventory), and Kyverno verifyImages (enforcement at admission). These are covered in Labs 16 and 15 respectively.

Runtime Threats

Even if every build-time and deploy-time control is perfect, a running container can still be compromised:

  1. Container escape. A kernel bug or a privileged container lets an attacker reach the host.
  2. Cryptomining. Someone exploits your app and quietly spends your CPU budget.
  3. Credential theft. A process reads the mounted ServiceAccount token and starts calling the API server as your workload.
  4. Lateral movement. From one compromised Pod, an attacker scans and reaches every other service on a flat network.

Runtime security (Lab 17: Falco) addresses these by watching system calls in real time. Every file open, every network connection, every process spawn results in a syscall that Falco can observe and match against rules.

15. Lab 11: Shift-Left Scanning (Manifests, Images, Secrets)

What we are doing: installing Trivy natively, scanning a YAML manifest for misconfigurations, scanning a container image for CVEs, and scanning a directory for hardcoded secrets. We will then integrate Trivy into a CI pipeline and explore the Trivy Operator, an in-cluster controller that rescans running workloads on its own.

Real-world mapping: In a mature DevSecOps pipeline, every git push triggers a Trivy scan. If a developer accidentally commits a root-running container or a leaked API key, the build fails immediately, before the code ever reaches a staging environment.

What is Trivy?

Trivy (from Aqua Security, open-source, CNCF) is a single binary that can scan many different targets for many different types of security problems. Instead of running five different tools, you run one. This matters because each additional tool in a pipeline adds maintenance burden, version drift, and integration complexity.

Trivy scan targets include:

  1. image: scan a container image for known vulnerabilities (CVEs) in OS packages and language-specific libraries.
  2. filesystem (fs): scan a local directory, including source code dependencies and secrets.
  3. repository (repo): clone and scan a Git repository URL.
  4. config: scan Kubernetes YAML, Dockerfiles, Terraform, and other IaC files for misconfigurations.
  5. sbom: generate a Software Bill of Materials listing every package inside an image.

What is a CVE?

CVE stands for Common Vulnerabilities and Exposures. It is a publicly maintained database of known security flaws, maintained by MITRE Corporation. Every entry has a unique identifier such as CVE-2021-44228 (the Log4Shell vulnerability). When a security researcher or vendor discovers a vulnerability in a software package, they submit it to the CVE database and it is assigned an ID.

Each CVE is also given a CVSS score (Common Vulnerability Scoring System), a number from 0 to 10 that represents severity. The number maps onto four named bands: Critical from 9.0, High from 7.0, Medium from 4.0, and Low below that. Those band names are what scanners print and what you gate a build on, so they matter more in practice than the underlying number.

CVSS severity bands and how teams gate on themOptional depth
  1. Critical (9.0 - 10.0): remotely exploitable with no authentication, often resulting in full system compromise. Fix immediately. Example: Log4Shell (CVSS 10.0).
  2. High (7.0 - 8.9): serious vulnerabilities, often remotely exploitable. Prioritize fixing within days.
  3. Medium (4.0 - 6.9): exploitable under specific conditions. Fix within weeks during normal patch cycles.
  4. Low (0.1 - 3.9): limited exploitability or impact. Track and fix when convenient.
  5. None (0.0): informational, no security impact.

In CI pipelines, most teams fail builds on Critical and High findings only, to avoid alert fatigue from the large number of Medium and Low findings that may exist in any real-world image.

CVEs vs Misconfigurations

CVEs are vulnerabilities in existing software packages (a bug in OpenSSL, a flaw in libcurl). Misconfigurations are how you have set up your workload (running as root, no resource limits, no readiness probe). Trivy can catch both: CVEs via image scanning, misconfigurations via config scanning.

Let us understand each finding:

  1. allowPrivilegeEscalation: false is missing. If a container does not explicitly disable privilege escalation, any process inside it can use sudo, setuid binaries, or kernel exploits to become root even if it started as a non-root user.
  2. runAsNonRoot: true is missing. The container starts as the root user (UID 0). If the application is compromised, the attacker is already root inside the container, making a container escape to the host node much easier.
  3. readOnlyRootFilesystem: true is missing. A writable root filesystem lets an attacker install tools (netcat, curl, a reverse shell) inside the container after gaining access, making the attack easier to expand.
  4. capabilities.drop: [ALL] is missing. Linux capabilities are fine-grained privileges (like the ability to bind to ports below 1024, or modify network interfaces). By default, containers get a generous set. Dropping all capabilities and adding back only what is needed reduces the blast radius of a compromise.

16. Lab 12: Pod Security Standards and Admission

What we are doing: labeling a namespace with Pod Security Admission controls, observing the rejection of an insecure Pod, understanding each violation field, deploying a fully compliant hardened Pod, and verifying it truly runs as a non-root user.

Real-world mapping: Container escape is a class of attack where an attacker who has compromised a container tries to break out of its sandbox and access the host node. Containers running as root, with extra Linux capabilities, or in privileged mode make escape dramatically easier. Pod Security Standards close the most common escape routes at the admission layer, before the Pod ever runs.

Why Pod Security Standards Exist: Replacing PSP

Before Kubernetes 1.21, the way to enforce security policies on Pods was a resource called PodSecurityPolicy (PSP). PSP was powerful but notoriously difficult to configure correctly. It had confusing interaction with RBAC (you had to grant a ServiceAccount permission to "use" a PSP, which caused many accidental misconfigurations). PSP was deprecated in 1.21 and removed entirely in 1.25.

Pod Security Standards (PSS) replaced PSP with a simpler model: three fixed, well-documented profiles (Privileged, Baseline, Restricted) that are enforced by the built-in Pod Security Admission (PSA) controller. The model needs no RBAC grants at all. You label a namespace, and PSA does the rest.

When you need more than the three fixed profiles: ValidatingAdmissionPolicy. PSS gives you exactly three profiles and nothing in between. When you need custom, organisation-specific rules, you have two native options. ValidatingAdmissionPolicy is built into the API server and expresses rules in CEL (the Common Expression Language) with no external webhook to run or secure, making it fast and highly available; it is ideal for relatively simple field checks. For richer policies (mutation, generation, image-signature verification, cross-resource lookups) a policy engine like Kyverno (Lab 15) is the more capable choice. A common production setup is PSS for the baseline, ValidatingAdmissionPolicy for lightweight custom guardrails, and Kyverno for everything else.

The Three Enforcement Modes

PSA operates in three modes. Crucially, you can apply different modes for different profiles on the same namespace.

  1. enforce: Pods that violate the policy are rejected by the API server. They will not be created. kubectl apply returns an error. This is the strongest mode.
  2. audit: Pods that violate the policy are allowed to run, but the violation is recorded in the Kubernetes audit log. Useful for understanding what is running in production before you flip to enforce.
  3. warn: Pods that violate the policy are allowed to run, but kubectl prints a warning message in the terminal output. Useful for notifying developers without breaking anything yet.

The label format is: pod-security.kubernetes.io/<MODE>=<PROFILE>

For example, to warn developers about baseline violations while strictly enforcing restricted: 

kubectl label namespace my-namespace \
  pod-security.kubernetes.io/warn=baseline \
  pod-security.kubernetes.io/enforce=restricted

# warn=baseline      prints a warning if baseline is violated
# enforce=restricted  hard-rejects anything that violates restricted

securityContext Fields Explained One by One

The securityContext block is where you configure a container's security behavior. It can appear at the Pod level (applies to all containers in the Pod) and at the container level (applies to one container, overrides the Pod-level setting for that field).

The full field reference is below. Lab 12 uses the important ones in context.

Every securityContext field, one by oneOptional depth
  1. runAsNonRoot: true - Kubernetes checks that the container's effective user ID is not 0 (root) at startup. If the container image's default user is root and you do not specify runAsUser, the Pod is rejected.
  2. runAsUser: 10001 - Sets the UID the container process runs as. Choose any number above 999. Many hardened images declare a specific user in their Dockerfile (e.g., USER 101). You can override it here.
  3. runAsGroup: 10001 - Sets the primary GID (group ID) of the container process.
  4. fsGroup: 2000 - Sets the group ID for mounted volumes. Files created in mounted volumes will be owned by this group. Useful when a non-root process needs to write to a PersistentVolume.
  5. allowPrivilegeEscalation: false - Prevents any process inside the container from gaining more privileges than it started with. Specifically, it sets the no_new_privs Linux flag, which blocks setuid binaries (like sudo) from elevating to root.
  6. readOnlyRootFilesystem: true - Makes the container's root filesystem read-only. If an attacker gains a foothold, they cannot install tools, write scripts, or persist changes to the filesystem. Writable paths (like a temp directory) must be explicitly mounted as emptyDir volumes.
  7. capabilities.drop: ["ALL"] - Drops all Linux capabilities from the container. Linux capabilities are fine-grained bits of privilege: CAP_NET_BIND_SERVICE (bind to port below 1024), CAP_SYS_ADMIN (a very broad privilege used in many exploits), CAP_NET_ADMIN (configure network interfaces), etc. Dropping all capabilities and adding only what is needed is the principle of least privilege applied to the kernel.
  8. capabilities.add: ["NET_BIND_SERVICE"] - After dropping all capabilities, add back only the specific ones the application requires. For example, a web server that needs to bind to port 80 needs NET_BIND_SERVICE.
  9. seccompProfile.type: RuntimeDefault - Seccomp (Secure Computing Mode) is a Linux kernel feature that filters which system calls a process is allowed to make. RuntimeDefault uses the default filter provided by the container runtime (containerd or CRI-O), which blocks several hundred dangerous syscalls while allowing the vast majority that normal applications need. This is required by the Restricted PSS profile.
  10. privileged: true - Gives the container full access to the host, equivalent to running a process directly on the node. Blocked by the Baseline profile. Only used for certain system components that truly need it (old-style CNI plugins, certain storage drivers). Never use in application workloads.
The next level of isolation: user namespaces. Running as non-root (runAsNonRoot) means the container is not UID 0 inside the container, but by default it still shares the host's user-ID space, so a container UID can still map to a privileged host UID after an escape. Kubernetes user namespaces close that gap: with spec.hostUsers: false, the Pod's UIDs are remapped to an unprivileged range on the host, so even root inside the container is a harmless, unprivileged user on the node. It needs a container runtime that supports it (containerd/CRI-O with the right config) and is the strongest built-in defence against container-escape privilege escalation. Treat it as the layer beyond runAsNonRoot once your runtime supports it.

What Happens Internally When a Pod is Rejected

When you run kubectl apply -f bad-pod.yaml, the request goes to the API server. The API server runs the PSA admission controller, which reads the namespace's labels, identifies that enforce=restricted is set, and checks the Pod spec against every rule in the Restricted profile. Finding four violations, it returns an HTTP 403 Forbidden response with the detailed error message above. The Pod object is never written to etcd. No scheduling happens. The rejection is immediate and complete.

Step 5: Understanding the readOnlyRootFilesystem + emptyDir Pattern

A common misconception is that readOnlyRootFilesystem: true breaks any application that writes files. In practice, most applications write to a small number of known directories (temp files, caches, PID files, sockets). You explicitly mount writable emptyDir volumes at those paths.

PSA Exemptions

Some system-level workloads genuinely need to bypass PSS (for example, a CNI plugin that needs host networking). You can configure exemptions in the PSA admission controller configuration (a cluster-level setting): 

# /etc/kubernetes/admission-configuration.yaml (on the API server node)
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: PodSecurity
  configuration:
    apiVersion: pod-security.admission.config.k8s.io/v1
    kind: PodSecurityConfiguration
    defaults:
      enforce: "baseline"       # default profile for unlabeled namespaces
    exemptions:
      usernames: []
      runtimeClasses: []
      namespaces:
      - kube-system             # system namespace is always exempt
      - calico-system           # exempt CNI namespace

  2. Use Kyverno (Lab 15) when: you need custom rules that go beyond the three fixed profiles. For example: require specific image registries, mandate resource limits, require specific labels, verify image signatures, auto-generate NetworkPolicies for new namespaces. PSS cannot express these; Kyverno can.

17. Lab 13: Least-Privilege RBAC

What we are doing: building a complete RBAC chain from scratch: ServiceAccount, Role with minimal verbs, and RoleBinding. We then verify the permission boundary with kubectl auth can-i from multiple angles and deploy a Pod that uses the ServiceAccount.

Real-world mapping: IAM Governance. CI/CD agents (Argo CD), logging sidecars, and developer tooling should hold only the permissions they need. A stolen token with cluster-admin access can delete every resource in the cluster. Granular RBAC limits blast radius to the minimum necessary.

RBAC Conceptual Foundation

Kubernetes RBAC (Role-Based Access Control) answers one question: Is this subject allowed to perform this verb on this resource? The answer flows through a chain of three objects.

The flow is one-directional: the API server receives a request, looks up all RoleBindings and ClusterRoleBindings that reference the requesting subject, collects the rules from the referenced Roles and ClusterRoles, and checks whether any rule permits the requested verb on the requested resource. If no rule matches, access is denied (default-deny).

The Four RBAC Object Types

Role (namespace-scoped)

A Role grants permissions within a single namespace. It cannot grant access to cluster-scoped resources (like Nodes) or resources in other namespaces. Most application permissions belong here.

ClusterRole (cluster-wide)

A ClusterRole grants permissions across the entire cluster or to cluster-scoped resources. Use sparingly. Built-in ClusterRoles like view, edit, and admin are defined by Kubernetes itself.

RoleBinding (binds a Role or ClusterRole to subjects in one namespace)

A RoleBinding says: "In namespace X, subject S has the permissions defined in Role R." A RoleBinding can reference either a Role (namespace-scoped) or a ClusterRole (the ClusterRole's rules are then scoped down to just that namespace).

ClusterRoleBinding (binds a ClusterRole cluster-wide)

A ClusterRoleBinding says: "Everywhere in the cluster, subject S has the permissions defined in ClusterRole R." Use only when cluster-wide access is truly required (e.g., a cluster monitoring agent that must read nodes in all namespaces).

Subjects: Who Can Be Granted Permissions

  1. User: a human identity, authenticated via a client certificate (the CN field becomes the username) or an OIDC token. Kubernetes has no built-in user database: it trusts external identity providers.
  2. Group: a set of users. Membership is determined by the OIDC provider or the certificate's O (organization) field. The built-in group system:authenticated contains every authenticated user.
  3. ServiceAccount: an identity for Pods running inside the cluster. Every Pod runs as exactly one ServiceAccount. A token is automatically mounted at /var/run/secrets/kubernetes.io/serviceaccount/token unless explicitly disabled. The full username format is system:serviceaccount:<namespace>:<name>.

All Verbs Explained

Every RBAC rule is a list of verbs. The table below maps each verb to the HTTP request it authorizes and to what a subject can actually do with it.

Verb HTTP Method What it does
get GET (single) Read one specific resource by name
list GET (collection) List all resources of a type (returns a collection)
watch GET with watch param Stream change events as resources are created, updated, or deleted
create POST Create a new resource
update PUT Replace an entire resource (full object required)
patch PATCH Partial update: only send the fields you want to change
delete DELETE (single) Delete one specific resource by name
deletecollection DELETE (collection) Delete all resources matching a label selector in bulk
use special Required to use a PodSecurityPolicy or certain admission resources (legacy)
Using "*" as a verb or resource is effectively granting everything. An account with verbs: ["*"] on resources: ["*"] can do anything including deleting namespaces and reading secrets. This is equivalent to cluster-admin and must never be granted to application service accounts.

Resources and Subresources

Subresources are distinct from their parent and must be listed separately in RBAC rules:

  1. pods: read pod metadata and spec
  2. pods/log: read stdout/stderr logs from a running container (separate permission from pods)
  3. pods/exec: open an exec session into a container (equivalent to SSH access, grant with extreme caution)
  4. pods/portforward: forward a local port to a port inside the pod
  5. deployments: manage Deployments (apps API group)
  6. services: manage Services
  7. secrets: read or write Secrets (contains sensitive data, restrict aggressively)
  8. configmaps: read or write ConfigMaps

Built-in ClusterRoles

Kubernetes ships four general-purpose ClusterRoles so that you do not have to write the common permission sets yourself. The table below shows how much access each one grants and who should hold it.

ClusterRole Access Level Appropriate Use
cluster-admin Full access to everything Never for application accounts. Break-glass emergencies only, with audit logging.
admin Full control within a namespace (except quota) Namespace owners, team leads
edit Read/write most namespace resources, no RBAC Developers who deploy apps
view Read-only on most namespace resources, no secrets Read-only dashboards, observability tools
cluster-admin is the most dangerous ClusterRole. A compromised token with this binding can delete the entire cluster, exfiltrate all secrets, and escalate to node access. Never bind it to application ServiceAccounts, CI/CD agents, or users in production.

ServiceAccount Token Automounting

By default, Kubernetes mounts a ServiceAccount token into every Pod at a well-known path. Any process inside the Pod can use this token to call the Kubernetes API. If your Pod does not need API access (most application Pods do not), disable automounting:

apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  automountServiceAccountToken: false  # do not mount API token into this pod
  containers:
  - name: app
    image: my-app:1.0

You can also set automountServiceAccountToken: false on the ServiceAccount object itself, which applies to all Pods using that ServiceAccount unless overridden per-Pod.

RBAC Anti-Patterns to Avoid

  1. cluster-admin for application service accounts: no application should need cluster-admin. If it seems necessary, re-evaluate the architecture.
  2. Wildcard verbs or resources: verbs: ["*"] and resources: ["*"] grant everything. Always enumerate explicitly.
  3. Binding to the default ServiceAccount: the default ServiceAccount exists in every namespace. Binding RBAC to it affects every Pod that does not specify a ServiceAccount, which is often all of them.
  4. Forgetting subresources: granting pods does not grant pods/exec. An application that only needs to list pods must not be granted exec access.
  5. RoleBinding in the wrong namespace: a RoleBinding must be in the same namespace as the Role it references. A RoleBinding in default referencing a Role in production will fail or be rejected.

18. Lab 14: Network Microsegmentation

What we are doing: starting a Calico-enabled cluster, deploying a frontend and a database Pod, confirming the default open connectivity, applying a default-deny NetworkPolicy, verifying that connectivity is broken, then restoring only the specific path we need with a targeted allow policy. We also write an egress policy that permits only DNS.

Real-world mapping: Zero-Trust East-West. Perimeter firewalls protect the north-south boundary (internet to cluster) but do nothing about east-west traffic (service to service inside the cluster). If an attacker exploits a public-facing web pod, they can freely reach every database, internal API, and management endpoint unless NetworkPolicies segment the traffic.

East-West Traffic: The Default Problem

By default, Kubernetes allows all Pods to communicate with all other Pods in all namespaces. This flat network model is simple but dangerous. A compromised Pod can:

  1. Port-scan the entire cluster network to discover services
  2. Connect directly to database Pods that are not meant to be publicly accessible
  3. Reach the Kubernetes API server from inside a Pod using its mounted ServiceAccount token
  4. Pivot to other namespaces including kube-system

NetworkPolicy: Pod-Level Firewall Rules

A NetworkPolicy is a Kubernetes object that defines ingress and egress rules for a selected set of Pods. Unlike AWS Security Groups (which are enforced by the cloud provider), NetworkPolicies are enforced by the CNI (Container Network Interface) plugin. Kubernetes itself does not enforce them.

Configured does not mean enforced. The Kubernetes API will accept a NetworkPolicy object regardless of whether the CNI enforces it. Flannel (the default Minikube CNI) accepts NetworkPolicy objects but silently ignores them. Always verify enforcement with a live connectivity test after applying a NetworkPolicy.

Which CNI Plugins Enforce NetworkPolicies

Enforcement depends entirely on which CNI plugin the cluster runs. The table below lists the common plugins and says whether a NetworkPolicy has any effect under each one.

CNI Plugin Enforces NetworkPolicies Notes
Calico Yes Also has its own CRD-based policy system with more features
Cilium Yes Also supports L7 HTTP policies and identity-based policies via eBPF
Flannel (default) No Policies are accepted but silently ignored. Not suitable for security enforcement.
Weave Net Yes Full NetworkPolicy support
Minikube default No Uses kindnet, which does not enforce NetworkPolicies

NetworkPolicy Structure Explained

The annotated manifest below breaks down each field of a NetworkPolicy and what it controls.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: example-policy
  namespace: my-namespace                  # policies are namespace-scoped
spec:
  podSelector:                             # which pods this policy applies to
    matchLabels:
      app: database                        # applies only to pods with label app=database
                                           # empty podSelector ({}) means: apply to ALL pods in namespace
  policyTypes:
    - Ingress                              # control incoming traffic to selected pods
    - Egress                              # control outgoing traffic from selected pods
                                           # if policyTypes includes Egress but egress rules are absent,
                                           # all egress from selected pods is DENIED
  ingress:
    - from:
        - podSelector:                     # allow from pods with matching labels in SAME namespace
            matchLabels:
              app: frontend
        - namespaceSelector:               # allow from pods in namespaces with matching labels
            matchLabels:
              team: backend
        - ipBlock:                         # allow from a CIDR range (useful for external IPs)
            cidr: 10.0.0.0/8
            except:
              - 10.0.5.0/24               # exclude a sub-range from the CIDR
      ports:
        - protocol: TCP
          port: 6379                       # only allow on this specific port
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: cache
      ports:
        - protocol: TCP
          port: 6379
When podSelector and namespaceSelector appear as sibling list items under from, they are OR conditions (either selector matches). When they are nested (namespaceSelector AND podSelector in the same list item), they are AND conditions. This is a common source of policy mistakes.

The Default-Deny Pattern

A NetworkPolicy with an empty podSelector ({}) matches all Pods in the namespace. A policy with no ingress rules but policyTypes: [Ingress] denies all ingress to those Pods. Combining these creates the default-deny-all pattern that is the foundation of zero-trust networking.

NetworkPolicy Limitations

  1. No FQDN-based rules: you cannot write "allow egress to api.example.com". Rules must use IP CIDR blocks or pod/namespace selectors. Cilium's CiliumNetworkPolicy extends this with FQDN support.
  2. No native packet logging: NetworkPolicies don't log dropped packets. You need Calico or Cilium's observability features (Hubble for Cilium) to see what is being blocked.
  3. No L7 awareness: standard NetworkPolicies operate at L3/L4 (IP, TCP/UDP, port). They cannot distinguish between GET /api and POST /admin on the same port. Cilium's CiliumNetworkPolicy supports HTTP method/path filtering.
  4. Namespace isolation requires namespace labels: to use namespaceSelector in a policy, the target namespace must have a label. Add labels with kubectl label namespace kube-system team=system.

Cilium: The Next-Level CNI

Cilium uses eBPF (Extended Berkeley Packet Filter) to enforce policies at the Linux kernel level with very low overhead. Beyond standard NetworkPolicy, Cilium supports:

  1. L7 HTTP policies: allow GET /api but deny POST /admin on the same port
  2. FQDN-based egress: allow egress to "*.amazonaws.com"
  3. Identity-based policies: use cryptographic workload identity instead of IP addresses (which change as pods restart)
  4. Hubble observability: a built-in network observability layer that shows real-time flow data and dropped packet reasons

Real-world mapping: Org-Specific Guardrails. Pod Security Standards cover the baseline. Organizations need additional rules: approved registries only, required labels for ownership tracking, no :latest tags, mandatory resource limits, and image signature verification. What Policy-as-Code Means

Policy-as-code means expressing security and operational rules as machine-readable, version-controlled YAML files stored in Git alongside application code. The same GitOps workflow that deploys applications also deploys policies. Benefits include:

  1. Every policy change is peer-reviewed via a pull request
  2. Every policy change is auditable via git history
  3. Policies can be tested in CI before deployment to production
  4. Policies apply consistently across all clusters synced from the same Git repository

Kyverno versus OPA/Gatekeeper

Kyverno and OPA/Gatekeeper are the two policy engines you will meet most often. The table below compares them on the attributes that usually decide which one a team adopts.

Attribute Kyverno OPA/Gatekeeper
Policy language Plain Kubernetes YAML Rego (a custom functional language)
Learning curve Any Kubernetes user can write policies Rego requires dedicated learning
Mutation support Yes, built-in with patching Limited (separate mutating webhook)
Generate resources Yes, built-in No (not a primary use case)
Image verification Yes, built-in verifyImages rule Requires external tooling
Policy testing CLI kyverno test opa test / conftest

Kyverno's Four Capabilities

1. Validate: Block Bad Resources

A validate rule rejects any resource that breaks it, at admission time, before the object is ever stored. Use it to block a Pod that carries the :latest image tag, one that sets no resource limits, or one that runs as root.

2. Mutate: Auto-Fix Resources

A mutate rule edits an incoming resource before it is stored, so the object that lands in etcd is not quite the one the author submitted. Use it to fill in a missing securityContext, stamp owner labels onto every Pod, or force imagePullPolicy: IfNotPresent.

3. Generate: Create Resources Automatically

A generate rule creates additional resources in response to one being created. The usual use is bootstrapping a namespace: the moment someone creates one, Kyverno drops in a default-deny NetworkPolicy, a LimitRange, and a ResourceQuota, so no namespace is ever born unprotected.

4. Verify Images: Block Unsigned Container Images

A verifyImages rule checks, at admission time, that a container image carries a valid cryptographic signature from a signer you trust, and blocks anything unsigned or wrongly signed before it runs. It reads the same Cosign and Sigstore signatures that Lab 16 produces.

How Kyverno Runs as an Admission Webhook

When Kyverno is installed, it registers a ValidatingWebhookConfiguration and a MutatingWebhookConfiguration with the Kubernetes API server. After that, every CREATE and UPDATE request for matching resource types is sent to Kyverno before being stored in etcd. Kyverno evaluates the request against all matching policies and either allows it (possibly with mutations applied), denies it with an error message, or allows it and records a violation in the PolicyReport.

Audit versus Enforce Mode

Every Kyverno validate policy runs in one of two modes. Audit records a violation and admits the resource anyway; Enforce rejects the resource at admission and returns an error to the caller.

Always deploy new policies in Audit mode first. Enforce mode will immediately block non-compliant resources, including existing workloads that get restarted or updated. Audit mode lets you see the blast radius (how many existing resources would fail) before you commit to enforcement.

Real-world mapping: Prove What You Run. Anyone with registry push access can push a malicious image under your namespace. Together they enable rapid incident response: when Log4Shell was announced, teams with SBOMs could immediately query which images contained the vulnerable library.

The Supply Chain Threat Landscape

Supply chain attacks inject malicious code at any point between writing source code and running it in production:

  1. SolarWinds (2020): attackers with access to the build environment injected malicious code into legitimate build outputs. The signed update package passed all standard checks because the signing happened after the injection.
  2. XZ Utils (2024): a malicious backdoor was inserted into a widely-used compression library by a long-term social engineering attack on the maintainer. The library was included in many container base images.
  3. Dependency confusion: attackers publish packages to public registries with names that shadow internal packages, causing builds to pull the attacker-controlled version.

SLSA: Supply Chain Levels for Software Artifacts

SLSA (pronounced "salsa") is a framework defining four levels of supply chain integrity:

Level Requirement
SLSA 1 Build process is scripted (not manual); provenance is generated
SLSA 2 Build service generates signed provenance; source is version controlled
SLSA 3 Build is isolated and reproducible; provenance is from a hardened build platform
SLSA 4 All dependencies are also at SLSA 4; two-party review of all changes

The Sigstore Project

Sigstore is an open-source project (part of the OpenSSF) that provides free, vendor-neutral infrastructure for signing software artifacts. Its three components work together:

Cosign

Cosign is the command-line tool that signs container images, blobs, and other artifacts. It can sign with a private key file, a KMS key (AWS KMS, GCP KMS, HashiCorp Vault), or keylessly using OIDC identity. Signatures are stored as OCI artifacts in the same container registry alongside the image.

Fulcio

Fulcio is a certificate authority that issues short-lived signing certificates tied to your OIDC identity. You authenticate to Fulcio using GitHub, Google, or Microsoft identity. Fulcio issues a certificate that expires after 10 minutes: long enough to sign, short enough that a stolen certificate is useless. The certificate proves "this signature was made by the holder of this OIDC identity at this time."

Rekor

Rekor is a public, tamper-evident transparency log that permanently records every signature. Once recorded, entries cannot be deleted or modified (it uses a Merkle tree structure similar to certificate transparency logs). This means anyone can independently verify that a signature existed and was made by a specific identity at a specific time.

21. Lab 17: Runtime Security with Falco

What we are doing: installing Falco as a DaemonSet using the eBPF driver, running a victim Pod, triggering three different detections (shell in container, reading a sensitive file, writing a binary to /tmp), reading and understanding the alert format, and writing a custom Falco rule.

Real-world mapping: Catching What Slips Through. Vulnerability scanning (Lab 11), admission control (Labs 12, 15), RBAC (Lab 13), and network policy (Lab 14) are all preventive controls. They stop known bad configurations and unsigned images. But zero-day vulnerabilities, misconfigurations that pass all checks, insider threats, and attacks on running infrastructure cannot be caught before deployment. Runtime security is the last line of defense: it detects what is actually happening inside running containers.

Why Runtime Detection Is Necessary

Preventive controls have inherent gaps:

  1. Zero-day vulnerabilities: a CVE that has not yet been published is not in any scanner database. An attacker using an unknown exploit bypasses all scanning.
  2. Misconfiguration drift: a configuration that passes admission may change over time (e.g., a container overwrites its own binary, a process gains capabilities at runtime).
  3. Post-exploitation behavior: an attacker who compromises a container will exhibit predictable behaviors: spawning a shell, reading credential files, establishing a reverse shell. These behaviors are detectable regardless of how they got in.
  4. Insider threats: a legitimate developer who has kubectl exec access can abuse it. Falco detects the shell, even if the RBAC allows it.

eBPF: The Technology Behind Modern Runtime Security

eBPF (Extended Berkeley Packet Filter) is a Linux kernel feature that allows small, sandboxed programs to run inside the kernel in response to events. These programs are verified by the kernel before running: they cannot crash the kernel, cannot loop forever, and cannot access arbitrary memory. This makes eBPF ideal for observability and security tooling.

When a container process makes a system call (syscall), the Linux kernel executes it. An eBPF probe intercepts the syscall at the kernel level and sends event data to a user-space process (Falco) with near-zero performance overhead. No process inside the container can hide from eBPF-based monitoring: the observation happens below the container's view of the world.

System Calls: The Lens Into Container Behavior

Every meaningful action a container process takes requires a system call to the Linux kernel:

Action Syscall(s)
Open a file open, openat
Write to a file write, pwrite64
Spawn a child process clone, execve, fork
Open a network connection connect, accept, bind
Change file permissions chmod, fchmod
Read /etc/passwd open + read on that path
Escalate capabilities setuid, setgid, capset

Falco watches these syscalls and evaluates each event against its rules engine to detect suspicious patterns.

Falco Rule Structure

The annotated rule below breaks down the fields that make up a Falco detection rule.

# Structure of a Falco rule (YAML syntax)
- rule: Terminal Shell in Container          # unique rule name; appears in alert output
  desc: >-                                   # human-readable description for documentation
    A shell was started inside a container.
    This may indicate post-exploitation activity.
  condition: >-                              # the detection condition: Falco filter expression
    spawned_process                          # macro: true when a new process is spawned
    and container                            # macro: true when the process is inside a container
    and shell_procs                          # macro: true when the process is a shell (sh, bash, zsh, etc.)
    and proc.tty != 0                        # filter: process has a terminal (interactive shell)
  output: >-                                 # what to log when the rule fires
    Terminal shell in container
    (user=%user.name                         # the OS user name running the shell
     container=%container.name              # container name from Docker/containerd
     image=%container.image.repository      # container image (without tag)
     cmd=%proc.cmdline                      # the full command line
     pid=%proc.pid                          # process ID
     ns=%k8s.ns.name                        # Kubernetes namespace
     pod=%k8s.pod.name)                     # Kubernetes pod name
  priority: Notice                           # severity: Emergency, Critical, Error, Warning, Notice, Informational, Debug
  tags: [shell, container, mitre_execution]  # tags for filtering and MITRE ATT&CK mapping

The Default Falco Ruleset

Falco ships with a comprehensive default ruleset that covers the most common attack behaviors:

  1. Terminal shell in container: an interactive shell (sh, bash, zsh) was spawned inside a container
  2. Write below root: a process wrote to the root filesystem of a container (should be read-only in hardened deployments)
  3. Sensitive file opened for reading: /etc/shadow, /etc/sudoers, /root/.ssh/authorized_keys were opened
  4. Unexpected network connection from container: a container established a network connection to an unexpected destination
  5. Binary executed in container: a new binary (not in the original image) was executed
  6. Privilege escalation: setuid or setgid was called, or a container gained new capabilities
  7. Contact with K8s API from container: a container directly contacted the Kubernetes API server

Writing a Custom Falco Rule

The file below defines two custom Falco rules: one for download tools running inside a container, one for reads of credential files. Save it as custom-rules.yaml:

# custom-rules.yaml (loaded into Falco via ConfigMap or Helm values)
- rule: Curl or Wget Executed in Container
  desc: >-
    curl or wget was executed inside a container.
    This may indicate data exfiltration, reverse shell download, or C2 communication.
  condition: >-
    spawned_process                    # a new process was created
    and container                      # it is inside a container
    and proc.name in (curl, wget)      # the process is curl or wget
  output: >-
    Download tool executed in container
    (user=%user.name
     cmd=%proc.cmdline
     container=%container.name
     image=%container.image.repository
     pod=%k8s.pod.name
     ns=%k8s.ns.name)
  priority: Warning                    # higher priority than Notice because this is more suspicious
  tags: [network, container, download, mitre_exfiltration]

- rule: Database Credentials File Read
  desc: >-
    A process read a file that commonly stores database credentials.
    Legitimate application startups do this once; subsequent reads may indicate credential theft.
  condition: >-
    open_read                          # macro: file was opened for reading
    and container                      # inside a container
    and (fd.name = "/app/config/database.yaml"
         or fd.name = "/app/.env"
         or fd.name endswith ".pem"   # private key files
         or fd.name endswith ".key")
    and not proc.name in (sh, bash)    # application processes, not shell scripts
  output: >-
    Credential file accessed
    (user=%user.name
     file=%fd.name
     proc=%proc.cmdline
     container=%container.name)
  priority: Critical
  tags: [credentials, container, mitre_credential_access]

Falco versus Complementary Controls

Falco is not the only control that operates at syscall time, and it is the only one of the three that does not block. The table below shows where each control sits.

Control When it operates What it prevents or detects
seccomp profiles At syscall time: blocks the syscall before it executes Prevents specific syscalls from being made at all
AppArmor profiles At syscall time: blocks based on file path and capabilities Restricts file access patterns and capability usage
Falco At syscall time: observes and alerts, does not block Detects suspicious patterns across any syscall
Falco detects but does not block. It is a detection and alerting tool, not a prevention tool. Use it alongside seccomp (which can block specific syscalls), AppArmor (which can restrict file access), and NetworkPolicies (which block network connections). Together they form multiple complementary layers.
