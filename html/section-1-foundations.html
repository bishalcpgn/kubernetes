1. Kubernetes Theory and Architecture

This section builds the mental model you need to work effectively with Kubernetes. Rather than jumping straight into commands, we start from the problem that Kubernetes solves and work upward through the architecture. Understanding why each component exists makes every kubectl command feel logical rather than magical.

1.1 The Journey: From Bare Metal to Kubernetes

Era 1: Bare Metal Servers

In the earliest era you deployed software directly onto physical servers, and the machine's limits were your application's limits. If your application needed more RAM than the server had, it crashed. If a neighbouring application on the same server leaked memory, yours suffered for it. The only way to isolate two applications was to buy a second server, which took weeks to arrive and then sat at 10-20% utilization for the rest of its life.

Era 2: Virtual Machines

Hypervisors such as VMware, Xen, and KVM solved the isolation problem by letting several virtual computers share one physical host. Each virtual machine got its own operating system, its own kernel, and its own network stack, so you could now run five isolated applications on a single server. Utilization improved, provisioning fell from weeks to minutes, and for the first time you could snapshot a workload and migrate it somewhere else.

But a virtual machine is a heavy thing to move around. Each one carries a full operating system kernel, which costs 512 MB to 2 GB of memory before your application starts, takes 30-60 seconds to boot, and ships as a multi-gigabyte image.

Era 3: Containers

A container is built from two Linux kernel features working together. Namespaces provide the isolation: each container sees only its own process tree, its own network interfaces, and its own filesystem mount points. Cgroups provide the resource limits: a ceiling on how much CPU and memory the container may consume. The decisive difference from a virtual machine is that containers share the host's kernel rather than shipping one of their own, and that single change cascades:

  1. A container image might be 50-200 MB instead of 2 GB.
  2. Starting a container takes milliseconds, not seconds.
  3. You can run hundreds of containers on a single VM that could only host a handful of VMs.
  4. Images are portable: build once on your laptop, run identically in any environment that has a container runtime.

Docker popularized containers from 2013 onward. Developers loved them because "it works on my machine" became "it works everywhere the Docker image runs".

Era 4: Why Containers Alone Are Not Enough in Production

Running a container on your laptop is easy. Running hundreds of containers across dozens of machines in production reveals problems that the container runtime itself does not solve:

  1. No self-healing: when a container crashes, docker run does not bring it back. You have to write monitoring and restart scripts yourself, and in practice those scripts are brittle and become a maintenance burden of their own.
  2. No automated scaling: when traffic grows tenfold, you launch more containers by hand. Doing it automatically needs something that watches metrics, decides when to scale, and starts or stops containers on its own.
  3. No scheduling intelligence: given 50 machines and 200 containers to place, which container goes where? Answering that needs something that tracks the free CPU and memory on every machine and places each container where it fits.
  4. No zero-downtime updates: to move to a new version you stop the old container and start the new one, and requests fail in the gap between the two. Rolling out gradually instead requires an orchestrator.
  5. No service discovery: a container gets a different IP address every time it starts, so nothing else can hold a stable address for it. You need a layer that provides steady names no matter which containers happen to be running.
  6. No secret management: getting passwords and API keys into a container without baking them into the image requires infrastructure that Docker alone does not provide.
Kubernetes is the answer to all of these problems

Kubernetes was created at Google, based on their internal system called Borg that managed Google's global compute infrastructure. Google open-sourced Kubernetes in 2014 and donated it to the Cloud Native Computing Foundation (CNCF). It solves every production operations problem listed above with a single, coherent system built on one central idea: desired state reconciliation.

1.2 The Master Concept: Desired State vs. Actual State

The most important idea in all of Kubernetes is the distinction between desired state and actual state, and the reconciliation loop that bridges the gap between them.

Desired State

Desired state is what you want the cluster to look like. You express it declaratively in YAML: "I want 3 replicas of my nginx container, each with 100m CPU and 128Mi memory, exposed on port 80." You write this down and give it to Kubernetes. You do not tell Kubernetes how to achieve it. You just describe the goal.

Actual State

Actual state is what is currently running in the cluster right now. Maybe you asked for 3 replicas, but a node just failed and one replica was lost. The actual state is 2 running replicas. Or maybe you asked for 3 replicas and the cluster has not even started spinning them up yet: the actual state is 0 running replicas.

The Reconciliation Loop

Kubernetes runs continuous loops called controllers that watch both the desired state (stored in etcd) and the actual state (what the kubelet reports), compute the difference, and take actions to close the gap. This is called the reconciliation loop.

This loop runs continuously, typically every few seconds. It is why Kubernetes is called "self-healing": it automatically detects that a pod died and creates a replacement without any human intervention.

This is fundamentally different from scripts

A traditional deployment script runs once and exits. If something goes wrong after the script finishes, nothing fixes it. The Kubernetes reconciliation loop runs forever. It does not matter when the failure happens: at 3am, during a network partition, or during a node hardware failure. Kubernetes will detect and respond to it.

1.3 Full Kubernetes Architecture Deep Dive

A Kubernetes cluster consists of two kinds of machines: control-plane nodes (which manage the cluster) and worker nodes (which run your applications). Here is the complete picture:

1.4 Control Plane Components: Deep Dive

kube-apiserver: The Single Source of Truth

The API server is the central hub of all Kubernetes communication. Every component in the cluster, whether it is the scheduler, the controller manager, the kubelet on a node, or your kubectl client, communicates exclusively through the API server. No component ever talks directly to etcd or directly to another component.

Why this design? It provides a single point for:

  1. Authentication: every request must prove who it is. The API server validates client certificates, bearer tokens, and other credential types, and it rejects anonymous requests unless you have explicitly configured otherwise.
  2. Authorization: once the API server knows who is asking, it checks whether that identity is allowed to perform the action. That check is RBAC (Role-Based Access Control), which Lab 13 covers in full.
  3. Admission control: even an authenticated, authorized request then passes through a chain of admission controllers, each of which may modify it or reject it outright. The PodSecurity controller enforces security profiles on Pods, and LimitRanger fills in default resource limits.
  4. Validation: the submitted YAML or JSON is checked for well-formedness and against the API schema, so a typo in a field name is rejected before any cluster state changes.
  5. Serialization and storage: accepted objects are serialized into etcd's key-value format and written there. The API server also watches etcd for changes and pushes them to every component that has registered a watch, which is how the rest of the cluster learns that anything happened.
The API server is stateless

The API server itself does not store any data. All state lives in etcd. This means you can run multiple API server replicas behind a load balancer for high availability, and they all share the same state because they all read from and write to the same etcd cluster.

etcd: The Cluster's Brain (Persistent Memory)

etcd is a distributed key-value store that holds the entire state of a Kubernetes cluster. When you create a Deployment, the YAML you submitted gets stored in etcd. When a pod is scheduled to a node, that assignment is stored in etcd. When a node reports itself as unhealthy, that status is stored in etcd.

etcd uses the Raft consensus algorithm to ensure that data is consistent even when some nodes fail. In a production cluster you run etcd with an odd number of members (3, 5, or 7). Raft requires a majority (quorum) of members to be available to accept a write. With 3 members, etcd can tolerate 1 failure. With 5 members, it can tolerate 2 failures.

Backup etcd in production

etcd is the single source of truth for everything in your cluster. If etcd is lost and you have no backup, your entire cluster configuration is gone: all Deployments, Services, Secrets, RBAC rules, everything. In production, etcd must be backed up regularly (typically to an object store like S3). In Minikube, this is not a concern because it is a development cluster.

In Minikube, etcd runs as a static pod (a pod defined by a file in /etc/kubernetes/manifests/ rather than through the API server) inside the Minikube container. You can see it:

iFind the etcd Pod in kube-system
kubectl get pod -n kube-system -l component=etcd
# Output: etcd-minikube   1/1   Running   ...
iiInspect the etcd Pod's configuration
kubectl describe pod etcd-minikube -n kube-system

kube-scheduler: Placing Pods on Nodes

The scheduler watches for Pods that have no node yet and picks one for each. That is its whole job. It does not start anything; it writes a node name onto the Pod, and the kubelet on that node takes over from there.

How the scheduler picks a node: filtering and scoringOptional depth

The scheduler's job is to watch the API server for pods that have been created but not yet assigned to a node (their spec.nodeName field is empty), and to decide which node each pod should run on.

The scheduling decision is a two-phase process:

Phase 1: Filtering (find feasible nodes)

The scheduler applies a series of filter predicates to eliminate nodes that cannot run the pod:

  1. Resource fit: the node is eliminated unless its allocatable CPU and memory can satisfy the pod's requests.
  2. Node selector: if the pod sets a nodeSelector, the node must carry every label it names. This is an exact match, and there is no way to soften it.
  3. Node affinity: if the pod sets affinity rules instead, the node must satisfy those. They are more expressive than nodeSelector, and section 2.5 covers the difference.
  4. Taints and tolerations: a taint on the node repels pods, so the node is eliminated unless the pod carries a matching toleration.
  5. Volume constraints: if the pod needs a persistent volume, a compatible volume has to be reachable from this node's zone.
  6. Pod anti-affinity: the node is eliminated if the pod has declared that it must not sit beside a pod that is already running there.

Phase 2: Scoring (rank the feasible nodes)

Among the nodes that passed the filters, the scheduler assigns a score to each one based on priority functions. Examples include: prefer the node with the most available CPU (spreads load), prefer the node that already has the required container image cached (reduces pull time), prefer nodes in the same topology zone as other replicas. The highest-scoring node wins and the pod is assigned to it.

Taints and Tolerations: a common source of confusion

A taint on a node is like a "no unauthorized pods" sign. By default, the scheduler will not place any pod on a tainted node. A toleration on a pod is like an authorization badge: "I am allowed on tainted nodes with this specific taint." Control-plane nodes in production clusters are typically tainted to prevent application workloads from being scheduled there.

kube-controller-manager: The Reconciliation Engine

The controller manager is a single binary that runs dozens of independent control loops side by side. Each loop watches one kind of object and works continuously to make reality match the spec you declared: the Deployment controller creates ReplicaSets, the ReplicaSet controller creates Pods, and the Node controller reacts when a node stops answering. Every one of them follows the same observe, compare, act pattern from 1.2. Section 1.9 defines the Deployment, ReplicaSet, and Pod objects themselves; what matters here is that each one has a controller whose entire job is keeping it true.

Inside the controller manager: what each controller doesOptional depth

The controller manager is a single binary that bundles dozens of individual controllers. Each controller is a goroutine (a lightweight Go thread) that watches the API server for changes to certain resources and takes action to reconcile desired state with actual state. Here are the most important controllers:

  1. Deployment controller. Turns a Deployment into a ReplicaSet matching its pod template and replica count.
  2. ReplicaSet controller: keeps the pod count exact. If a pod is deleted or crashes it creates a replacement, and if there are too many it deletes the surplus.
  3. Node controller: marks a node NotReady when its heartbeats stop, which usually means the kubelet there has died. After a timeout it evicts every pod from that node so the ReplicaSet controller can reschedule them elsewhere.
  4. Endpoints controller: maintains the Endpoints object for each Service, which is the list of pod IP addresses currently matching that Service's label selector. kube-proxy reads those Endpoints to program its routing rules.
  5. Job controller: creates the pods needed to run a batch task to completion, retrying failed pods up to a configured limit.
  6. ServiceAccount controller: creates the default ServiceAccount in every new namespace, along with the API token that goes with it. That token is what a pod presents to the API server, and Lab 13 builds on it.
  7. Namespace controller: garbage-collects every resource inside a namespace when the namespace is deleted.

1.5 Worker Node Components: Deep Dive

kubelet: The Node Agent

The kubelet is a process that runs on every worker node. It is the only Kubernetes component that runs directly on the host machine rather than inside a container. Its job is to make sure the containers described in the pods assigned to its node are running and healthy.

Here is how the kubelet operates:

  1. Watching for assigned pods: the kubelet establishes a persistent watch connection to the API server. Whenever a new pod is assigned to its node (i.e., spec.nodeName is set to this node's name), the API server notifies the kubelet immediately.
  2. Pulling images: the kubelet asks the container runtime (containerd) to pull the required container images if they are not already cached locally.
  3. Starting containers: the kubelet calls the container runtime via the Container Runtime Interface (CRI), a gRPC API, to create and start the containers specified in the pod's spec.
  4. Mounting volumes: the kubelet mounts the pod's volumes (ConfigMaps, Secrets, PersistentVolumes) into the container's filesystem before starting it.
  5. Liveness and readiness probes: the kubelet periodically executes the pod's health probes. If a liveness probe fails, the kubelet restarts the container. If a readiness probe fails, the kubelet removes the pod from the Endpoints list, the set of pod IPs a Service is currently willing to send traffic to, so the pod stops receiving requests.
  6. Reporting status: the kubelet periodically sends status updates about the node and its pods back to the API server, including CPU/memory usage, pod phases (Pending, Running, Succeeded, Failed), and container states.
Static Pods: how control-plane components start

On control-plane nodes, the core components (etcd, kube-apiserver, kube-scheduler, kube-controller-manager) run as "static pods". These are pod manifests stored in /etc/kubernetes/manifests/ on the node's filesystem. The kubelet reads these files directly, without going through the API server, and starts the pods. This is how Kubernetes bootstraps itself: the kubelet starts the API server, and then the API server becomes available for everything else.

kube-proxy: Programming the Network

kube-proxy runs on every node and is responsible for implementing Services. When you create a Service, it gets a virtual IP address (called the ClusterIP). Traffic sent to that virtual IP needs to be redirected to the actual pod IP addresses that currently back the Service. kube-proxy does this by programming the Linux kernel's packet filtering rules.

kube-proxy supports three modes:

  1. iptables mode (default on most clusters): kube-proxy writes iptables rules that use DNAT (Destination Network Address Translation) to redirect traffic destined for a Service's ClusterIP to one of the backend pod IPs, chosen randomly. This is efficient for small clusters but can have performance issues with thousands of Services.
  2. IPVS mode: kube-proxy uses the Linux kernel's IPVS (IP Virtual Server) module, which is designed for high-performance load balancing. It supports multiple load-balancing algorithms (round-robin, least connections, etc.) and scales better to large numbers of Services.
  3. nftables mode (newer): uses the nftables framework, which is the successor to iptables in the Linux kernel. More efficient rule management.

Container Runtime: containerd and CRI-O

The container runtime is the software that actually creates and runs containers. Kubernetes does not interact with Docker directly. Instead, it uses a standardized interface called the Container Runtime Interface (CRI), a gRPC API. Any container runtime that implements CRI can work with Kubernetes.

The two main runtimes are:

  1. containerd: the most widely used runtime, originally developed as part of Docker and then donated to the CNCF. It is lightweight and focuses purely on running containers. Most Kubernetes distributions, including Minikube, use containerd by default.
  2. CRI-O: developed by Red Hat specifically for Kubernetes. Minimal footprint, closely tracks Kubernetes release cycles. Used by OpenShift and many enterprise distributions.

1.7 The Kubernetes API: Resources, Groups, and Versions

When you write apiVersion: apps/v1 at the top of a Deployment YAML, you are specifying the API group and version. Understanding this structure helps you read documentation and understand error messages.

API Groups

Kubernetes organizes its API into groups. The core group (for foundational resources like Pods, Services, Namespaces, ConfigMaps) has no group name. Its apiVersion is just a version number like v1. All other groups have names. Each resource also carries a stability level in its version string, which tells you how much the field layout can still change under you. There are three levels. What each stability level actually promisesOptional depth

Kubernetes uses semantic versioning suffixes to indicate the maturity and stability of an API:

  1. v1alpha1, v1alpha2, etc.: experimental features. The API may change or be removed between Kubernetes versions. Do not use in production.
  2. v1beta1, v1beta2, etc.: feature is mostly stable but the API may still have breaking changes. Generally safe for non-critical production use, but plan for migration.
  3. v1, v2, etc.: stable, committed API. Will not have breaking changes within the same major Kubernetes version. Safe for all production use.

1.8 The Declarative Model: Why YAML + apply Beats Imperative Commands

There are two ways to work with Kubernetes: imperative and declarative. Understanding the difference is essential for production operations.

Imperative Approach

In the imperative approach, you tell Kubernetes exactly what action to take right now: 

kubectl run nginx --image=nginx:alpine
kubectl scale deployment nginx --replicas=3
kubectl set image deployment/nginx nginx=nginx:1.25
kubectl expose deployment nginx --port=80 --type=NodePort

Problems with imperative commands in production:

  1. The intent lives only in your shell history. There is no persistent record of what you did or why.
  2. Another person (or an automated system) looking at the cluster cannot know what commands were run to create it.
  3. If you need to recreate the cluster (disaster recovery), you must remember and re-execute every command in the right order.
  4. Drift happens: if someone runs a different command on the cluster and you do not know about it, your mental model is wrong.

Declarative Approach

In the declarative approach, you write a YAML file describing the desired end state and tell Kubernetes to make it so. Save it as deployment.yaml: 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
  namespace: default
spec:
  replicas: 3                      # desired number of pods
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:alpine        # desired container image
        ports:
        - containerPort: 80

kubectl apply -f deployment.yaml

If you run kubectl apply again with a modified YAML (e.g., you changed replicas: 3 to replicas: 5), Kubernetes computes the diff and applies only the change. If you run it with the same YAML unchanged, nothing happens. This is called idempotency: applying the same desired state multiple times has the same result as applying it once.

The production rule: always use declarative apply

Store your YAML files in a Git repository. Every change to your cluster goes through a Git commit and a kubectl apply. This gives you: a full audit history of every change, the ability to roll back by reverting a commit, peer review via pull requests, and a complete disaster-recovery playbook (re-apply all the YAML files). This approach is the foundation of GitOps, which you will explore in Lab 10.

1.9 Core Kubernetes Objects: Beginner-Friendly Explanations

Pod

A Pod is the smallest unit of deployment in Kubernetes. It is a wrapper around one or more containers that share:

  1. A single network namespace (one IP address for the whole pod)
  2. The same volumes (filesystem mounts)
  3. The same lifecycle (they start and stop together)

Most of the time, a Pod contains exactly one container. Multi-container pods are used for the "sidecar" pattern, where a helper container (logging agent, proxy, config reloader) runs alongside the main application container.

You rarely create Pods directly

Pods are ephemeral. If a Pod dies, nothing recreates it automatically. In practice, you almost always use a Deployment (which creates and manages pods via a ReplicaSet) rather than creating Pods directly. The exception is one-off debugging tasks: kubectl run debug --image=busybox --restart=Never -- sleep 3600

ReplicaSet

A ReplicaSet ensures that a specified number of pod replicas are running at any given time. If a pod crashes, the ReplicaSet creates a replacement. If a node fails and takes pods with it, the ReplicaSet creates replacements on other nodes. You define the desired replica count and a pod template, and the ReplicaSet controller maintains that count.

You almost never create ReplicaSets directly either. Deployments create and manage ReplicaSets for you, adding the ability to do rolling updates and rollbacks.

Deployment

A Deployment is what you use to run stateless applications in production. It manages a ReplicaSet and adds:

  1. Rolling updates: when you change the pod template (e.g., update the container image), the Deployment creates a new ReplicaSet with the new template and gradually shifts traffic from the old pods to the new ones, one batch at a time. During the update, some old pods and some new pods are running simultaneously.
  2. Rollback: if the new version is broken, you can roll back to the previous version with a single command: kubectl rollout undo deployment/my-app
  3. Revision history: Kubernetes keeps the old ReplicaSets around (up to revisionHistoryLimit, default 10) so rollback is always available.

Service

Pods are ephemeral: they come and go, and each time a pod starts it gets a new IP address. If Service A needs to talk to Service B, it cannot hardcode the IP address of Service B's pods. A Service solves this by providing a stable virtual IP address (the ClusterIP) and a stable DNS name that always routes to the currently healthy pods matching a label selector.

The Service below finds its backends by the label app: my-app rather than by pod IP:

apiVersion: v1
kind: Service
metadata:
  name: my-app           # DNS name: my-app.default.svc.cluster.local
spec:
  selector:
    app: my-app          # routes to pods with this label
  ports:
  - port: 80             # the port the Service listens on
    targetPort: 8080     # the port on the pod to forward to
  type: ClusterIP        # internal-only (the default)

Namespace

A Namespace is a virtual partition within a cluster. Resources in different namespaces are isolated from each other by default. You can have a "dev" namespace and a "prod" namespace on the same cluster, with different teams and different permissions for each. Most Kubernetes resources (Pods, Services, Deployments) are namespace-scoped. A few resources (Nodes, PersistentVolumes, ClusterRoles) are cluster-scoped and have no namespace.

ConfigMap

A ConfigMap stores non-sensitive configuration data (environment variables, config files, command-line flags) as key-value pairs in the cluster. Pods can consume ConfigMaps as environment variables or as files mounted into the container's filesystem. The key benefit: you do not have to bake configuration into your container image. The same image can run in dev, staging, and prod by using different ConfigMaps.

Secret

A Secret is like a ConfigMap but intended for sensitive data: passwords, API keys, TLS certificates, and tokens. Secrets are base64-encoded (not encrypted by default, but encryption-at-rest can be configured). Access to Secrets is controlled by RBAC. Pods can consume Secrets as environment variables or as volume-mounted files.

Base64 is encoding, not encryption

A common beginner mistake is thinking Kubernetes Secrets are secure by default. Base64 encoding is trivially reversible. Anyone with read access to the Secret object can recover the plaintext with echo "dGVzdA==" | base64 -d. For real security, enable etcd encryption at rest, use strict RBAC to control who can read Secrets, or use an external secrets manager like HashiCorp Vault. Lab 6 covers Secret management in depth.

PersistentVolume and PersistentVolumeClaim

Containers are ephemeral: when a container is deleted, any data written to its filesystem is lost. For workloads that need durable storage (databases, file servers), Kubernetes provides a storage abstraction:

  1. PersistentVolume (PV): a piece of storage that has been provisioned in the cluster. It might be an NFS share, an AWS EBS volume, a GCP Persistent Disk, or a local directory. PVs are cluster-scoped resources (they do not belong to a namespace).
  2. PersistentVolumeClaim (PVC): a request for storage by a user or pod. A PVC says "I need 10 GB of storage with ReadWriteOnce access mode." Kubernetes finds a matching PV and binds them together. The pod mounts the PVC, not the PV directly. This separation lets cluster admins manage storage pools without exposing implementation details to application developers.

1.10 Service Types: When to Use Each

Kubernetes Services come in four types. The type determines how the Service is exposed to the outside world.

ClusterIP (the default)

A ClusterIP Service gets a virtual IP address that is only reachable from within the cluster. No traffic from outside the cluster can reach a ClusterIP Service directly.

Use when: your service only needs to be reached by other pods in the cluster. The vast majority of services in a microservices architecture are ClusterIP services. For example: a database, a cache, a backend API that the frontend calls.

NodePort

A NodePort Service exposes the Service on a static port (between 30000 and 32767) on every node's external IP address. External traffic hitting <any-node-IP>:<nodePort> is routed to the Service's backend pods.

Use when: you need external access and do not have a cloud load balancer. Useful for development, demos, and on-premises clusters. Not ideal for production because you expose a non-standard port and must manage the node IP yourself.

minikube service my-app --url

# On Minikube, this is how you reach a NodePort Service.
# It prints the URL including the correct node IP and nodePort.

LoadBalancer

A LoadBalancer Service provisions an external load balancer from the cloud provider (AWS ELB, GCP Load Balancer, Azure LB). The cloud load balancer gets a public IP and routes traffic to the NodePorts on your cluster's nodes.

Use when: you are running on a cloud provider and need to expose a service to the internet with a stable public IP. This is the standard way to expose production services in cloud-hosted clusters.

On Minikube: LoadBalancer services stay in "pending" external IP state because there is no cloud provider. Use minikube tunnel in a separate terminal to emulate a load balancer.

ExternalName

An ExternalName Service maps a Kubernetes Service name to an external DNS name. It does not create any proxy or ClusterIP. Instead, when a pod looks up the Service's DNS name, it gets back a CNAME record pointing to the external hostname.

Use when: you have an external service (a managed database, a third-party API) that you want to reference by a Kubernetes-style DNS name from within the cluster, so you can easily swap it out later without changing application code.

The Service below resolves the in-cluster name my-database to an external hostname instead of to any Pod:

apiVersion: v1
kind: Service
metadata:
  name: my-database
spec:
  type: ExternalName
  externalName: mydb.example.com  # DNS resolution returns CNAME to this

How Services Get DNS Names

A ClusterIP is a number, and nothing should hardcode a number. Every Service also gets a DNS name from CoreDNS, the cluster's built-in DNS server running in kube-system. The full form is:

<service-name>.<namespace>.svc.cluster.local
        |             |         |
        |             |         +-- cluster domain (fixed)
        |             +------------ namespace the Service lives in
        +-------------------------- the Service's metadata.name

You rarely type the whole thing. A Pod's resolver is configured with search domains, so from inside a Pod in the same namespace, nginx-service alone resolves. From a different namespace you need nginx-service.other-namespace. This is the single most common cause of "connection refused" between two working services: the name resolved in the wrong namespace, or did not resolve at all.

iResolve a Service name from inside the cluster

  nslookup kubernetes.default.svc.cluster.local
# Output: an Address line pointing at the ClusterIP of the kubernetes Service.
# If this fails, CoreDNS itself is unhealthy, not your application.
iiConfirm CoreDNS is running when resolution fails
kubectl get pods -n kube-system -l k8s-app=kube-dns

One variation is worth naming now, because Lab 6 uses it without ceremony. Setting clusterIP: None on a Service makes it headless: it gets no virtual IP and does no load balancing, and its DNS name resolves directly to the IP of every matching Pod instead of to a single front door.

Why StatefulSets need a headless ServiceOptional depth

Resolving to every Pod is the behavior a StatefulSet needs. With a headless Service, each Pod also gets its own stable name of the form <pod-name>.<service-name>.<namespace>.svc.cluster.local, so web-0 and web-1 are individually addressable. A database replica has to know which peer it is talking to, and a load-balanced ClusterIP would make that impossible. Lab 6 uses this.

Key Takeaways

  2. Every component reaches the cluster through the API server.   3. Controllers reconcile continuously rather than running once. A controller compares the desired state stored in etcd against the actual state the kubelet reports and closes the gap on every pass, which is the whole reason a deleted Pod comes back without anyone asking.
  4. etcd holds all cluster state and the API server holds none. That split is why you can run several API server replicas behind one load balancer, and why etcd is the component you size for quorum (3, 5, or 7 members) and back up.
  5. One kubectl apply travels the whole architecture. Your call reaches the API server, the API server writes the object to etcd, the controller-manager creates the ReplicaSet and its Pods, the scheduler assigns each Pod a node, and kubelet asks containerd to start the container you later listed with crictl.

2. Core Working Concepts

This section covers the foundational concepts you will use every single day when working with Kubernetes. Understanding these deeply will save you hours of debugging and confusion. We will start with how Kubernetes organizes resources, then move into how you tell Kubernetes what you want, how it allocates compute resources, and finally how it finds and groups things together.

2.1 Namespaces

Imagine you have a single large office building. Different companies rent different floors. Each floor has its own locked door, its own reception desk, and its own rules about who can enter. People on one floor generally cannot walk into another floor without permission. Yet they all share the same building infrastructure: the elevators, the parking lot, the power grid.

Kubernetes namespaces work exactly like this. A namespace is a virtual cluster inside your real cluster. All the physical nodes, the network fabric, and the control plane are shared. But inside the namespace, you get a private, isolated space where your Pods, Services, Deployments, and other resources live. The API server enforces these boundaries.

What a Namespace Actually Is A namespace is not a separate machine, not a separate network, and not a container. It is a label that the Kubernetes API server uses to scope every API request. When you ask for "all pods in namespace team-alpha", the API server filters its internal database to return only objects whose metadata includes namespace: team-alpha. It is a logical boundary enforced in software.

The Four Default Namespaces

When you install a fresh Kubernetes cluster, four namespaces are created automatically. Each one has a specific purpose, and understanding them will prevent a lot of confusion.

kubectl get namespaces
  1. default: This is where your resources go when you do not specify a namespace. If you run kubectl apply -f my-app.yaml and your YAML does not include a namespace field, Kubernetes places everything in default. For learning and small personal projects this is fine. For anything with more than one team or application, relying on default becomes messy very quickly because everything piles up together with no separation.
  2. kube-system: This is where Kubernetes runs its own internal components. The DNS server (CoreDNS), the network plugin, the metrics server, and the Kubernetes dashboard all live here. You will look at this namespace to debug cluster-level problems, but you should almost never deploy your own applications here. Touching things in kube-system without knowing exactly what you are doing can destabilize your entire cluster. 
    kubectl get pods -n kube-system
  3. kube-public: This namespace is readable by all users, even unauthenticated ones. It holds cluster information that should be publicly accessible. In practice, the only notable thing here is a ConfigMap called cluster-info that contains the cluster's API server endpoint and certificate authority data. For most day-to-day work, you will never touch this namespace.
  4. kube-node-lease: This namespace exists for performance reasons. Each node in the cluster has a Lease object here. The kubelet on each node updates its Lease object on a regular heartbeat (every few seconds). The control plane watches these Leases instead of watching full Node objects, which dramatically reduces the load on the API server in large clusters.

Why Namespaces Matter in Real Organizations

Namespaces serve four major purposes that become critical as your cluster grows.

  1. RBAC Boundaries: Kubernetes roles and role bindings are namespace-scoped by default. This means you can give a developer on Team Alpha full read/write access to the team-alpha namespace while giving them zero access to the team-beta namespace. The Role below grants that access inside team-alpha and nowhere else: 
    apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: team-alpha   # This role cannot affect any other namespace
  name: developer-role
rules:
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: [""]
  resources: ["pods", "services", "configmaps"]
  verbs: ["get", "list", "watch"]
  2. Resource Quotas: You can cap how much CPU, memory, and how many objects a namespace can consume. This prevents a single team from accidentally exhausting all cluster resources and starving other teams.
  3. Network Isolation: By default, all Pods in a cluster can talk to all other Pods, even across namespaces. But when you use NetworkPolicy objects (covered in Lab 14), you can enforce rules like "Pods in namespace team-alpha can only talk to Pods in namespace shared-services".
  4. Organizational Clarity: Even without strict security requirements, namespaces let you run kubectl get pods -n payments and see only payment-related Pods, rather than scrolling through hundreds of Pods from every team.
Namespaces Do NOT Provide Network Isolation by Default A common misconception is that putting services in different namespaces automatically isolates their network traffic. It does not. A Pod in namespace team-alpha can still call a Service in namespace team-beta using the full DNS name: service-name.team-beta.svc.cluster.local. You need explicit NetworkPolicy objects to restrict cross-namespace traffic.

When NOT to Use Namespaces

Namespaces add operational overhead. You always have to remember to add -n my-namespace to every kubectl command. RBAC becomes more complex. For small teams early in development, this overhead can slow you down with little benefit.

Consider staying in the default namespace when: you are a single developer learning Kubernetes, your team has two or three people and one application, or you are running a short-lived proof-of-concept cluster.

Move to multiple namespaces when: multiple teams share a single cluster, you run multiple environments (staging, production) on the same cluster, you have compliance or security requirements for resource isolation, or you want different resource quotas for different teams.

ResourceQuota: Capping Resource Usage Per Namespace

A ResourceQuota is a Kubernetes object that sets hard upper limits on the total resources a namespace can consume. Once a quota is applied, the API server tracks running totals across all Pods, Services, and other objects in that namespace. Any request that would push the total over a quota limit is rejected immediately.

ResourceQuota solves a critical multi-tenant problem: without it, one team can accidentally (or intentionally) consume all cluster CPU and memory, starving every other team. Quotas give platform teams a governance mechanism: "Team Alpha gets exactly 4 CPU cores and 8 GiB of RAM. No more."

There are two categories of things you can quota:

  1. Compute resources: requests.cpu, requests.memory, limits.cpu, limits.memory. These are summed across all containers in all Pods in the namespace.
  2. Object counts: pods, services, persistentvolumeclaims, secrets, configmaps, replicationcontrollers, and others. These limit how many of each object type can exist simultaneously in the namespace.

Let's walk through a complete ResourceQuota lab. Save the following manifest as team-alpha-quota.yaml. It sets both compute and object-count limits for the team-alpha namespace.

The following YAML defines a ResourceQuota with compute resource caps and object count limits:

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-alpha-quota
  namespace: team-alpha    # Quotas are always namespace-scoped
spec:
  hard:
    # --- Compute resource limits ---
    # These are AGGREGATE limits across ALL Pods in the namespace.
    # "requests.cpu: 4" means the SUM of all Pod CPU requests cannot exceed 4 cores.
    requests.cpu: "4"          # Total CPU requested across all Pods: max 4 cores
    requests.memory: 8Gi       # Total memory requested across all Pods: max 8 GiB
    limits.cpu: "8"            # Total CPU limits across all Pods: max 8 cores
    limits.memory: 16Gi        # Total memory limits across all Pods: max 16 GiB

    # --- Object count limits ---
    # These prevent runaway creation of resources that consume cluster-level capacity.
    pods: "50"                 # At most 50 Pods can exist in this namespace at once
    services: "10"             # At most 10 Services
    persistentvolumeclaims: "20"  # At most 20 PVCs (each PVC consumes storage)
    secrets: "50"              # At most 50 Secrets
    configmaps: "50"           # At most 50 ConfigMaps

Apply the quota, verify current usage, and observe what happens when you exceed it:

iApply the ResourceQuota to the cluster
kubectl apply -f team-alpha-quota.yaml
iiCheck current usage against the quota at any time
kubectl describe resourcequota team-alpha-quota -n team-alpha
iiiSee what happens when you exceed the quota
kubectl apply -f big-deployment.yaml

# The API server rejects the request because it would exceed the quota.
ResourceQuota Forces All Pods to Declare Resources Once you apply a ResourceQuota that includes requests.cpu or requests.memory, every single Pod in that namespace MUST declare both requests and limits in its container spec. Any Pod that omits them will be rejected by the API server with a "must specify requests" error. This can break existing workloads that were deployed without resource declarations. The solution is to apply a LimitRange first (described below) to set automatic defaults, so Pods that omit resource declarations still get sensible values injected automatically.
Quota Scopes ResourceQuota can also be scoped to apply only to certain Pods. For example, you can set a quota that applies only to BestEffort Pods (those with no requests or limits), or only to Terminating Pods (those with an activeDeadlineSeconds set). This is an advanced feature but useful when you want separate budgets for different quality-of-service tiers within the same namespace.

LimitRange: Setting Defaults and Maximums Per Container

A LimitRange operates at the container level, not the namespace level. While ResourceQuota controls the aggregate total across the whole namespace, LimitRange sets boundaries and defaults for individual containers and PersistentVolumeClaims. It solves two distinct problems:

  1. Missing resource declarations. Developers forget to set requests and limits on their containers. When you also have a ResourceQuota active, those Pods get rejected. A LimitRange automatically injects default requests and limits into any container that omits them, so developers do not have to specify them explicitly unless they need non-default values.
  2. Runaway resource claims. Without a maximum, a developer could request 100 CPU cores for a single container, starving the whole cluster. LimitRange lets you set a ceiling per container so no single workload can claim unreasonable resources.

LimitRange supports three types of targets, each with its own set of fields:

  1. Container: applies to every container in every Pod in the namespace, including init containers, the short-lived containers that run to completion before the main ones start.
  2. Pod: applies to the sum of all containers within a single Pod.
  3. PersistentVolumeClaim: applies to storage requests in PVCs.

Let's walk through a complete LimitRange lab. Save the following manifest as team-alpha-limits.yaml.

The following YAML defines a LimitRange with defaults, hard boundaries, and PVC storage limits:

apiVersion: v1
kind: LimitRange
metadata:
  name: team-alpha-limits
  namespace: team-alpha      # LimitRanges are namespace-scoped
spec:
  limits:
  - type: Container           # These rules apply to every container individually
    # Defaults injected when the container spec omits these fields
    default:
      cpu: 500m               # If a container declares no CPU limit, it gets 500m
      memory: 256Mi           # If a container declares no memory limit, it gets 256Mi
    defaultRequest:
      cpu: 100m               # If a container declares no CPU request, it gets 100m
      memory: 128Mi           # If a container declares no memory request, it gets 128Mi

    # Hard boundaries: API server rejects containers outside these
    max:
      cpu: "2"                # No single container can request more than 2 CPU cores
      memory: 2Gi             # No single container can request more than 2 GiB RAM
    min:
      cpu: 50m                # No single container can request less than 50m CPU
      memory: 64Mi            # No single container can request less than 64Mi RAM

  - type: PersistentVolumeClaim
    max:
      storage: 50Gi           # No single PVC can request more than 50 GiB
    min:
      storage: 1Gi            # No single PVC can request less than 1 GiB

Apply the LimitRange and inspect it to confirm the configured limits:

iApply the LimitRange to the cluster
kubectl apply -f team-alpha-limits.yaml
iiInspect it to confirm all configured limits
kubectl describe limitrange team-alpha-limits -n team-alpha

Test that defaults are injected automatically, then verify the maximum is enforced:

iiiRun a pod without specifying any resources
kubectl run test-pod --image=nginx:alpine -n team-alpha
ivCheck the resource values LimitRange injected
kubectl get pod test-pod -n team-alpha -o jsonpath='{.spec.containers[0].resources}'

vTry to exceed the max and watch it be rejected

  --requests='cpu=3,memory=4Gi'

Always Pair LimitRange with ResourceQuota These two objects are designed to work together. Apply them in this order:
  1. Apply the LimitRange first to establish defaults and maximums per container.
  2. Apply the ResourceQuota to cap the namespace-level aggregate totals.
With both in place: every Pod gets sensible resource values (from LimitRange defaults if not specified), and the namespace as a whole cannot exceed its allocated share of the cluster (enforced by ResourceQuota). Neither object alone is sufficient: a ResourceQuota without a LimitRange breaks Pods that omit resource declarations, and a LimitRange without a ResourceQuota does not prevent a team from spinning up 1,000 small Pods that collectively exhaust the cluster.

2.2 Imperative vs Declarative

Section 1.8 introduced these two styles. This section is the practical half: which one to reach for, the commands that go with each, and why the choice matters more than it first appears. It shapes how you work day to day, how you hand changes to a teammate, and whether your cluster is auditable when something breaks in production.

The Analogy: Building a House

Imperative is calling a contractor every hour: "pour the foundation now, wait for it to dry, frame the walls now." You name each step, and if something goes wrong halfway the contractor stops and waits for you.

Declarative is handing over blueprints and saying "build this." The contractor works out the order, and rebuilds a collapsed wall without phoning you. You describe the end state, not the route to it.

Kubernetes is built around the declarative model. The API server holds the desired state you submitted, and controllers work continuously to make reality match it. That is the reconciliation loop from 1.2, and it is the mechanism that makes the cluster self-healing: nobody has to notice a failure and react to it, because the loop is already comparing and correcting.

Imperative: Telling Kubernetes What to Do Right Now

These commands show the imperative style, where each command directly changes cluster state on the spot.

iImperative: create a deployment right now
kubectl create deployment nginx --image=nginx:1.25
iiImperative: scale it right now
kubectl scale deployment nginx --replicas=3
iiiImperative: expose it right now
kubectl expose deployment nginx --port=80 --type=ClusterIP
ivImperative: update the image right now
kubectl set image deployment/nginx nginx=nginx:1.26
vImperative: delete it right now
kubectl delete deployment nginx

The problem with imperative commands in production is that there is no record of what was done or why. If three engineers make imperative changes over a week, nobody can look at the cluster and understand its current state by reading source code. The cluster becomes a "snowflake" that exists only in the live system, nearly impossible to recreate reliably.

Declarative: Describing What You Want to Exist

Let's walk through a declarative deployment. Save the following as deployment.yaml. It describes the desired state of an nginx Deployment in full.

The following YAML defines a Deployment with 3 replicas, resource requests and limits:

Why Declarative is Essential for Production

Three things follow once your manifests live in Git. The first is GitOps: every infrastructure change becomes a pull request, so it gets reviewed before it lands and can be rolled back with a single commit. The second is auditability: when something breaks at 2am, the Git log tells you exactly what changed and who changed it. The third is reproducibility: you can rebuild an entire staging cluster with kubectl apply -f ./. A cluster built by imperative commands offers none of these, because all you have when it breaks is the broken cluster and no history of how it got that way. Lab 10 turns this into an automated loop.

Always Use Declarative for Anything That Matters Use imperative commands only for things you are willing to throw away. Use declarative YAML for anything that needs to exist tomorrow. When you find yourself using an imperative command that you want to keep, convert it to YAML immediately using the --dry-run=client -o yaml trick described below.

kubectl apply vs kubectl create vs kubectl replace

kubectl create -f file.yaml: Creates the resource if it does not exist. Fails with an error if the resource already exists. Use this when you know you are creating something new and want the command to fail loudly if it already exists.

kubectl replace -f file.yaml: Deletes the existing resource and recreates it from the YAML. This is a destructive operation. For Deployments, this causes a brief interruption. Use it carefully.

kubectl apply -f file.yaml: This is the Swiss Army knife and the command you should use almost always in declarative workflows. It creates the resource if it does not exist. If the resource already exists, it computes a diff and applies only the changes. It does not destroy and recreate the resource.

kubectl apply -f deployment.yaml

One more thing worth knowing about apply: it does not blindly overwrite. It reconciles three versions of the object, which is why it can leave fields set by other tools alone.

How kubectl apply computes a diff: the three-way mergeOptional depth

When you run kubectl apply, Kubernetes uses a technique called a three-way strategic merge to figure out what to change. It compares three things:

  1. The last applied configuration stored as an annotation on the object itself.
  2. The current live state of the object, what actually exists in the cluster right now.
  3. The new configuration you are applying, the contents of your YAML file.

From these three, kubectl apply computes: fields in the new YAML but not in last-applied are added; fields in last-applied but not in the new YAML are removed; fields that differ from live state are updated; fields in live state not managed by kubectl apply are left alone.

Do Not Mix apply and create/replace If you create a resource with kubectl create, it will not have the last-applied-configuration annotation. If you later try to manage it with kubectl apply, the three-way merge will not work correctly. Pick one approach and stick with it for each resource.

2.3 Resource Requests, Limits, and QoS

One of the most common sources of mysterious failures in Kubernetes clusters is incorrect or missing resource configuration. Pods get evicted, crash-looping, or throttled in ways that seem unpredictable until you understand exactly how Kubernetes models and enforces resource usage.

Two Types of Resources, Two Very Different Behaviors

CPU is "compressible": If a container tries to use more CPU than its limit allows, Kubernetes simply throttles it. The container keeps running but gets less CPU time. It slows down, but it does not crash or get killed.

Memory is "incompressible": If a container tries to use more memory than its limit allows, the Linux kernel sends it an OOM (Out Of Memory) kill signal and the process dies immediately. Kubernetes then restarts the container. If this keeps happening, you see CrashLoopBackOff with exit code 137.

Resource Over-limit behavior
CPU: wants 800m, limit 500m Throttled to 500m. Slower but alive.
Memory: wants 600Mi, limit 512Mi OOM kill, container restarts, CrashLoopBackOff.
OOM Kill is Silent and Confusing When a container is OOM killed, you will see OOMKilled in the container state and exit code 137. New engineers often spend hours looking at application logs for the crash cause, not realizing the application was killed externally by the kernel before it could even log anything. Always check kubectl describe pod and look for OOMKilled: true before diving into application logs.

Requests vs Limits: What is the Difference?

Requests are what the scheduler uses. When you submit a Pod to Kubernetes, the scheduler looks at each node and asks: "Does this node have enough unallocated resources to satisfy the sum of all requests for this Pod?" The request is a reservation. The actual container may use less than its request or try to use more.

Limits are enforced by the Linux kernel via cgroups on the node where the container actually runs. The kernel enforces CPU limits by throttling and memory limits by killing.

The container spec below sets both, so you can see which number the scheduler reads and which one the kernel enforces:

containers:
- name: my-app
  image: my-app:1.0
  resources:
    requests:
      cpu: 250m      # Scheduler reserves this on a node
      memory: 256Mi  # Scheduler reserves this on a node
    limits:
      cpu: 1000m     # Kernel throttles at this value
      memory: 512Mi  # Kernel OOM kills at this value

Understanding CPU Units

Kubernetes measures CPU in millicores, where 1000m is one full core. The table below converts the values you will write most often.

Millicores Decimal Meaning
1000m 1.0 1 full CPU core
500m 0.5 Half a core
250m 0.25 Quarter of a core
100m 0.1 One tenth of a core
2000m 2.0 2 full cores

Understanding Memory Units

Memory suffixes come in two families, binary and decimal, and they are not interchangeable. The table below lists both so you can see the size difference.

Suffix Type Value Use in Kubernetes
Ki Binary 1,024 bytes Preferred
Mi Binary 1,048,576 bytes Preferred
Gi Binary 1,073,741,824 bytes Preferred
K Decimal 1,000 bytes Avoid
M Decimal 1,000,000 bytes Avoid
G Decimal 1,000,000,000 bytes Avoid

Always use Mi and Gi in Kubernetes. 256Mi = 268,435,456 bytes. 256M = 256,000,000 bytes. The difference matters.

How the Scheduler Uses Requests: Bin-Packing

The Kubernetes scheduler uses requests (not limits) to decide which node a Pod should run on. This is a bin-packing problem: fit the Pods into nodes without overflowing the node's capacity.

Node A (4 CPU, 8Gi) Result
Already allocated: 2000m CPU, 4Gi RAM Remaining: 2000m CPU, 4Gi RAM
New Pod requests: 500m CPU, 1Gi RAM 500m <= 2000m, 1Gi <= 4Gi → CAN schedule
New Pod requests: 3000m CPU, 1Gi RAM 3000m > 2000m → CANNOT schedule on Node A

This means you can have a node with CPU usage of only 20% in your monitoring dashboard, but new Pods cannot be scheduled on it. Why? Because the running Pods have high requests even though they are not actively using all that CPU. The scheduler works on reservations, not actual usage.

QoS Classes: Who Gets Evicted First

From the requests and limits you set, Kubernetes derives a Quality of Service class for each Pod: Guaranteed, Burstable, or BestEffort. You never set it directly. It decides who gets killed first when a node runs out of memory, so it is worth knowing which class your Pods land in.

Under memory pressure the kubelet evicts in class order: BestEffort Pods first, then Burstable Pods worst-offender first, and Guaranteed Pods only as a last resort. This command reports the class Kubernetes assigned to a Pod:

kubectl get pod my-pod -o jsonpath='{.status.qosClass}'

# Output: Guaranteed, Burstable, or BestEffort.
HPA requires CPU requests The Horizontal Pod Autoscaler computes target CPU utilization as a percentage of the CPU request. With no CPU request set there is nothing to take a percentage of, so autoscaling silently does nothing and you get unable to get metrics for resource cpu: unable to fetch metrics from resource metrics API. This is the single most common reason HPA does not work in Lab 5.
How Kubernetes derives each QoS classOptional depth

Kubernetes automatically assigns every Pod one of three QoS classes based on the resource requests and limits you specify. This class determines the Pod's eviction priority when a node runs low on resources.

QoS Class Rule Eviction priority
Guaranteed requests == limits for ALL containers, both CPU and memory Evicted last
Burstable At least one container has a request or limit set, but not all equal Middle
BestEffort No requests or limits set on any container Evicted first

2.4 Labels, Annotations, and Selectors

Kubernetes manages thousands of objects in a cluster. It needs a way to group, filter, and connect these objects to each other. Labels and selectors are the mechanism Kubernetes uses for this.

Labels: The Grouping Mechanism

A label is a key-value pair attached to a Kubernetes object in its metadata section. Labels are used for grouping and selection. They are searchable, filterable, and used by other Kubernetes objects to find Pods they should manage.

The Pod below carries four labels describing its application, version, environment, and tier:

apiVersion: v1
kind: Pod
metadata:
  name: my-web-pod
  labels:
    app: web
    version: "1.2"
    environment: prod
    tier: frontend
spec:
  containers:
  - name: web
    image: nginx:1.25

Label naming rules: Keys can optionally have a prefix separated from the name by a slash (e.g., app.kubernetes.io/name). The name part must be 63 characters or fewer, start and end with an alphanumeric character, and can contain dashes, underscores, and dots. Values follow the same rules.

How Services, Deployments, and NetworkPolicies Use Label Selectors

Deployments use a selector to know which Pods belong to them:

spec:
  replicas: 3
  selector:
    matchLabels:
      app: web          # This Deployment manages Pods with label app=web
      environment: prod
  template:
    metadata:
      labels:
        app: web          # Pod template MUST include these labels
        environment: prod # or the selector will never match anything

Services use a selector to decide which Pods to route traffic to:

spec:
  selector:
    app: web          # Route traffic to all Pods with app=web
  ports:
  - port: 80
    targetPort: 8080

Two Styles of Selector

Kubernetes supports two distinct styles of label selector. Both answer the question "which Pods match these label conditions?", but they differ in how much they can express, and, more importantly, in which API objects accept them. A Service takes only the simpler style; a Deployment takes either. Getting this wrong produces a manifest the API server rejects, so it is worth knowing which is which.

Equality-Based Selectors

Equality-based selectors are the simpler form. They test whether a label key has a specific value.

  1. The operators. Equality-based selectors use three operators:
    1. = or ==: the label value must exactly equal the given string. Both operators mean the same thing.
    2. !=: the label value must NOT equal the given string. This also matches Pods that do not have the key at all.
  2. Using them with kubectl. Multiple conditions are combined with a comma, which acts as a logical AND. A Pod must satisfy all conditions to match. 
    # Match Pods where app equals "web"
kubectl get pods -l app=web

# Match Pods where app equals "web" AND environment equals "prod" (logical AND)
kubectl get pods -l app=web,environment=prod

# Match Pods where environment does NOT equal "staging"
# Also matches Pods that have no "environment" label at all
kubectl get pods -l environment!=staging

# Match Pods where tier equals "frontend" AND version equals "v2"
kubectl get pods -l tier=frontend,version=v2

# The = and == operators are identical
kubectl get pods -l app=web
kubectl get pods -l app==web
Equality-based selectors are the only style supported in Service and ReplicationController spec selectors. They are intentionally simple because Services need to resolve quickly at runtime.

Set-Based Selectors

Set-based selectors are more expressive. Instead of testing equality against a single value, they test membership in a set of values.

  1. The operators. Set-based selectors use four operators:
    1. In: the label value must be one of the listed values. This is an OR within a single key.
    2. NotIn: the label value must NOT be any of the listed values. Also matches if the key is absent.
    3. Exists: the label key must be present on the object, regardless of its value.
    4. DoesNotExist: the label key must NOT be present on the object at all.
  2. In a manifest. Set-based selectors are used in matchExpressions inside Deployment, ReplicaSet, DaemonSet, Job, and StatefulSet specs. They can also be combined with matchLabels (shorthand for equality) in the same selector block. All conditions across both must be satisfied simultaneously. The selector below combines one equality match with four set-based expressions: 
    # Inside a Deployment, ReplicaSet, Job, DaemonSet spec:
selector:
  matchLabels:
    app: web                   # Shorthand equality: app must equal "web"
  matchExpressions:
  - key: environment
    operator: In
    values:
    - prod
    - staging                  # environment must be "prod" OR "staging"

  - key: version
    operator: NotIn
    values:
    - "0.1"
    - "0.2"                    # version must NOT be "0.1" or "0.2" (excludes old versions)

  - key: canary
    operator: DoesNotExist     # Pod must NOT have the "canary" label at all
                               # Useful for targeting only stable (non-canary) Pods

  - key: track
    operator: Exists           # Pod MUST have a "track" label (any value is fine)
  3. With kubectl. The same operators work on the command line: 
    # In operator: environment must be prod OR staging
kubectl get pods -l 'environment in (prod, staging)'

# NotIn operator: tier must NOT be backend or database
kubectl get pods -l 'tier notin (backend, database)'

# Exists operator: Pods that HAVE the "canary" label (any value)
kubectl get pods -l canary

# DoesNotExist operator: Pods that do NOT have the "canary" label
kubectl get pods -l '!canary'

# Combining set-based and equality in one kubectl command
kubectl get pods -l 'app=web,environment in (prod, staging),!canary'

Side-by-Side Comparison

The two styles differ in which operators they offer, which objects accept them, and how much they can express. Read the table row by row to see where each one wins.

A Deployment's spec.selector is immutable after creation. Once you apply a Deployment, you cannot change its selector. If you need to change which Pods a Deployment manages (for example, adding a new required label), you must delete the Deployment and recreate it. This is one reason to design label selectors carefully before your first deploy.
Selector Design Rules
  1. Keep selectors narrow enough to uniquely identify one application's Pods. A selector of just app=web is risky if you ever run two different "web" apps in the same namespace.
  2. Always include both app and at least one more dimension (like component or tier) in selectors for complex deployments.
  3. The Pod template labels in spec.template.metadata.labels must be a superset of the selector. Every label in the selector must appear on the Pod, but the Pod can have additional labels.
  4. Never use DoesNotExist or NotIn as the only condition in a selector: it could accidentally match unrelated Pods that happen to lack those labels.

Annotations: Metadata for Tools, Not for Selection

Annotations are also key-value pairs on Kubernetes objects, but they serve a completely different purpose from labels. Annotations are not used for selection. Instead, annotations are used to attach arbitrary metadata that tools, operators, and external systems can read.

The metadata block below carries scrape settings that Prometheus reads, alongside ordinary bookkeeping fields that no controller acts on:

metadata:
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/port: "9090"
    description: "Main web application for the ecommerce platform"
    contact: "team-alpha@mycompany.com"
    deployed-by: "ci-pipeline-job-12345"
Labels vs Annotations Use labels when you need to SELECT or GROUP objects (a Service finding Pods, monitoring querying all production Pods). Use annotations when you need to STORE metadata that tools or humans will read but that does not participate in selection (config for a monitoring agent, a timestamp, a ticket number, a long description).

2.5 Node Scheduling: Taints, Tolerations, and Affinity

By default the scheduler drops a Pod on any node with enough free CPU and memory for its requests, and for many workloads that is exactly what you want. Production nodes are not interchangeable, though: some have GPUs, some have fast NVMe disks, some are reserved for system components, some sit in other availability zones. You need to say things like "only run this on GPU nodes" or "never put two replicas on one node." Four tools do that: taints, tolerations, nodeSelector, and affinity/anti-affinity.

Tool Direction Mechanism Strength
Taint Node to Pod Repel Hard (NoSchedule) or Soft (PreferNoSchedule)
Toleration Pod to Node Allow entry Works with taints
nodeSelector Pod to Node Require labels Hard, Pod stays Pending if no match
Node Affinity Pod to Node Require or prefer Hard or Soft, more expressive than nodeSelector
Pod Affinity Pod to Pod Co-locate Hard or Soft, put me near this type of Pod
Pod Anti-Affinity Pod to Pod Spread apart Hard or Soft, keep me away from this type of Pod

Taints: Repelling Pods from Nodes

A taint is a property you apply to a node. It acts like a "Do Not Enter" sign. Any Pod that does not explicitly declare it can tolerate that taint will be refused scheduling on that node. Taints are the mechanism Kubernetes uses internally to mark nodes as unschedulable, to reserve control-plane nodes for system components, and to fence off nodes during drains.

A taint has three parts: a key, a value, and an effect. The key and value together describe what the taint is about (for example, hardware=gpu). The effect controls what happens to Pods that do not tolerate the taint:

  1. NoSchedule: the scheduler will not place new non-tolerating Pods on this node. Pods already running when the taint is added are NOT evicted. This is the most common effect and is used to reserve nodes for specific workloads.
  2. PreferNoSchedule: the scheduler tries to avoid placing non-tolerating Pods here, but will do so as a last resort if no other suitable nodes exist. A soft constraint, useful when you prefer isolation but do not require it.
  3. NoExecute: the strongest effect. New non-tolerating Pods are not scheduled AND existing non-tolerating Pods already running are evicted. Kubernetes uses this automatically when a node becomes unreachable or has disk pressure.
# Add a taint to a node
# Format: kubectl taint nodes <node-name> <key>=<value>:<effect>
kubectl taint nodes node-gpu-1 hardware=gpu:NoSchedule
#                               ^^^^^^^  ^^^  ^^^^^^^^^^^
#                               key      val  effect

# Add a soft taint (prefer to avoid, but not a hard block)
kubectl taint nodes node-gpu-1 hardware=gpu:PreferNoSchedule

# Add a NoExecute taint (evicts existing Pods too)
kubectl taint nodes node-gpu-1 hardware=gpu:NoExecute

# View existing taints on a node
kubectl describe node node-gpu-1 | grep Taints

# Remove a taint by appending a minus sign at the end
kubectl taint nodes node-gpu-1 hardware=gpu:NoSchedule-
#                                                      ^ minus sign removes the taint

# Kubernetes adds these taints automatically:
# node.kubernetes.io/not-ready:NoExecute          node is unhealthy
# node.kubernetes.io/unreachable:NoExecute         node lost contact with control plane
# node.kubernetes.io/disk-pressure:NoSchedule      node is running out of disk
# node.kubernetes.io/memory-pressure:NoSchedule    node is running low on memory

Kubernetes adds taints automatically in these situations.

Tolerations: Allowing Pods onto Tainted Nodes

A toleration is a property you add to a Pod that says "I can run on a node that has this specific taint." Tolerations are the counterpart to taints. A Pod with the matching toleration is permitted to be scheduled onto the tainted node, but it is not forced there. The scheduler still picks the best available node from among those the Pod can run on.

A toleration matches a taint when the key, operator, value, and effect all align. There are two operators:

  1. Equal: matches a taint where the key equals the specified key AND the value equals the specified value.
  2. Exists: matches a taint where the key equals the specified key, regardless of value. You can omit the value field when using Exists.

The Pod spec below shows three shapes of toleration: an exact match, a key-only match, and one that expires after a fixed number of seconds:

spec:
  tolerations:
  # Tolerate the specific taint hardware=gpu:NoSchedule
  - key: "hardware"          # Must match the taint's key exactly
    operator: "Equal"        # Use Equal when you want to match a specific value
    value: "gpu"             # Must match the taint's value exactly
    effect: "NoSchedule"     # Must match the taint's effect exactly

  # Tolerate ANY taint with key "hardware", regardless of value or effect
  - key: "hardware"
    operator: "Exists"       # No "value" field needed with Exists

  # Tolerate a NoExecute taint for up to 60 seconds, then get evicted
  # (useful for graceful shutdown during node drains)
  - key: "node.kubernetes.io/not-ready"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 60    # Stay on the node for 60s before being evicted
                             # Without this field, the Pod stays indefinitely

  containers:
  - name: trainer
    image: tensorflow/tensorflow:latest-gpu
Tolerations Allow, They Do Not Force A very common beginner mistake: adding a toleration to a Pod does not guarantee it lands on the tainted node. The toleration only removes the barrier. If you want a Pod to always run on GPU nodes, you need both a toleration (to be allowed on tainted GPU nodes) AND a nodeSelector or node affinity rule (to actively direct the Pod there). Without both, the Pod might tolerate the taint but still get scheduled on a non-GPU node because it has more free capacity.

nodeSelector: Simple Node Selection

nodeSelector is the simplest way to constrain a Pod to run only on nodes with specific labels. You first label the nodes you want to target, then add a nodeSelector field to the Pod spec. The scheduler will only consider nodes whose labels include all key-value pairs in the nodeSelector. If no matching node exists, the Pod stays in Pending state indefinitely until a matching node appears.

nodeSelector uses equality matching only: every key-value pair must match exactly. It does not support set-based operators like In or NotIn. For that expressiveness you need node affinity, described next.

iLabel the nodes you want to target
kubectl label nodes node-gpu-1 hardware=gpu
kubectl label nodes node-gpu-2 hardware=gpu
kubectl label nodes node-ssd-1 storage=nvme
iiVerify the labels were applied
kubectl get nodes --show-labels | grep hardware
iiiRemove a label from a node
kubectl label nodes node-gpu-1 hardware-

# The trailing minus sign removes the label, the same pattern as taints.

Once the node carries the label, a Pod asks for it with a nodeSelector block:

spec:
  nodeSelector:
    hardware: gpu       # Only schedule this Pod on nodes with label hardware=gpu
    # You can add multiple key-value pairs - ALL must match (logical AND)
    # storage: nvme     # Uncomment to also require an NVMe storage node
  containers:
  - name: app
    image: my-gpu-app:latest
When to Use nodeSelector vs Node Affinity Use nodeSelector when your requirement is simple: "this Pod must run on nodes with label X=Y." Use node affinity when you need more expressive rules: "prefer nodes with label X in set (A, B, C)" or "fall back to other nodes if preferred nodes are unavailable." nodeSelector is always a hard requirement. Node affinity can be either hard (required) or soft (preferred).

Affinity: More Expressive Placement Rules

nodeSelector only does exact label matches. Affinity rules go further: they can express preferences as well as requirements, match on sets of values, and place a Pod relative to other Pods rather than to node labels. There are three kinds, and each answers a different question.

  1. Node affinity: which nodes may this Pod land on? This is nodeSelector with set-based operators and an optional "prefer, but do not require" mode.
  2. Pod affinity: which other Pods does this Pod want to sit beside? Use it when two services talk to each other often enough that a network hop between nodes costs real latency, such as an application and its local cache.
  3. Pod anti-affinity: which other Pods must this Pod stay away from? Use it to spread the replicas of one Deployment across separate nodes or zones, so that losing a single node cannot take all of them out at once.

The two Pod rules both need a topologyKey, which is the node label that defines what "near" means. Setting it to kubernetes.io/hostname means the same node, and topology.kubernetes.io/zone means the same availability zone. None of the labs require these rules, so the mechanics of each one sit in the three optional blocks below.

Node affinity: more expressive node selectionOptional depth

Node affinity is a more powerful replacement for nodeSelector. It uses the same set-based selector operators you learned in section 2.4 (In, NotIn, Exists, DoesNotExist, Gt, Lt) and supports two scheduling modes:

  1. requiredDuringSchedulingIgnoredDuringExecution: a hard requirement. The Pod will only be scheduled on a node that satisfies this rule. If no node qualifies, the Pod stays Pending. If a node's labels change after the Pod is running, the Pod is NOT evicted.
  2. preferredDuringSchedulingIgnoredDuringExecution: a soft preference. The scheduler tries to place the Pod on a matching node but falls back to other nodes if no match exists. Each preference has a weight from 1 to 100, where higher weight means stronger preference.

The Pod spec below uses both modes in a single nodeAffinity block:

spec:
  affinity:
    nodeAffinity:

      # HARD REQUIREMENT: Pod will only schedule on nodes in specific zones
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:        # Multiple terms here = OR (any term can match)
        - matchExpressions:       # Multiple expressions within one term = AND (all must match)
          - key: topology.kubernetes.io/zone
            operator: In
            values:
            - us-east-1a          # Node must be in us-east-1a OR us-east-1b
            - us-east-1b
          - key: kubernetes.io/os
            operator: In
            values:
            - linux               # AND the node must be running Linux

      # SOFT PREFERENCES: try these, but fall back if not available
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80                # High weight = strong preference
        preference:
          matchExpressions:
          - key: storage
            operator: In
            values:
            - ssd                 # Prefer SSD nodes (weight 80)

      - weight: 20                # Lower weight = weaker preference
        preference:
          matchExpressions:
          - key: node-type
            operator: In
            values:
            - high-memory         # Also prefer high-memory nodes (weight 20)
                                  # If both ssd AND high-memory match, score = 100
                                  # If only ssd matches, score = 80
                                  # If only high-memory matches, score = 20
                                  # If neither matches, score = 0 (but Pod still schedules)
  containers:
  - name: app
    image: my-app:latest
nodeSelectorTerms - OR Logic Between Terms Inside requiredDuringSchedulingIgnoredDuringExecution, if you provide multiple items in the nodeSelectorTerms list, a node only needs to match ONE of them (OR logic). But within a single term, all matchExpressions must match (AND logic). This lets you express complex rules like: "nodes in zone A with SSD, OR nodes in zone B regardless of storage type."

Pod affinity is the one to reach for when latency between two services costs you more than the risk of losing them together.

Pod affinity: co-locating PodsOptional depth

While node affinity controls which nodes a Pod can land on, pod affinity controls which other Pods a Pod wants to be near. You use pod affinity when two services communicate so frequently that placing them on the same node reduces network latency significantly, for example an application Pod and its local cache.

The topologyKey field is critical: it defines what "near" means. kubernetes.io/hostname means "same node." topology.kubernetes.io/zone means "same availability zone." The scheduler groups nodes by the value of that label and tries to place the Pod in the same group as the target Pods.

The Pod spec below asks the scheduler to place this Pod on a node that already runs a cache Pod:

spec:
  affinity:
    podAffinity:
      # HARD: must be scheduled on a node that already has a Pod with app=cache
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - cache               # Find nodes that have a Pod with label app=cache
        topologyKey: kubernetes.io/hostname
        # topologyKey: kubernetes.io/hostname  = same physical node
        # topologyKey: topology.kubernetes.io/zone = same availability zone (same datacenter)
        # topologyKey: topology.kubernetes.io/region = same region (same country/cloud region)
  containers:
  - name: app
    image: my-latency-sensitive-app:latest
Pod Affinity Can Create Scheduling Bottlenecks If you use required pod affinity and the target Pods do not exist yet (or all live on one node), your Pod will be stuck in Pending or all replicas will crowd onto a single node. Use preferred pod affinity for most co-location use cases, and reserve required for strict data locality requirements.

Anti-affinity is the reverse trade: you accept a worse packing of Pods onto nodes in exchange for surviving the loss of any one node.

Pod anti-affinity: spreading replicasOptional depth

Pod anti-affinity is the opposite of pod affinity. It tells the scheduler "do not place this Pod near other Pods that match this selector." The most common use case is spreading Deployment replicas across different nodes or availability zones so that a single node failure does not take down your entire service.

Without anti-affinity, Kubernetes might place all three replicas of your web server on the same node if that node has the most free resources. If that node goes down, all three replicas are lost simultaneously. With anti-affinity, you can guarantee each replica lands on a different node.

The Pod spec below pushes every replica of the web Deployment onto a different node:

spec:
  affinity:
    podAntiAffinity:
      # HARD: never schedule this Pod on a node that already has a Pod with app=web
      # This guarantees each replica of the web Deployment lands on a different node
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - web                 # Match Pods with label app=web (i.e., other replicas of myself)
        topologyKey: kubernetes.io/hostname  # "different node" = different hostname

      # SOFT: also prefer different availability zones
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
            - key: app
              operator: In
              values:
              - web
          topologyKey: topology.kubernetes.io/zone  # "prefer different AZ"
  containers:
  - name: web
    image: my-web-app:latest
Topology Spread Constraints - the Modern Alternative Kubernetes 1.19+ introduced topologySpreadConstraints as a more predictable and controllable way to spread Pods across nodes and zones. It lets you declare "spread my Pods such that no topology domain has more than N more Pods than any other." For new clusters, prefer topologySpreadConstraints over pod anti-affinity for spreading workloads. Anti-affinity is still the right tool for strict "never co-locate" requirements.
Choosing the Right Scheduling Tool
  1. Use taints + tolerations to reserve nodes for specific workloads (GPU nodes, spot nodes, system nodes). Taints go on nodes; tolerations go on Pods.
  2. Use nodeSelector for simple, hard node selection by label. Fast to write, no flexibility. Pod stays Pending if no match.
  3. Use node affinity when you need set-based matching, soft preferences, or complex multi-condition rules.
  4. Use pod affinity to co-locate Pods that benefit from low-latency communication (app + cache on same node).
  5. Use pod anti-affinity to spread replicas across nodes or zones for fault tolerance. Combine with topologySpreadConstraints for fine-grained control.
  6. For most spreading use cases on Kubernetes 1.19+, prefer topologySpreadConstraints over pod anti-affinity.

2.6 Multi-Container Pods: Init Containers and Sidecars

Most Pods hold one container. When a Pod holds more, the extras almost always fall into one of two roles, and Kubernetes has a separate mechanism for each.

Role Where it goes Lifecycle
Init container spec.initContainers Runs to completion before app containers start. Several run in order, one after another.
Sidecar spec.initContainers with restartPolicy: Always Starts before the app and keeps running beside it for the life of the Pod.

Use an init container for setup that must finish first: wait for a database to accept connections, run a schema migration, or pull config into a shared volume. If it exits non-zero, kubelet restarts it and the app never starts, which is usually what you want.

Use a sidecar for a helper that must run the whole time: a log shipper, a metrics exporter, or a service-mesh proxy. Declaring it in initContainers with restartPolicy: Always is the modern way, stable since Kubernetes v1.33.

The manifest below runs a migration first, then keeps a log shipper alongside the app. Save it as multi-container.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: multi-container-demo
spec:
  volumes:
    - name: logs
      emptyDir: {}                  # shared by the app and the log shipper

  initContainers:
    - name: run-migration           # plain init container: must finish first
      image: busybox:1.36
      command: ['sh', '-c', 'echo "migrating..."; sleep 3; echo done']

    - name: log-shipper             # sidecar: restartPolicy makes it long-running
      image: busybox:1.36
      restartPolicy: Always         # the only accepted value here
      command: ['sh', '-c', 'tail -F /var/log/app/out.log']
      volumeMounts:
        - name: logs
          mountPath: /var/log/app

  containers:
    - name: app
      image: busybox:1.36
      command: ['sh', '-c', 'while true; do echo "hello $(date)" >> /var/log/app/out.log; sleep 5; done']
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
iApply it and watch the init container run before the app
kubectl apply -f multi-container.yaml
kubectl get pod multi-container-demo -w
# Output: STATUS moves Init:0/2 -> Init:1/2 -> Running as each stage completes.
# Press Ctrl+C once it reaches Running.
iiConfirm the sidecar is tailing the shared volume
kubectl logs multi-container-demo -c log-shipper --tail=5
# Output: the "hello ..." lines the app container is writing.
# -c selects a container; without it kubectl asks you to pick one.
kubectl delete pod multi-container-demo
Why sidecars moved into initContainersOptional depth

Before this existed, a sidecar was just a second entry in spec.containers, which caused two persistent bugs.

  1. Startup races. Containers in spec.containers start together with no ordering, so an app could issue its first request before the proxy beside it was listening.
  2. Jobs that never finished. A Job is complete when its containers exit. A sidecar that runs forever meant the Job hung forever, which is why service-mesh proxies broke batch workloads.

Putting the sidecar in initContainers reuses the init machinery to fix both: Kubernetes starts it before the app, lets the Pod proceed once it is started rather than finished, and terminates it after the app exits so Jobs can complete. The feature was alpha in v1.28, on by default in v1.29, and stable in v1.33.

One consequence worth knowing: a sidecar's resource requests count toward the Pod's total, so they affect scheduling and QoS class exactly like an app container's.

Key Takeaways

  1. A namespace scopes names, not network traffic. The API server filters objects by their metadata.namespace, so two teams can each own a Service called api, but a Pod in one namespace still reaches api.other-team.svc.cluster.local until you write a NetworkPolicy.
  2. Requests are for the scheduler and limits are for the kernel. The scheduler places a Pod by summing its requests against a node's free capacity, while cgroups on the chosen node enforce the limits, so a Pod with no requests at all is scheduled as though it needs nothing and can crowd a node that has no room for it.
  3. Memory over its limit kills the container; CPU over its limit only slows it. An OOM kill surfaces as OOMKilled and exit code 137 in kubectl describe pod and leaves nothing in the application log, so read describe before you read logs.
  4. Kubernetes computes a Pod's QoS class from its requests and limits. You never set the class directly, and under memory pressure the kubelet evicts BestEffort Pods first and Guaranteed Pods last, so setting a critical Pod's requests equal to its limits is what earns it the Guaranteed class and the last place in that order.
  5. Labels are the wiring between objects. A Service, a Deployment, and a NetworkPolicy all find Pods through a label selector rather than a name or an IP, and a Deployment's selector cannot be changed after creation, so a careless selector means deleting and recreating the Deployment.
  6. Taints repel, tolerations permit, and affinity attracts. Taints go on nodes and tolerations go on Pods, node affinity states which nodes a Pod prefers or requires, and pod anti-affinity or topologySpreadConstraints push replicas apart for fault tolerance.

3. The kubectl Debugging Toolkit

Knowing how to create resources in Kubernetes is only half the skill. The other half, and arguably the more valuable half in day-to-day operations, is knowing how to investigate and diagnose problems. Production incidents do not come with a manual. You need to know how to read the signals Kubernetes gives you, narrow down the problem, and fix it efficiently under pressure.

The Debugging Mindset

  1. GET: Find that something is wrong. "My application is returning errors or not responding." Run kubectl get pods and look for a Pod in Error or CrashLoopBackOff.
  2. DESCRIBE: Find WHY it is wrong. "What events led to this state?" Run kubectl describe pod <name> and read the Events section. 90% of problems are diagnosed here.
  3. LOGS: Read the application's own error messages. "What did the application say before it crashed?" Run kubectl logs <pod> --previous to read the last run's output.
  4. EXEC: Look inside the running container. "Is the config file correct? Can it reach the database?" Run kubectl exec -it <pod> -- sh to inspect from inside.

Work through these steps in order. Do not jump to exec before reading describe and logs. Most problems are solved by step 2 or 3.

3.10 Node Maintenance: cordon, drain, and uncordon

Sooner or later you need to take a node out of service to patch its kernel or resize it. Deleting the node would strand its Pods. Kubernetes gives you three commands to move workloads off first.

Command What it does
kubectl cordon Marks the node unschedulable. Existing Pods stay put; no new ones land there.
kubectl drain Cordons the node, then evicts its Pods so their controllers reschedule them elsewhere.
kubectl uncordon Marks the node schedulable again once maintenance is finished.
iStop new Pods landing on the node
kubectl cordon minikube
kubectl get nodes
# Output: STATUS becomes "Ready,SchedulingDisabled"
iiEvict the Pods so they can be rescheduled
kubectl drain minikube --ignore-daemonsets --delete-emptydir-data

# --ignore-daemonsets   DaemonSet Pods are expected on every node, so skip them
# --delete-emptydir-data acknowledges that emptyDir contents will be lost
iiiPut the node back into service
kubectl uncordon minikube
kubectl get nodes
# Output: STATUS back to "Ready"
Draining a single-node cluster empties it

On Minikube there is nowhere else for the Pods to go, so they will sit in Pending until you run uncordon. Run the drain above only if you are ready to undo it immediately. On a real multi-node cluster this is the normal way to patch a node.

What eviction actually does, and PodDisruptionBudgetsOptional depth

drain does not delete Pods directly. It submits an eviction request for each one, which is a different API endpoint that respects a safety valve called a PodDisruptionBudget (PDB).

A PDB declares how much of an application may be down at once, for example "at least 2 of my 3 replicas must stay available." If evicting a Pod would breach that budget, the API server refuses the eviction and drain waits rather than taking your service down. The budget below keeps at least two replicas of web running through any voluntary disruption:

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2            # or use maxUnavailable: 1
  selector:
    matchLabels:
      app: web

This is why a drain can appear to hang. It is usually not stuck, it is respecting a budget. Check with kubectl get pdb. Note that a PDB only protects against voluntary disruption like a drain; it cannot stop a node from crashing.

Key Takeaways

  1. The workflow is get, then describe, then logs. get tells you which object is unhealthy, describe tells you why Kubernetes thinks so, and logs tells you what the application itself said, which is the path that took the payment-api outage to a wrong database password in three commands.
  2. The Events section of describe holds the cause of most Pod failures. Image pull errors, unschedulable Pods, failed probes, and OOM kills all announce themselves there, so reading Events first stops you from guessing at application code that was never the problem.
  3. A crash-looping Pod needs logs --previous. The container running right now was started after the failure and has nothing to say, while the previous run holds the error that caused the exit.
  4. exec is the last step, not the first. A shell inside the container rarely shows you anything describe and logs have not already shown you, so save it for what you cannot see from outside, such as whether a mounted config file really holds the value you expect.
  5. drain evicts Pods rather than deleting them. Eviction respects a PodDisruptionBudget, so a drain that appears to hang is usually honoring a budget, and on a single-node cluster it leaves every Pod Pending until you run uncordon.

Section A: Conceptual Foundation, Understanding the Object Hierarchy

Before writing a single line of YAML or running a single command, you need a solid mental model of how Kubernetes objects relate to each other. Rushing to commands without this model is the single biggest reason beginners get confused when things go wrong.

The Kubernetes Workload Object Hierarchy

When you deploy an application in Kubernetes, you are creating a layered hierarchy of objects. Each layer exists for a specific reason. Understanding why each layer exists is as important as knowing what it is.

Read this diagram carefully. It shows four critical facts:

  1. A Deployment does not contain Pods directly, it creates and owns a ReplicaSet, which in turn creates and owns the Pods.
  2. Pods each get their own private cluster IP address, which changes every time a Pod is deleted and recreated.
  3. A Service is not nested inside the Deployment hierarchy at all, it is a completely separate object that finds Pods using label selectors.
  4. Labels (the key-value pair app: web) are the glue that connects all of these objects together.

The Four Objects, in One Table

Section 1.9 introduced these objects and 1.10 covered the Service types. Here they are in one place, because this lab creates all four and you will want the definitions within reach.

Object Its one job Why you rarely create it directly
Pod Wraps one or more containers that share an IP, volumes, and a lifecycle It is ephemeral. A naked Pod, meaning one you created directly with kubectl run or a raw Pod manifest, has no controller watching it. If its node dies it is gone for good and nothing brings it back.
ReplicaSet Keeps exactly N Pods alive that match a label selector It has no concept of updates. Changing its image leaves the running Pods untouched.
Deployment Owns a ReplicaSet and adds rolling updates and rollbacks You do create this one. It is the object you normally write for a stateless workload.
Service Gives a changing set of Pods three stable things: a ClusterIP, a DNS name, and load balancing across whichever Pods are currently healthy You do create this one too. A Deployment alone has no stable address, so almost every Deployment is paired with a Service.

The chain runs one way: you create a Deployment, it creates a ReplicaSet, and the ReplicaSet creates the Pods. The Service sits outside that chain and finds Pods by label instead. That last detail breaks more first labs than anything else, so it gets its own subsection below.

Pod IPs are temporary

Every Pod gets a private address from the cluster's Pod CIDR, the block of IPs reserved for Pods, so it looks like 10.244.0.5. These addresses are reachable only from inside the cluster, and they do not survive a restart: delete a Pod and its replacement comes back on a different one. Nothing should ever connect to a Pod IP directly, and that is the whole reason Services exist.

The object that bridges a Service to those Pod IPs is called an Endpoints object, or an EndpointSlice in current clusters, which is the same idea split across several smaller objects so it scales. It holds the list of Pod IPs that currently match the Service's selector, and kube-proxy turns that list into the routing rules in the kernel. You will see it in this lab's kubectl describe output.

In production you rarely expose Services one by one

NodePort opens a high-numbered port on every node in the cluster, which is convenient for a lab and awkward for security. Real clusters put one HTTP entry point in front of everything and route by hostname and path, using an Ingress Controller or its successor the Gateway API. Lab 7 builds exactly that. For this lab, NodePort keeps the moving parts down.

Labels: the Three Rules That Break Labs

A label is a key-value pair attached to an object, such as app: web or environment: production. A selector is a query against those labels. That is the entire idea, and 2.4 goes deeper into it, but the stakes are worth stating plainly: without labels a Deployment cannot find its Pods, a Service cannot route to them, and an autoscaler cannot find the Deployment to scale. Three specific mismatches cause most first-lab failures.

  1. A Deployment's spec.selector.matchLabels must exactly match the labels under spec.template.metadata. If they differ, the API server rejects the manifest outright.
  2. A Service's spec.selector must match the Pod labels, not the Deployment's own labels. These are often different, and when they are, the Service accepts traffic and quietly routes it nowhere.
  3. Labels are case and whitespace sensitive. app: Web and app: web are two different labels.

Anatomy of a Manifest

Every object you write has the same four top-level fields, plus a fifth that Kubernetes fills in itself.

Step 1: Create the Deployment

We will write a Deployment manifest line by line and understand exactly what every field means and why it is there. This is more important than simply copying and pasting, once you understand the structure, you can write any Deployment from scratch.

1.1 Write the Manifest

Create a new file named nginx-deployment.yaml in your working directory and add the following content:

apiVersion: apps/v1         # The Deployment object lives in the 'apps' API group, stable version v1
kind: Deployment            # We are declaring a Deployment object
metadata:
  name: nginx-deployment    # The name of this Deployment in the cluster. Must be unique per namespace.
  labels:
    app: web                # A label on the Deployment object itself. Useful for querying later.
                            # Note: this label is ON the Deployment, not on the Pods it creates.
spec:                       # Begin the desired-state declaration
  replicas: 2               # Desired number of identical Pod copies. Kubernetes will always try
                            # to maintain exactly this many running Pods.

  selector:                 # How this Deployment finds and claims its own Pods.
    matchLabels:            # The Deployment owns all Pods whose labels include EVERY entry here.
      app: web              # This MUST exactly match the labels in spec.template.metadata.labels.
                            # If it does not match, the API server will reject the manifest.

  template:                 # The Pod template. Everything under here defines how each Pod is created.
    metadata:
      labels:
        app: web            # Labels placed on every Pod that this Deployment creates.
                            # The selector above (app: web) must match these labels exactly.
                            # The Service we create later will also use this label to find Pods.
    spec:                   # The specification of the Pod itself
      containers:           # A list of containers inside each Pod (we have one here)
      - name: nginx         # A name for this container. Used in logs and kubectl exec.
        image: nginx:1.29-alpine
                            # The container image to run. Format: <repository>/<name>:<tag>
                            # 'nginx' pulls from Docker Hub's official nginx image.
                            # '1.29-alpine' is a specific, pinned version tag.
                            # '-alpine' means it is based on Alpine Linux, a very small base
                            # image (~5 MB) with a smaller attack surface than ubuntu-based images.
                            # NEVER use ':latest' in production, the image can change without
                            # your knowledge on the next pull, breaking reproducibility.

        ports:
        - containerPort: 80 # Documents that this container listens on port 80.
                            # This is informational, it does not actually open or expose the port.
                            # The Service will use targetPort: 80 to send traffic here.

        resources:          # Resource requests and limits (see Section 2.3 for full explanation)
          requests:         # What the scheduler RESERVES on the node for this container.
            cpu: "50m"      # 50 millicores = 0.05 of one CPU core. The scheduler guarantees this.
            memory: "64Mi"  # 64 Mebibytes of RAM reserved. This affects node placement decisions.
          limits:           # The MAXIMUM this container is allowed to consume.
            cpu: "200m"     # If the container tries to use more CPU, it is throttled, not killed.
            memory: "128Mi" # If the container exceeds this memory limit, the kernel kills it
                            # (OOMKilled). Always set limits to prevent one runaway Pod from
                            # destabilizing the entire node.

Why the selector and template labels must match: the Deployment controller uses spec.selector to find Pods in the cluster that it is responsible for. It cannot track them by name (Pods have random name suffixes), labels are the only connection. If your selector says app: web but your Pod template says app: frontend, the Deployment will create Pods it cannot find again, and the ReplicaSet will spin up new ones endlessly. The API server validates this consistency when you apply the manifest, a mismatch is a validation error, not a runtime error.

1.2 Apply the Manifest

Now apply the manifest to the cluster. The kubectl apply command sends this YAML to the Kubernetes API server. The API server validates it, stores it in etcd, and notifies the Deployment controller. The controller creates a ReplicaSet, the ReplicaSet creates two Pods, the scheduler assigns each Pod to a node, and the kubelet on that node pulls the image and starts the containers.

kubectl apply -f nginx-deployment.yaml

You should see:

deployment.apps/nginx-deployment created

If you run the command again without changing the file, you will see deployment.apps/nginx-deployment unchanged. This is the idempotent nature of kubectl apply: it compares what you submitted to what already exists and only makes changes if there is a difference. This is safe to run repeatedly and is why apply is always preferred over kubectl create for manifest-driven workflows.

What happens inside Kubernetes when you run kubectl apply
  1. kubectl serializes your YAML to JSON and sends an HTTP PUT/PATCH request to the API server.
  2. The API server authenticates you, authorizes the action via RBAC, validates the schema, applies admission webhooks (if any), and persists the object to etcd.
  3. The API server publishes a watch event saying "Deployment nginx-deployment was created."
  4. The Deployment controller (inside kube-controller-manager) receives this event and creates a ReplicaSet.
  5. The ReplicaSet controller receives its creation event and creates 2 Pod objects (just data in etcd at this point, no container yet).
  6. The scheduler receives the Pod creation events, evaluates all nodes for CPU/memory fit, affinity rules, and taints, and assigns each Pod to a node by writing a nodeName field into the Pod spec.
  7. The kubelet on the chosen node receives the Pod assignment event, calls the container runtime (containerd) to pull the image and start the containers, then writes back the Pod's IP address and status.

All of this happens in seconds and entirely through the watch-notify pattern, no component polls; every component is notified only when something it cares about changes.

Step 2: Test Self-Healing

Self-healing is one of the most important behaviors Kubernetes provides, and it is not magic, it is the Deployment's reconciliation loop responding to a change in actual state. Understanding this loop is the mental model that makes Kubernetes make sense.

2.1 The Reconciliation Loop in Detail

The ReplicaSet controller runs an infinite loop. On every iteration, it:

  1. Reads the desired state from its ReplicaSet object: "I need 2 Pods with label app=web and this specific Pod template."
  2. Reads the actual state from the cluster: "I can find 1 Pod with label app=web that matches my selector."
  3. Computes the difference: "I am 1 Pod short."
  4. Takes action: creates 1 new Pod object.
  5. Yields control and waits for the next change notification.

When you delete a Pod, this loop immediately detects the discrepancy and creates a replacement. The replacement Pod will have a fresh name, a new IP address, and will go through the full lifecycle: Pending (waiting for scheduling) → ContainerCreating (image being pulled, container being started) → Running (container is running) → (eventually) Ready (container passed the readiness check).

Important distinction, Pod deletion vs. node failure: when you delete a Pod manually, it is a graceful termination, Kubernetes sends SIGTERM to the container, waits for the graceful shutdown period (terminationGracePeriodSeconds, default 30 seconds), and then sends SIGKILL. When a node fails (powers off, loses network), Kubernetes waits for the node's heartbeat timeout (default ~5 minutes) before marking the node as NotReady and evicting its Pods to healthy nodes. The self-healing behavior is the same in both cases, but the timing differs.

2.3 Understanding Pod Lifecycle Phases

Every Pod passes through a defined set of phases during its lifetime. Understanding these phases is essential for debugging:

  1. Pending: the Pod object has been created in etcd, but it is not yet running on a node. This phase includes waiting for the scheduler to assign a node, waiting for the image to be pulled, and waiting for volumes to be mounted. A Pod stuck in Pending for more than a minute usually indicates a resource constraint (not enough CPU/memory on any node) or a volume binding problem.
  2. ContainerCreating: the node has been assigned and the container runtime is preparing the container, pulling the image, creating the container filesystem, setting up networking. This normally takes a few seconds to a few minutes depending on image size and network speed.
  3. Running: at least one container in the Pod is running. Note that Running does not mean the Pod is ready to serve traffic, readiness is a separate concept enforced by readiness probes (see Lab 5).
  4. Succeeded: all containers in the Pod have exited with exit code 0. This is the terminal state for Job Pods and short-lived tasks. A Deployment never targets this state, it always wants its Pods Running.
  5. Failed: at least one container has exited with a non-zero exit code and will not be restarted. Distinct from CrashLoopBackOff, which is a condition (not a phase) where a container keeps crashing and Kubernetes applies an exponential backoff before restarting it again.
  6. Unknown: the API server cannot get status from the node. This usually means the node has lost network connectivity.

Step 3: Scale the Deployment

3.1 What Happens Internally When You Scale

Scaling a Deployment changes the spec.replicas field in the Deployment object. The Deployment controller detects this change, updates the ReplicaSet's spec.replicas field, and the ReplicaSet controller creates or deletes Pods to reach the new count. No Pods are restarted or modified, new ones are added (scale up) or existing ones are gracefully terminated (scale down). The existing Pods continue serving traffic throughout.

There are two kinds of scaling in Kubernetes:

  1. Horizontal scaling (what we are doing here): add more Pod replicas. This is the Kubernetes-native scaling approach. It works well for stateless applications where each Pod is identical and independent. The kubectl scale command and the Horizontal Pod Autoscaler (HPA) both do horizontal scaling.
  2. Vertical scaling: give each Pod more CPU and memory. In Kubernetes this means updating the resources.requests and resources.limits in the Pod template, which triggers a rolling update (Pods are replaced one at a time with the new resource configuration). The Vertical Pod Autoscaler (VPA) automates this but requires careful planning, it is not the default scaling approach.

3.2 Scale Up to 4 Replicas

These commands raise the replica count and then confirm the new Pods are created and running.

iScale the Deployment to 4 replicas
kubectl scale deployment nginx-deployment --replicas=4
# Watch the Deployment report its progress
iiConfirm the Deployment now wants 4 replicas
kubectl get deployment nginx-deployment
# Confirm all 4 Pods are present and Running
iiiWatch the four Pods get created
kubectl get pods -l app=web -o wide

Expected output after a few seconds:

NAME               READY   UP-TO-DATE   AVAILABLE   AGE
nginx-deployment   4/4     4            4           8m

The two new Pods are identical to the two existing ones, same image, same labels, same resource requests, different names and IP addresses. The ReplicaSet created them from the same Pod template.

Declarative vs. imperative scaling: kubectl scale is an imperative command, it directly modifies the cluster state. For a persistent change, update the replicas: 4 field in your nginx-deployment.yaml file and re-run kubectl apply -f nginx-deployment.yaml. This keeps your YAML file as the source of truth and allows version control of your desired state. In a GitOps workflow, you would never use kubectl scale in production, all changes go through Git.

3.3 Mention of Horizontal Pod Autoscaler

Manual scaling is useful for understanding the concept, but in production you want scaling to happen automatically in response to load. The Horizontal Pod Autoscaler (HPA) watches metrics (CPU utilization, memory, or custom application metrics) and automatically adjusts spec.replicas when thresholds are crossed. For example, an HPA might say "keep CPU utilization below 70%, scale up if it goes higher, scale down when load drops."

HPA requires the metrics-server to be installed in the cluster. We cover HPA configuration in Lab 5. For now, scale back down to 2 so we are working with a manageable number of Pods:

kubectl scale deployment nginx-deployment --replicas=2
kubectl get pods -l app=web

Step 4: Expose with a Service

Our Pods are running and healthy, but they are completely unreachable from outside the cluster. Each Pod has a private cluster IP address, but those addresses are ephemeral and not accessible from your laptop or from the internet. We need a Service to create a stable, durable network endpoint.

4.1 The Three-Port Model

NodePort Services introduce a concept that confuses almost every beginner: three different port numbers. Here is a precise explanation of each:

  1. port: the port on the Service itself, the port that other Pods inside the cluster use when they connect to this Service via its ClusterIP or DNS name. For example, another Pod would reach your Nginx at nginx-service:80. This is the Service's listening port.
  2. targetPort: the port on the Pod that the Service forwards traffic to. This must match the port your application is actually listening on inside the container. For Nginx, that is port 80. If your application listens on port 3000, targetPort should be 3000 even if the Service's port is 80.
  3. nodePort: the port on each Node's external IP address that is opened by kube-proxy. This is what you use from outside the cluster. Traffic arriving at <any-node-ip>:30080 is forwarded to the Service, which in turn forwards it to a Pod's port 80. The valid range for nodePort is 30000-32767.

The traffic path for an external request is:

4.2 Write the Service Manifest

Create a new file named nginx-service.yaml:

apiVersion: v1              # Services are in the core API group, so no group prefix, just 'v1'
kind: Service               # We are declaring a Service object
metadata:
  name: nginx-service       # The stable DNS name will be based on this: nginx-service.default.svc.cluster.local
spec:
  type: NodePort            # Expose the Service on each Node's IP at a static port.
                            # Default type is ClusterIP (no external access).
                            # LoadBalancer would provision a cloud load balancer (not available in bare Minikube).

  selector:                 # Which Pods should receive traffic from this Service?
    app: web                # This must match the Pod labels (from spec.template.metadata.labels in the Deployment).
                            # Kubernetes continuously watches for Pods with this label and updates
                            # the Endpoints object as Pods come and go.

  ports:
    - protocol: TCP         # Only TCP is valid here for HTTP traffic (UDP is supported for some use cases)
      port: 80              # The port the Service listens on (inside the cluster)
      targetPort: 80        # The port on the Pod to forward traffic to (must match containerPort in the Deployment)
      nodePort: 30080       # The port opened on every node's external interface.
                            # Omit this to let Kubernetes pick a random port in 30000-32767.
                            # We pin it to 30080 so the lab instructions are deterministic.

Section B: Troubleshooting Guide

Every Kubernetes beginner encounters the same set of errors. Here is a systematic guide to diagnosing and fixing the most common ones. The universal first step for any problem is always the same three-command sequence:

kubectl get pods                    # Step 1: identify which Pod is troubled and its STATUS
kubectl describe pod <pod-name>     # Step 2: read the Events section at the bottom for the cause
kubectl logs <pod-name>            # Step 3: read the container's own output for application errors

Ninety percent of all Kubernetes problems are diagnosed by those three commands in that order. Do not skip ahead to guess-and-check; follow the sequence.

Problem: Pod Stuck in Pending

Symptom: kubectl get pods shows a Pod in Pending status for more than 60 seconds.

What it means: the scheduler cannot find a node that satisfies the Pod's requirements. The Pod exists in etcd but has not been assigned to any node, so no container has started.

Most common causes and fixes:

  1. Insufficient resources: the Pod's resources.requests exceed what is available on any node. Run kubectl describe pod <name> and look for an event like 0/1 nodes are available: 1 Insufficient cpu. Fix: reduce resource requests, or add more nodes, or scale down other workloads to free up capacity. In Minikube, you can check available resources with kubectl top nodes (requires metrics-server).
  2. Node taints / affinity rules: the Pod has affinity or toleration constraints that no node satisfies. Look for events like didn't match node selector or node(s) had taint. Fix: adjust nodeSelector, affinity, or tolerations in the Pod spec.
  3. PVC not bound: the Pod requires a PersistentVolumeClaim that cannot find a matching PersistentVolume. Run kubectl get pvc and check for Pending status. Not relevant for this lab, but common in stateful workloads.
iDiagnose Pending: read the Events section
kubectl describe pod <pod-name>
iiCheck available node resources
kubectl describe nodes | grep -A 5 "Allocated resources"

Problem: ImagePullBackOff or ErrImagePull

Symptom: kubectl get pods shows ImagePullBackOff or ErrImagePull in the STATUS column.

What it means: the node's container runtime (containerd) attempted to pull the container image and failed. Kubernetes will retry with exponential backoff (1s, 2s, 4s, 8s... up to 5 minutes between retries), which is why the status is BackOff.

Most common causes and fixes:

  1. Typo in the image name or tag: ngnix:1.29 instead of nginx:1.29, or nginx:1.99-alpine (a tag that does not exist). Run kubectl describe pod <name> and read the Events, it will say something like Failed to pull image "ngnix:1.29": rpc error: ... not found. Fix: correct the image name in your manifest and re-apply.
  2. Private registry without credentials: the image is in a private registry and no ImagePullSecret is configured. The error will say unauthorized: authentication required. Fix: create a Secret of type kubernetes.io/dockerconfigjson and reference it in spec.imagePullSecrets.
  3. Docker Hub rate limit: anonymous Docker Hub pulls are limited to 100 per 6 hours per IP address. You may see toomanyrequests: Too Many Requests. Fix: authenticate to Docker Hub by creating an image pull secret with your Docker Hub credentials, or use a different registry mirror.
iDescribe a Pod to read its events
kubectl describe pod <pod-name>
# Look for: Events → Failed → reason for the failure
# Correct the image and re-apply
iiFix the image name and reapply the manifest
# Edit nginx-deployment.yaml and correct the image name first.
kubectl apply -f nginx-deployment.yaml

Problem: CrashLoopBackOff

Symptom: kubectl get pods shows CrashLoopBackOff and the RESTARTS counter is climbing.

What it means: the container is starting, but the process inside it is exiting almost immediately with a non-zero exit code. Kubernetes is restarting it automatically (as configured by the restart policy), but applying exponential backoff to avoid thrashing. The application itself is crashing on startup.

Most common causes and fixes:

  1. Application startup failure: the application cannot find a required configuration file, environment variable, or network dependency. Fix: read the logs from the crashed container.
  2. Wrong container command or entrypoint: the command in the Pod spec does not match what the image provides. Fix: run kubectl exec -it <pod> -- sh if the container stays up long enough, or check the image's documentation.
  3. Failing liveness probe: a liveness probe is configured and the container's health endpoint is returning errors, causing Kubernetes to kill and restart the container. Fix: check liveness probe configuration and application health endpoint.
  4. Missing secrets or ConfigMaps: the Pod references a Secret or ConfigMap that does not exist. This usually causes CreateContainerConfigError rather than CrashLoopBackOff, but can manifest as either.
iRead the previous container's logs (--previous)
kubectl logs <pod-name> --previous

Diagnosis:

iCheck whether the Service has any backing Pods

Problem: OOMKilled, Container Killed by Out-of-Memory

Symptom: Pod shows OOMKilled in its status, or kubectl describe pod <name> shows Reason: OOMKilled in the last container state. The RESTARTS counter may be climbing (if the Deployment's restart policy is keeping it alive).

Most common causes:

  1. Memory limit set too low for the application's actual memory usage.
  2. Memory leak in the application causing gradual memory growth until the limit is hit.
  3. A sudden spike in request volume causing much higher memory usage than baseline.
iConfirm OOMKilled
kubectl describe pod <pod-name>

# Exit code 137 = 128 + 9 (SIGKILL from the kernel's OOM killer)
iiCompare live memory usage against the limit
kubectl top pods
iiiFix: raise the memory limit and reapply
# In nginx-deployment.yaml, change limits: memory: "128Mi" to a higher value.
# Then apply the edited manifest:
kubectl apply -f nginx-deployment.yaml

Setting limits too low causes OOM kills; setting them too high wastes node capacity and can prevent other Pods from being scheduled.

Symptom: Pod shows CreateContainerConfigError status. The container never starts.

Step 6: Cleanup

Why Cleanup Matters

Cleaning up after a lab is not just housekeeping, it teaches you how Kubernetes object deletion works and why resource accounting matters. In a shared cluster, leaving unused Deployments and Services running wastes node CPU and memory, occupies port ranges (a second Service cannot use nodePort 30080 if it is already taken), and clutters your namespace making it harder to read the current state.

When you delete a Deployment, Kubernetes cascades the deletion:

  1. The Deployment is marked for deletion.
  2. The Deployment controller deletes the ReplicaSet(s) it owns.
  3. The ReplicaSet controller deletes all Pods it owns.
  4. Each Pod's containers receive SIGTERM, wait for terminationGracePeriodSeconds (default 30s), then receive SIGKILL if still running.
  5. kube-proxy removes iptables rules for the deleted Pods.

The Service is a separate object and must be deleted separately, deleting the Deployment does not delete the Service.

Delete the Resources

These commands remove the Deployment and Service and then confirm nothing is left behind.

iDelete both resources in one command (order does not matter)
kubectl delete -f nginx-service.yaml -f nginx-deployment.yaml

deployment.apps "nginx-deployment" deleted
iiConfirm the Deployment is gone
kubectl get deployments
kubectl get replicasets
kubectl get pods -l app=web
kubectl get service nginx-service
# The last command should return:
# Error from server (NotFound): services "nginx-service" not found
# That error message is the expected outcome, it confirms the Service is deleted.

Alternative cleanup with label selectors: if you have many files in a lab directory, you can delete all resources with a specific label: kubectl delete all -l app=web. The all pseudo-resource covers Deployments, ReplicaSets, Pods, Services, and a few other types. Note that ConfigMaps, Secrets, and PersistentVolumeClaims are not included in all and must be deleted explicitly.

5. Lab 2: Rolling Updates and Rollbacks

What we are doing: Re-deploying an nginx Deployment with an explicit update strategy, rolling out a new image version while watching the replacement sequence live, deliberately breaking an image to observe safe failure, rolling back, and exploring declarative update patterns.

Real-world mapping: Rolling updates are the bread-and-butter of daily Kubernetes operations. Every time your CI/CD pipeline pushes a new Docker image, Kubernetes uses this mechanism to swap in the new version pod-by-pod, keeping your service available throughout.

Introduction: What are Rolling Updates?

A rolling update is Kubernetes' default strategy for changing a running Deployment. Instead of stopping all pods and starting new ones (which causes downtime), it gradually replaces old pods with new ones while ensuring a minimum number of pods stay available at all times. This gives you zero-downtime deployments by default.

The alternative, the Recreate strategy, kills every old pod before starting any new ones. This means a gap in service availability. It is appropriate only when your application cannot run two versions simultaneously (for example, a database schema migration that is not backward-compatible).

Update Strategy Comparison

The diagram below contrasts how the Recreate and RollingUpdate strategies replace pods over time.

Understanding maxSurge and maxUnavailable

These two parameters control the speed and safety of rolling updates. They can be set as an integer (absolute pod count) or a percentage of the desired replica count.

Percentage values are always rounded in the direction that is safer:
  • maxUnavailable percentages round down: fewer pods may be unavailable, ensuring more capacity stays up.
  • maxSurge percentages round up: more temporary pods are allowed, avoiding a situation where zero new pods can be created.

Take a Deployment with 4 replicas and both values left at their 25% default:

  1. maxUnavailable: 25% rounds down to 1: at most 1 pod may be unavailable at any time, so you always have at least 3 pods serving traffic.
  2. maxSurge: 25% rounds up to 1: at most 1 extra pod may exist above the desired 4, so the maximum total is 5 pods during the update.
  3. At default settings (maxUnavailable: 25%, maxSurge: 25%), a 4-replica update proceeds one pod at a time, cycling through: create new, wait for ready, delete old, repeat.
Setting maxUnavailable: 0 and maxSurge: 1 gives you the safest possible rolling update: never reduce capacity below desired, but allow one extra pod at a time. This is ideal for production. The trade-off is a slower update since you must wait for each new pod to pass its readiness probe before deleting an old one.

How Kubernetes Implements Updates: ReplicaSets Under the Hood

Every Deployment manages one or more ReplicaSets. When you trigger an update:

  1. Kubernetes creates a new ReplicaSet with the new pod template (new image, new env vars, etc.).
  2. It begins scaling up the new ReplicaSet and simultaneously scaling down the old ReplicaSet, respecting maxSurge and maxUnavailable.
  3. The old ReplicaSet is never deleted: it is kept with 0 replicas as a rollback target. By default the last 10 revisions are retained (controlled by revisionHistoryLimit).
  4. Each distinct revision is a separate ReplicaSet. kubectl rollout undo simply scales the old RS back up and the current one back down.
kubectl get replicasets -l app=nginx-deployment
# Output:
# NAME                          DESIRED   CURRENT   READY   AGE
# nginx-deployment-6d4b9d6f9c   4         4         4       10m   <-- current (v2)
# nginx-deployment-7c8b9f4d1a   0         0         0        5m   <-- old (v1), kept for rollback

Readiness Probes Make Rolling Updates Safe

A rolling update is only as safe as the readiness probe. Kubernetes considers a pod "available" and ready to receive traffic only when its readiness probe passes. Without a readiness probe, Kubernetes starts routing traffic to the new pod the moment the container process starts, even before the application has finished initializing.

If you do not configure a readiness probe, Kubernetes assumes the pod is ready as soon as the container starts. A new pod running a slow-starting application (for example, a Spring Boot app that takes 20 seconds to start) will receive traffic while still initializing, causing errors. Lab 5 covers readiness probes in full detail: treat it as a required companion to this lab.

Step 0: Deploy with an Explicit Strategy Block

Create the file nginx-deployment.yaml with a fully annotated strategy block:

apiVersion: apps/v1           # The API group: apps, version v1
kind: Deployment              # Resource type
metadata:
  name: nginx-deployment      # Unique name within the namespace
  namespace: default          # Target namespace
  labels:
    app: nginx-deployment     # Labels on the Deployment object itself (not the pods)
  annotations:
    # Change-cause is stored in rollout history for audit purposes.
    # Populated by --record flag (deprecated) or set manually here.
    kubernetes.io/change-cause: "Initial deploy: nginx 1.26-alpine"
spec:
  replicas: 4                 # Desired number of pod replicas
  revisionHistoryLimit: 5     # Keep last 5 ReplicaSets for rollback (default: 10)

  selector:
    matchLabels:
      app: nginx              # Deployment manages pods that have this label

  strategy:
    type: RollingUpdate       # Other option: Recreate (causes downtime)
    rollingUpdate:
      maxUnavailable: 1       # At most 1 pod may be unavailable during update.
                              # Can also be a percentage: "25%"
                              # 25% of 4 = 1.0, rounds DOWN to 1.
      maxSurge: 1             # At most 1 extra pod above desired (4+1=5 max).
                              # Can also be a percentage: "25%"
                              # 25% of 4 = 1.0, rounds UP to 1.

  minReadySeconds: 10         # A new pod must stay Ready for 10s before
                              # the next old pod is terminated. Extra safety buffer.

  template:                   # Pod template - defines the pods this Deployment creates
    metadata:
      labels:
        app: nginx            # MUST match selector.matchLabels above
    spec:
      containers:
      - name: nginx           # Container name (used in kubectl set image and logs)
        image: nginx:1.26-alpine  # Image and tag to run
        ports:
        - containerPort: 80   # Port the container listens on (informational)
        resources:
          requests:
            cpu: "100m"       # 0.1 CPU cores - used by scheduler for placement
            memory: "64Mi"    # 64 MiB RAM minimum request
          limits:
            cpu: "200m"       # Hard limit: container cannot use more than 0.2 cores
            memory: "128Mi"   # OOMKilled if it exceeds this
        readinessProbe:       # Determines when pod is READY to receive traffic
          httpGet:
            path: /           # HTTP GET / on port 80
            port: 80
          initialDelaySeconds: 5   # Wait 5s after container start before first probe
          periodSeconds: 5         # Run probe every 5 seconds
          failureThreshold: 3      # Remove from endpoints after 3 consecutive failures

Step 3: Declarative Updates (Preferred in Production)

The kubectl set image command is imperative: it modifies the running object. In production, you should prefer the declarative approach: edit the YAML file and apply it. This keeps your source of truth (the YAML file) synchronized with the cluster state.

iEdit the manifest, then apply only the diff
# Edit nginx-deployment.yaml first:
#   - Change image: nginx:1.26-alpine  TO  image: nginx:1.27-alpine
#   - Update the change-cause annotation to describe the change
kubectl apply -f nginx-deployment.yaml

# kubectl apply performs a three-way merge:
#   1. Your new YAML (desired state)
#   2. The last-applied configuration (stored as annotation)
#   3. The live object in the cluster
# Only the differences are patched.
iiWatch the declarative rollout finish
kubectl rollout status deployment/nginx-deployment
If you mix imperative (kubectl set image) and declarative (kubectl apply) approaches, your YAML file and cluster state will diverge. The next kubectl apply may unexpectedly revert the imperative change. Choose one approach per Deployment and stick to it. In GitOps pipelines, always use declarative apply.

minReadySeconds: Extra Safety Buffer

The minReadySeconds field in the Deployment spec adds an extra wait after a pod's readiness probe first passes before Kubernetes considers the pod "available" and moves on to the next replacement. This catches cases where an app reports ready too early (for example, before its background cache is warm) then crashes shortly after.

Beyond Rolling Updates: Canary and Blue-Green Patterns

Rolling updates handle the common case. For more control, teams use advanced patterns:

Key Takeaways

  1. A RollingUpdate replaces Pods a few at a time so the Service stays up. Kubernetes starts new Pods, waits for them to report Ready, and only then terminates old ones, which is why the rollout you watched never dropped below serving capacity.
  2. maxUnavailable sets the floor and maxSurge sets the ceiling. maxUnavailable rounds down and maxSurge rounds up, so the pair decides how fast the rollout moves and how much extra capacity it borrows while it moves.
  3. A rollout is two ReplicaSets, not one set that changes. The old ReplicaSet scales down as the new one scales up, and Kubernetes keeps the old one at zero replicas so that kubectl rollout undo has something to scale back up.
  4. A broken image cannot take a running application down. You pointed the Deployment at nginx:99.99-does-not-exist and the new Pods stalled in ImagePullBackOff while the old Pods kept serving, because a Pod that never becomes Ready never joins the Service.
  5. Readiness probes are what make any of this safe. Without one, Kubernetes counts a container as ready the moment it starts and sends traffic to a process that is not listening yet, so Lab 5 completes what this lab began.

6. Lab 3: ConfigMaps and Secrets

What we are doing: Creating ConfigMaps and Secrets using all three methods (literals, files, YAML), then consuming them inside pods via four different injection patterns: individual env vars, bulk env var injection, volume-mounted files, and command-line argument substitution.

Real-world mapping: Configuration separation is the difference between an image you can promote through environments unchanged and one that has environment-specific values baked into it. Proper secret handling is a foundational security requirement for any production workload.

Why Hardcoding Configuration in Images is Wrong

Consider what happens if you bake your database password and environment name into your Docker image:

  1. You cannot promote the same image. Your CI builds a new image for each environment (dev, staging, prod), even though only the configuration differs. You test a different artifact than the one you deploy. This violates the principle of immutable build artifacts.
  2. Secrets end up in your registry. Anyone with pull access to the image can run docker inspect or examine the filesystem layers to extract credentials.
  3. Config drift becomes unmanageable. When you need to change a value, you must rebuild and redeploy the image rather than just updating a ConfigMap or Secret.

The 12-Factor App methodology (factor III) states plainly: "Store config in the environment." Kubernetes ConfigMaps and Secrets are the Kubernetes-native implementation of this principle.

ConfigMap vs Secret: Structural Comparison

ConfigMaps and Secrets are structurally almost identical Kubernetes objects. The differences are:

  1. Storage encoding: ConfigMap values are stored as plain UTF-8 strings. Secret values are stored base64-encoded in etcd.
  2. Access restrictions: Kubernetes can be configured to restrict RBAC access to Secrets more tightly than ConfigMaps.
  3. In-memory delivery: When mounted as volumes, Secrets are served from an in-memory tmpfs, not written to the node's disk.
  4. Environment signal: Using the Secret kind communicates to operators that this data is sensitive, enabling tooling (audit logging, policy engines) to enforce stricter controls.
Critical security reality: base64 is encoding, not encryption. Anyone who can run kubectl get secret can instantly decode the value: 
kubectl get secret my-secret -o jsonpath='{.data.MY_KEY}' | base64 -d
Base64 offers zero security. Kubernetes Secrets are only as secure as your cluster's:
  1. Encryption at rest: the API server must be configured with an EncryptionConfiguration that uses AES-GCM or a KMS provider. Without this, Secrets are stored as plaintext base64 in etcd.
  2. RBAC: restrict who can get/list/watch Secret objects. Being able to list secrets is equivalent to reading them all.
  3. Audit logging: Secret reads should be logged so you know if credentials have been accessed unexpectedly.
For production systems, prefer an Operator: a controller a third party ships alongside a custom resource type, which reconciles that resource the way built-in controllers reconcile Pods. The External Secrets Operator pulls values from AWS Secrets Manager, HashiCorp Vault, or GCP Secret Manager into Kubernetes Secrets on demand, and Sealed Secrets instead keeps an encrypted copy in Git that a cluster controller decrypts at apply time. These tools are covered in Section 3.

How Injection Works Under the Hood

The same ConfigMap or Secret can reach a container in two fundamentally different ways, and the difference explains the update behavior you will see later in this lab. Understanding the mechanism removes the mystery from "why did my env var not change?"

When the kubelet on a node starts a pod, it reads the pod spec and resolves every configMapKeyRef, secretKeyRef, envFrom, and volume reference by querying the API server for the named objects. What happens next depends on how the data is consumed:

  1. As environment variables: the kubelet reads the ConfigMap/Secret once, sets the resulting variables in the container's process environment, and then starts the container. A process's environment is fixed at exec time and cannot be changed from outside, so these values are frozen for the life of the container. If the ConfigMap changes afterwards, the running container keeps the old values until it is recreated. This is why a kubectl rollout restart is required to pick up env-var changes.
  2. As mounted volumes: the kubelet writes the data into a projected volume backed by a per-pod directory on the node, then bind-mounts it into the container. A background loop in the kubelet periodically re-syncs this directory against the current ConfigMap/Secret in the API server. When a value changes, the kubelet atomically swaps the directory contents (using a symlink flip, so the application never sees a half-written file), and the new content appears inside the container without a restart. The refresh is not instant: it is bounded by the kubelet's sync period plus its cache propagation delay, which in practice is up to roughly one to two minutes.

Two things follow from how the mount works. First, your application has to re-read the file to see a change. Kubernetes updates the file on disk; it cannot make your process notice. Many servers expose a reload signal for exactly this (nginx -s reload). Second, mounted Secrets are written to an in-memory tmpfs, never the node's disk, so they do not survive a reboot on disk and are unlikely to end up in disk-level backups.

A subtlety that surprises people: subPath volume mounts do not receive automatic updates. When you mount a single key with subPath (to place one file alongside others in an existing directory), the kubelet copies the file once at start and never refreshes it. If you need live updates, mount the whole volume at a dedicated directory instead of using subPath.

Size Limits and Design Constraints

ConfigMaps and Secrets are stored as ordinary objects in etcd, the cluster's key-value store, and they inherit etcd's constraints. Treating them as small configuration carriers rather than general-purpose storage keeps your cluster healthy.

  1. 1 MiB hard size limit. A single ConfigMap or Secret cannot exceed 1 MiB, because that is etcd's per-object ceiling. This rules out shipping large files (TLS bundles with long chains, big seed datasets, binaries) as ConfigMaps. For large data, use a volume, an init container that downloads it, or an artifact store.
  2. Namespace-scoped. A ConfigMap or Secret lives in exactly one namespace and can only be consumed by pods in the same namespace. There is no cross-namespace reference. To share config across namespaces you must duplicate it (or use a tool that syncs copies).
  3. Not a database. Every pod that mounts or env-references a ConfigMap/Secret causes the kubelet to watch it. Thousands of frequently-changing ConfigMaps create real API-server and etcd load. Config should change on the order of deployments, not requests.
  4. No built-in versioning. Updating a ConfigMap overwrites it in place; there is no history and no automatic rollback. This is why config tied to a specific image version is often made immutable and given a version-suffixed name (for example app-config-v3), so a rollback to an old Deployment also references the matching old config.

Securing Secrets in Production

As the danger callout above stressed, base64 is encoding, not encryption. A Secret object provides organizational separation of sensitive data, but on its own it provides almost no confidentiality. Production-grade secret handling layers several controls on top.

  1. Encryption at rest. By default, Secrets are stored in etcd as plaintext base64. The API server can be configured with an EncryptionConfiguration so that Secret data is encrypted before it is written to etcd, using either a locally-held AES-GCM key or, better, an external KMS provider (AWS KMS, GCP KMS, Azure Key Vault) so the encryption key never lives on the cluster. Without this, anyone who can read the etcd data files or take an etcd backup can read every Secret.
  2. Least-privilege RBAC. Treat the ability to get, list, or watch Secrets as equivalent to reading their contents. In particular, list on Secrets returns their data, so it is just as sensitive as get. Grant these verbs narrowly, scope Roles to specific namespaces, and avoid wildcard resources: ["*"] rules.
  3. Audit logging. Configure the API server audit policy to record reads of Secret objects. If credentials are ever leaked, the audit log is how you determine what was accessed and when.
  4. External secret managers. The strongest pattern keeps the source of truth outside the cluster entirely. The External Secrets Operator syncs values from AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager, or Azure Key Vault into Kubernetes Secrets on demand. Sealed Secrets takes the opposite approach: it encrypts a Secret so the ciphertext is safe to commit to Git, and a controller in the cluster decrypts it at apply time. Both keep plaintext secrets out of your manifests and version control.
Never commit a plaintext Secret manifest (with real data or stringData values) to a Git repository. Git history is effectively permanent, so a secret committed once is compromised even if you delete it in a later commit. Use Sealed Secrets, the External Secrets Operator, or a CI-injected value instead, and rotate any credential that has ever been committed in plaintext.

Creating Secrets

stringData vs data: Which to Use

Secrets have two data fields:

  1. data: values must be base64-encoded by you before putting them in the YAML.
  2. stringData: values are plain text; Kubernetes base64-encodes them automatically on write. stringData is write-only: it never appears in the stored object (use data to read back).
The trailing newline bug: when encoding values for the data field, always use echo -n (no trailing newline). Without -n, the newline character becomes part of the base64-encoded value, and your application will receive the password with a \n appended, causing authentication failures that are very hard to diagnose. 
# WRONG - includes trailing newline in the encoded value
echo "mysecretpassword" | base64
# bXlzZWNyZXRwYXNzd29yZAo=   <-- the 'o=' at end encodes the newline

# CORRECT - no trailing newline
echo -n "mysecretpassword" | base64
# bXlzZWNyZXRwYXNzd29yZA==

The Secret below carries three sensitive values in stringData, so Kubernetes does the base64 encoding for you. Save it as app-secret.yaml:

  namespace: default     # Must match consuming pod's namespace

    app: demo-app
type: Opaque             # Generic secret type (arbitrary key-value pairs).
                         # Other types: kubernetes.io/tls (TLS certs),
                         #   kubernetes.io/dockerconfigjson (registry creds)

  DB_PASSWORD: "SuperSecurePassword123"   # Database password
  API_KEY: "sk-abcdef1234567890"          # External API key
  REDIS_URL: "redis://redis-service:6379" # Connection string with sensitive host

Four Consumption Methods

Method 1: Individual Environment Variables

Best for: injecting specific keys as env vars when you want explicit control over env var names.

The Pod below takes one key from the ConfigMap and one from the Secret, naming each variable itself:

apiVersion: v1
kind: Pod
metadata:
  name: env-individual-pod
spec:
  containers:
  - name: app
    image: alpine:3.20
    command: ["sh", "-c", "echo APP_ENV=$APP_ENV DB_PASS=$DB_PASS && sleep 3600"]
    env:
    - name: APP_ENV              # Name of the env var inside the container
      valueFrom:
        configMapKeyRef:
          name: app-config       # Name of the ConfigMap object
          key: APP_ENV           # Key within the ConfigMap's data section
          optional: false        # Default false: pod fails if ConfigMap/key missing
    - name: DB_PASS              # Env var name can differ from the secret key name
      valueFrom:
        secretKeyRef:
          name: app-secret       # Name of the Secret object
          key: DB_PASSWORD       # Key within the Secret's data section
          optional: false        # Pod will not start if secret is missing

Method 2: All Keys as Environment Variables (envFrom)

Best for: injecting many keys at once. Every key in the ConfigMap or Secret becomes an env var with the same name.

With envFrom, all keys are injected. If a key name is not a valid environment variable identifier (contains dashes, starts with a digit, etc.), it will be silently skipped. If the ConfigMap and Secret have a key with the same name, the Secret's value wins (the one listed later in envFrom overrides earlier ones). Always audit key names to avoid hidden conflicts.

The Pod below pulls every key from both objects in two envFrom entries. Save it as env-bulk-pod.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: env-bulk-pod
spec:
  containers:
  - name: app
    image: alpine:3.20
    command: ["sh", "-c", "env | sort && sleep 3600"]
    envFrom:
    - configMapRef:
        name: app-config         # Injects ALL keys from app-config as env vars
        optional: false          # Fail if ConfigMap not found
    - secretRef:
        name: app-secret         # Injects ALL keys from app-secret as env vars
        optional: false          # Fail if Secret not found
    # Result: APP_ENV, LOG_LEVEL, MAX_CONNECTIONS, DB_PASSWORD, API_KEY, REDIS_URL
    # are all available as environment variables

Method 3: Volume-Mounted Files

Best for: configuration files (nginx.conf, application.properties), or when the application reads from files rather than env vars. Each key in the ConfigMap becomes a separate file in the mounted directory. The filename is the key name; the file content is the value.

The Pod below mounts the ConfigMap and the Secret as two separate read-only directories. Save it as volume-mount-pod.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: volume-mount-pod
spec:
  volumes:
  - name: config-volume          # Volume name (referenced in volumeMounts below)
    configMap:
      name: app-config           # Which ConfigMap to project as files
      # Optional: only mount specific keys (omit to mount all keys)
      items:
      - key: nginx.conf          # Key in the ConfigMap
        path: nginx.conf         # Filename in the mounted directory
      - key: LOG_LEVEL
        path: log-level.txt      # Key name and path can differ

  - name: secret-volume          # Separate volume for secrets
    secret:
      secretName: app-secret     # Which Secret to project as files
      defaultMode: 0400          # File permissions: owner read-only (octal)
      # In production: 0400 prevents other processes from reading credentials

  containers:
  - name: app
    image: alpine:3.20
    command: ["sh", "-c", "ls /etc/config && cat /etc/config/nginx.conf && sleep 3600"]
    volumeMounts:
    - name: config-volume        # Must match volumes[].name above
      mountPath: /etc/config     # Directory where files appear inside container
      readOnly: true             # Best practice: config should not be modified by app

    - name: secret-volume
      mountPath: /etc/secrets    # Separate directory for secret files
      readOnly: true             # Always read-only for secrets

Method 4: Command-Line Arguments via Env Var Substitution

Best for: applications that accept configuration only via command-line flags, not environment variables.

The Pod below injects two values as environment variables, then expands them into the container's args with Kubernetes $(VAR_NAME) substitution:

apiVersion: v1
kind: Pod
metadata:
  name: args-pod
spec:
  containers:
  - name: app
    image: alpine:3.20
    env:
    - name: LOG_LEVEL            # First inject env var from ConfigMap
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: LOG_LEVEL
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: app-secret
          key: DB_PASSWORD
    # Then reference env vars in args using $(VAR_NAME) syntax
    # Note: this is Kubernetes variable substitution, not shell substitution
    command: ["/app/server"]
    args:
    - "--log-level=$(LOG_LEVEL)"       # Expanded by Kubernetes before container starts

Update Behavior: A Critical Difference

What happens when you edit a ConfigMap or Secret depends entirely on how the Pod consumes it. The two callouts below cover each case.

Environment variables do not auto-update A value injected from a ConfigMap or Secret as an environment variable is read once, at container start time, and then frozen. Changing the ConfigMap afterwards has no effect on a running Pod. To pick up the new value you must restart the Pods: 
kubectl rollout restart deployment/your-deployment
Volume-mounted files do auto-update A ConfigMap or Secret mounted as a volume is refreshed in place, with a delay of roughly 2 minutes (controlled by the kubelet's syncFrequency and configMapAndSecretChangeDetectionStrategy settings). Your application still has to re-read the file to see the new value, so this suits configuration that can be reloaded without a restart. nginx, for example, picks up a changed config with nginx -s reload.

Key Takeaways

  1. Configuration belongs outside the image. An image with values baked in cannot be promoted from staging to production unchanged, and any credential inside it is readable by everyone who can pull that image.
  2. A Secret is a ConfigMap with base64 and stricter handling, not encryption. Anyone who can read the Secret can decode it in one command, so a Secret is only private once you add encryption at rest, tight RBAC, or an external secret manager.

7. Lab 4: Persistent Volumes and Data Survival

What we are doing: Creating a PersistentVolumeClaim, mounting it into a pod, writing data, destroying the pod, recreating it against the same PVC, and proving the data survived. Then contrasting with emptyDir to show ephemeral behavior.

Real-world mapping: Every stateful workload (PostgreSQL, Redis, Elasticsearch, Kafka) needs persistent storage. Understanding the PV/PVC/StorageClass model is essential before you can run databases on Kubernetes.

The Core Problem: Containers are Ephemeral

A container's writable layer is temporary. When a container exits (whether normally, due to a crash, or because the pod was deleted), all data written inside the container's filesystem is permanently lost. The next time the container starts, it gets a fresh copy of the image's filesystem.

This is actually a feature for stateless applications: every start is clean. But for a database, this is catastrophic. You need storage that exists independently of any individual container and that can be re-attached when the pod is recreated, possibly on a different node.

kubectl describe storageclass standard
Static vs Dynamic Provisioning:
  • Static provisioning: A cluster admin manually creates PersistentVolume objects representing pre-existing storage (NFS shares, existing EBS volumes). Developers then create PVCs that match the pre-created PVs. Used when storage must be pre-allocated or managed externally.
  • Dynamic provisioning: The developer creates a PVC referencing a StorageClass. The StorageClass provisioner automatically creates a new PV (and the underlying storage, for example a new EBS volume) to satisfy the claim. This is the standard approach in cloud environments and is what Minikube does.

Access Modes Explained

Access modes define how a volume can be mounted. They are a constraint between the storage backend and the PVC request:

  1. ReadWriteOnce (RWO): The volume can be mounted read-write by a single node at a time. Multiple pods on the same node can share it. Most block storage (AWS EBS, GCP Persistent Disk, Azure Disk) only supports RWO. This is the most common mode.
  2. ReadOnlyMany (ROX): The volume can be mounted read-only by many nodes simultaneously. Useful for distributing static content or configuration files.
  3. ReadWriteMany (RWX): The volume can be mounted read-write by many nodes simultaneously. Requires a shared filesystem: NFS, CephFS, AWS EFS (NFS-based), GCP Filestore. Standard block storage does NOT support RWX.
  4. ReadWriteOncePod (RWOP): The volume can be mounted read-write by exactly one pod (stronger than RWO which is per-node). Requires Kubernetes 1.22+ and a CSI driver that supports it.
A common mistake is requesting ReadWriteMany for a standard block storage volume (EBS, GCP PD). These storage backends physically cannot be attached to multiple nodes simultaneously. The PVC will remain in Pending state with an error like "no persistent volumes available for this claim" because no PV can satisfy the RWX access mode with a block storage backend.

Reclaim Policies

The reclaim policy determines what happens to a PV when the PVC that bound to it is deleted:

  1. Delete: The PV object and the underlying storage (the EBS volume, the GCP PD) are deleted. This is the default for dynamically provisioned volumes. Data is permanently lost. Use with caution in production.
  2. Retain: The PV object is kept and the underlying storage is preserved, but the PV enters a Released state and cannot be rebound automatically. An admin must manually recover or delete the PV. Use for databases where data loss is catastrophic.
  3. Recycle (deprecated): Performs a simple rm -rf on the volume and makes it available again. Deprecated in favor of dynamic provisioning. Do not use in new deployments.

Common Volume Types

  1. emptyDir: Created when the pod is assigned to a node, deleted when the pod is removed. Lives in the node's memory or disk (configurable via medium: Memory for RAM-backed storage). Shared between all containers in the same pod. Use for temporary scratch space, shared caches between sidecar containers.
  2. hostPath: Mounts a directory from the node's filesystem into the pod. Data survives pod deletion (until the node is reprovisioned). Security risk: a pod with a hostPath mount can potentially access any file on the node, including system files. Avoid in production; used internally by system components like metrics-server.
  3. persistentVolumeClaim: The standard durable storage option. Mounts a PVC-backed PV into the pod. Data survives pod deletion and can follow the pod to another node (cloud storage is network-attached).

Beyond this Lab: Volume Snapshots

Persistent volumes keep your data alive across Pod restarts, but they do not protect you from accidental deletion or corruption. For point-in-time backups, Kubernetes provides the VolumeSnapshot API, a CSI-driver feature for capturing the state of a PersistentVolumeClaim and restoring from it later.

  1. VolumeSnapshotClass: like a StorageClass, but for snapshots. It names the CSI driver that takes the snapshot and its deletion policy. A cluster admin creates one per backend.
  2. VolumeSnapshot: a request to snapshot a specific PVC at this moment. The CSI driver creates the underlying snapshot and binds it to a VolumeSnapshotContent object.
  3. Restore: create a new PVC whose spec.dataSource points at the VolumeSnapshot. Kubernetes provisions a fresh volume pre-populated with the snapshot's data.
Snapshots need CSI driver support. VolumeSnapshots only work when the cluster's CSI driver implements the snapshot capability. Minikube's default hostpath driver does not, so this is a concept to know rather than run here; on a cloud provider (EBS, GCP PD, Azure Disk CSI) it works out of the box. Note that a snapshot is crash-consistent storage state, not an application-consistent backup, so quiesce the application (or use a backup tool like Velero) for databases.

Key Takeaways

  1. A container filesystem dies with the container; a PersistentVolume does not. You deleted storage-pod, recreated it against the same claim, and the file you had written was still there.
  2. The chain is StorageClass, then PersistentVolume, then PersistentVolumeClaim, then mount. The StorageClass is the template a provisioner uses, the PV is the real storage it creates, the PVC is the request that binds to it, and the Pod mounts the PVC by name.
  3. An access mode describes the storage, not your preference. RWO attaches to one node, RWX needs a shared filesystem such as NFS, CephFS, or EFS, and asking a block-storage class for RWX leaves the PVC Pending indefinitely.
  4. The reclaim policy decides whether the data outlives the claim. Delete destroys the volume along with the PVC and suits development, while Retain keeps the volume and hands you the cleanup.
  5. emptyDir is scratch space, not storage. It lives exactly as long as the Pod and is shared by every container in it, which the contrast exercise proved by deleting the Pod and finding the file gone.

8. Lab 5: Health Probes and Autoscaling (HPA)

What we are doing: Configuring all three probe types (startup, liveness, readiness) with annotated YAML, observing pod removal from Service endpoints when readiness fails, enabling metrics-server, deploying an HPA, generating load, and watching the cluster auto-scale.

Real-world mapping: Health probes are the foundation of reliable Kubernetes deployments. Without them, Kubernetes cannot distinguish a running container from a healthy one. HPA is the primary tool for handling traffic spikes without manual intervention.

Why Probes Exist

The container runtime can tell Kubernetes that a container's process has started. It cannot tell Kubernetes whether the application inside is actually healthy or ready. Consider:

  1. A Java application where the JVM starts in 1 second but the Spring context takes 30 seconds to initialize.
  2. A web server that started successfully but is now deadlocked waiting for a database connection that will never come.
  3. A service that is temporarily overwhelmed and returning 503 errors but has not crashed.

Without probes, Kubernetes handles all three cases the same way: the container is "running," so traffic is sent to it and it is not restarted. With probes, Kubernetes can detect and respond to each condition automatically.

The Three Probe Types

Liveness Probe: Is the Container Alive?

A liveness probe failure causes Kubernetes to restart the container. Use liveness probes to recover from states where the application is stuck and cannot self-recover, such as:

  1. Deadlock: threads are blocked waiting for each other, the process is running but making no progress.
  2. Corrupted in-memory state: the app is running but producing incorrect results.
  3. Resource exhaustion: leaked memory or file descriptors that will never be released without a restart.
Never check external dependencies in a liveness probe. If your liveness probe checks the database and the database goes down, ALL your pods will restart simultaneously. You lose your entire service at the moment the database is already having problems. Liveness probes should only check the health of the application process itself (for example: can I serve an HTTP /healthz endpoint from in-process memory?).

Readiness Probe: Is the Container Ready for Traffic?

A readiness probe failure causes Kubernetes to remove the pod from Service endpoints. Traffic stops being sent to the pod. The container is NOT restarted. When the probe passes again, the pod is re-added to endpoints automatically. Use readiness probes for:

  1. Startup warmup: application is running but loading caches or establishing connections.
  2. Temporary overload: application is momentarily unable to handle more requests.
  3. Dependency checks: it is safe to check the database in a readiness probe because failure means "stop sending me traffic," not "restart me."
  4. Rolling updates (critical): a pod must pass its readiness probe before the rolling update proceeds to replace the next old pod.

Startup Probe: Give Slow-Starting Apps Time

A startup probe disables liveness and readiness probes until the startup probe first succeeds. This solves the slow-starting application problem: without a startup probe, you must set initialDelaySeconds high enough for the slowest possible startup, which means liveness probes are also delayed that long on every subsequent check.

With a startup probe: set failureThreshold * periodSeconds to the maximum allowed startup time. Once the startup probe passes once, liveness and readiness probes take over with their normal shorter intervals.

Three Probe Mechanisms

  1. httpGet: Kubernetes sends an HTTP GET to the specified path and port. Any 2xx or 3xx response is a success. 4xx and 5xx are failures. Most common for web applications. Does not require any changes to the application.
  2. tcpSocket: Kubernetes tries to open a TCP connection to the specified port. Success means the port is accepting connections. Use for databases, message queues, or any TCP service that does not speak HTTP.
  3. exec: Kubernetes runs a command inside the container. Exit code 0 is success; any other exit code is failure. Use when you need custom logic that cannot be expressed as an HTTP endpoint or TCP check (for example: check if a lock file exists, run a health check script).

Critical Probe Parameters

The annotated reference below explains every probe tuning parameter and the trade-off each one controls: 

# Full parameter reference - applies to all three probe types
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 15    # Wait 15s after container start before first probe.
                             # Set this to >= your typical startup time.
                             # Too low: restart loop on slow-starting apps.
                             # Too high: slow detection of unhealthy containers.
  periodSeconds: 10          # Run the probe every 10 seconds.
                             # Lower value = faster detection, more API server load.
  timeoutSeconds: 5          # Fail the probe if no response within 5 seconds.
                             # Default is 1s - often too short for loaded services.
                             # Must be less than periodSeconds.
  failureThreshold: 3        # Take action (restart/remove from endpoints) after
                             # 3 consecutive failures. 3 * 10s = 30s to respond.
                             # Lower = faster response but more false positives.
  successThreshold: 1        # Probe must pass 1 consecutive time to be considered
                             # successful (default and minimum for liveness/startup).
                             # Readiness probes can be set higher (e.g., 2) to
                             # require sustained health before re-adding to endpoints.

Common Mistakes

  1. Too-short initialDelaySeconds: if the app takes 20s to start and initialDelaySeconds is 5, the liveness probe fails 3 times before startup is complete, causing a restart loop. The pod never gets past CrashLoopBackOff.
  2. Missing readiness probe during rolling updates: without a readiness probe, traffic is sent to pods the moment their container process starts, before the app is ready. Users see errors during every deployment.
  3. Checking database in liveness probe: database downtime causes all pods to restart simultaneously, making a bad situation worse. A liveness probe should test only the health of the application process itself.
  4. Default timeoutSeconds: 1s: under load, a healthy application might take 2-3 seconds to respond. With a 1s timeout, your pods get spuriously restarted during traffic spikes. Always set timeoutSeconds to at least your application's 99th-percentile response time.

HPA Conceptual Foundation

The Scaling Formula

The HPA controller runs in the kube-controller-manager and queries metrics-server every 15 seconds. When it decides to scale, it uses this formula:

desiredReplicas = ceil(currentReplicas * (currentMetricValue / desiredMetricValue))

Example: 3 replicas, current CPU = 90%, desired = 50%:
  desiredReplicas = ceil(3 * (90 / 50))
                  = ceil(3 * 1.8)
                  = ceil(5.4)
                  = 6 replicas

Example: 6 replicas, current CPU = 10%, desired = 50%:
  desiredReplicas = ceil(6 * (10 / 50))
                  = ceil(6 * 0.2)
                  = ceil(1.2)
                  = 2 replicas   (scales DOWN to 2)
Scale-up is fast (immediate), scale-down is slow (5-minute default stabilization window). This asymmetry is intentional: scaling up quickly absorbs traffic spikes before they cause errors. Scaling down slowly prevents "flapping" where the HPA scales down, load spikes again immediately, and it scales back up repeatedly. The stabilization window can be configured in the HPA spec's behavior field (requires autoscaling/v2).

Why CPU Requests are Mandatory

HPA measures CPU utilization as a percentage of the pod's CPU request, not as a percentage of node capacity. If a pod has no CPU request defined, the HPA has no denominator for its percentage calculation and shows <unknown> for the TARGETS column. The HPA cannot scale a Deployment whose pods have no CPU requests.

Pod uses 80m CPU, CPU request = 200m:
  Utilization = 80m / 200m = 40%   <-- HPA sees 40%, target is 50%, no scaling needed

Pod uses 80m CPU, CPU request = NONE:
  Utilization = 80m / ??? = unknown  <-- HPA cannot compute, shows <unknown>

  name: hpa-demo                         # HPA name (typically matches Deployment name)
  namespace: default

  scaleTargetRef:                        # Which workload to scale
    apiVersion: apps/v1
    kind: Deployment
    name: hpa-demo                       # Must match Deployment metadata.name exactly

  maxReplicas: 10                        # Never scale above 10 replicas.
                                         # Prevents runaway scaling from misconfiguration
                                         # or a traffic spike that would overwhelm nodes.

  - type: Resource                       # "Resource" means CPU or memory (built-in metrics)
    resource:
      name: cpu                          # Scale based on CPU utilization
      target:
        type: Utilization                # "Utilization" = % of CPU request.
                                         # Alternative: AverageValue (e.g., "200m" absolute)
        averageUtilization: 50           # Target: keep average CPU at 50% of requests.
                                         # If average exceeds 50%, scale up.
                                         # If average drops well below 50%, scale down.

    scaleDown:
      stabilizationWindowSeconds: 300    # Wait 300s (5 min) after last scale-up event
                                         # before scaling down. Prevents flapping.
      policies:
      - type: Pods
        value: 1                         # Scale down at most 1 pod per 60 seconds.
        periodSeconds: 60                # This makes scale-down gradual and conservative.
    scaleUp:
      stabilizationWindowSeconds: 0      # No stabilization window on scale-up.
                                         # Scale up immediately when threshold is crossed.
      policies:
      - type: Pods
        value: 4                         # Scale up at most 4 pods per 60 seconds.
        periodSeconds: 60                # Burst scaling for rapid traffic growth.

VPA, KEDA, and Beyond

  1. VPA (Vertical Pod Autoscaler): Instead of adding pods (horizontal), VPA makes existing pods bigger by adjusting their CPU and memory requests. Useful when adding pods does not help (single-threaded apps, tight state). Do NOT run VPA in Auto mode alongside HPA on the same Deployment: they fight over pod sizing and can cause restart loops.
  2. KEDA (Kubernetes Event-Driven Autoscaling): extends HPA to scale based on any external metric: message queue depth (RabbitMQ, Kafka, SQS), HTTP request rate, Prometheus metrics, cron schedules, and more. KEDA can scale to zero (HPA cannot). Essential for event-driven architectures and batch workloads.
  3. Cluster Autoscaler: when HPA wants to add pods but no node has enough capacity, Cluster Autoscaler provisions a new node from the cloud provider. This is the final layer of autoscaling: pod-level (HPA), then node-level (Cluster Autoscaler).
In-place Pod resize changes the vertical-scaling story. Historically, changing a running Pod's CPU or memory requests forced Kubernetes to recreate the Pod (a restart). Recent Kubernetes versions support resizing a Pod's resources in place via the Pod's resize subresource, so a container can be given more CPU or memory without being restarted (subject to the container's resizePolicy). This makes Vertical Pod Autoscaler far less disruptive and is worth checking your cluster version for before assuming every resource change means a rollout.

Key Takeaways

  1. The three probes do three different jobs. A liveness probe restarts a container that is stuck, a readiness probe pulls a Pod out of the Service endpoints while it is warming up or overloaded, and a startup probe holds the other two back until a slow application has finished booting.
  2. Never check an external dependency in a liveness probe. A liveness probe that queries the database turns one database outage into a cluster-wide restart storm, because every replica fails the same check at the same moment.
  3. Readiness is what makes a rolling update zero-downtime. You watched a Pod leave the Endpoints list the moment its readiness probe failed and rejoin once it passed, which is the mechanism Lab 2 depended on.
  4. An HPA needs metrics-server and a CPU request. The HPA reads current CPU as a percentage of the request, so a Pod with no request gives it nothing to divide by and the TARGETS column stays <unknown>.
  5. Scale up is immediate and scale down waits. The default 5-minute stabilization window stops the HPA from removing replicas the instant load dips, which is why your replica count fell well after the load generator stopped.

9. Lab 6: Other Workload Types (StatefulSet, DaemonSet, Job, CronJob)

Kubernetes ships five workload controllers. Section 1 focused on Deployment because it covers the majority of real-world applications. Production clusters also depend on the other four. Each solves a problem that Deployment deliberately does not handle, and picking the wrong controller leads to subtle bugs (data corruption, missed schedules, pods not landing on every node). This lab gives you hands-on experience with all five so you can choose confidently.

Workload Controller Comparison

The table below compares the five controllers on the properties that decide which one a workload needs: pod identity, per-pod storage, and when the pods are expected to stop.

Deployment Stateless apps (web servers, APIs) Random hash suffix Shared or none Forever (restarted on crash)
StatefulSet Databases, queues, anything needing stable identity Stable ordinal (web-0, web-1) Own PVC per pod Forever (restarted on crash)

StatefulSet: Stable Identity and Per-Replica Storage

A StatefulSet is used for workloads that need each pod to have a persistent, stable identity across restarts. The canonical examples are relational databases (PostgreSQL, MySQL), distributed data stores (Cassandra, Elasticsearch), and message brokers (Kafka, RabbitMQ). If you restart a database pod, it must reconnect to its own data volume, not a random shared one. If you have a leader-follower database cluster, the leader must start before the followers can safely connect. StatefulSet handles both requirements natively.

What Stable Pod Identity Means

With a Deployment, a pod named web-abc123-xyz789 might become web-def456-uvw012 after a restart. The hash suffix is random. With a StatefulSet, pods get ordinal names: web-0, web-1, web-2. The ordinal is permanent for the lifetime of that replica. If web-1 crashes and is restarted, it comes back as web-1, not a different name. This predictability allows other systems (and other pods) to address each replica directly.

Headless Services and Per-Pod DNS

The serviceName field in a StatefulSet spec points to a headless Service (a Service with clusterIP: None). This Service does not load-balance traffic. Instead, it creates a stable DNS record for each pod individually, following the pattern: 


<pod-name>.<service-name>.<namespace>.svc.cluster.local

# For a StatefulSet named "web" with serviceName "nginx" in namespace "default":
web-0.nginx.default.svc.cluster.local
web-1.nginx.default.svc.cluster.local

This per-pod DNS is how Cassandra nodes discover each other, how Kafka brokers register with ZooKeeper, and how database replicas find the primary. None of this is possible with a regular Service that resolves to a single virtual IP.

volumeClaimTemplates: One PVC Per Pod

The volumeClaimTemplates field is the storage counterpart to stable pod names. Instead of one PVC shared by all replicas, Kubernetes creates a separate PVC for each pod automatically, named <template-name>-<pod-name>. So for a StatefulSet named web with two replicas and a template named data, you get: data-web-0 and data-web-1. Each pod always mounts its own PVC, and that PVC persists even if the pod is deleted.

Ordered Startup and Termination

StatefulSet enforces a strict ordering rule: web-0 must be in Running and Ready state before web-1 is created. web-1 must be Running and Ready before web-2 is created, and so on. During scale-down and deletion, the order reverses: web-2 is terminated before web-1, and web-1 before web-0.

This ordering is critical for databases. In a leader-follower PostgreSQL cluster, the leader (postgres-0) must be fully available before followers (postgres-1, postgres-2) start attempting replication. During shutdown, followers must stop before the leader so there is no data loss from in-flight replication packets. Because StatefulSet encodes that ordering as a platform guarantee, you do not have to write init-container logic to reproduce it yourself.

When NOT to use StatefulSet: if you are running on a cloud provider (AWS, GCP, Azure), prefer managed databases (RDS, Cloud SQL, Azure Database) over StatefulSets for production databases. Managed databases handle backups, failover, patching, and volume management for you. StatefulSets are best for cases where a managed service does not exist, you need to run on-premises, or you are running a distributed system not offered as a managed product.

Full Annotated StatefulSet YAML

Create the headless Service first, then the StatefulSet. Save both in statefulset.yaml:

# are created for each individual pod (web-0.nginx.default.svc.cluster.local)
apiVersion: v1
kind: Service
metadata:
  name: nginx                       # must match StatefulSet's serviceName field
  labels:
    app: nginx-sts
spec:
  ports:
  - port: 80                        # which port to expose from the pods
    name: web
  clusterIP: None                   # "None" makes this a headless Service (no load balancing)
  selector:
    app: nginx-sts                  # routes DNS to pods with this label
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web                         # pods will be named web-0, web-1, etc.
spec:
  serviceName: "nginx"              # MUST match the headless Service name above
  replicas: 2                       # creates web-0 and web-1 in order
  selector:
    matchLabels:
      app: nginx-sts                # must match pod template labels
  template:
    metadata:
      labels:
        app: nginx-sts              # label applied to every pod in this StatefulSet
    spec:
      terminationGracePeriodSeconds: 10   # how long to wait for graceful shutdown
      containers:
      - name: nginx
        image: nginx:1.27-alpine          # pinned minor version for reproducibility
        ports:
        - containerPort: 80
          name: web
        volumeMounts:
        - name: data                      # matches the volumeClaimTemplates name below
          mountPath: /usr/share/nginx/html  # where nginx serves files from
  volumeClaimTemplates:             # one PVC is created automatically per pod replica
  - metadata:
      name: data                    # PVCs will be named data-web-0, data-web-1
    spec:
      accessModes: ["ReadWriteOnce"]  # one node can mount it read-write (standard for block storage)
      resources:
        requests:
          storage: 1Gi              # how much disk each pod gets

DaemonSet: One Pod Per Node

A DaemonSet guarantees that exactly one copy of a pod runs on every node in the cluster (or a subset of nodes, if you use node selectors). When a new node joins the cluster, the DaemonSet controller automatically schedules the pod on it. When a node leaves, its pod is garbage-collected. You never set a replica count for a DaemonSet because the replica count is always equal to the number of matching nodes.

Use Cases

DaemonSets are the correct choice for any per-node system service:

  1. Log collectors: Fluentd, Fluent Bit, Filebeat. These need to run on every node to tail log files from /var/log and ship them to Elasticsearch, Loki, or a SIEM.
  2. Monitoring agents: Prometheus node-exporter (hardware and OS metrics), Datadog agent, Dynatrace OneAgent. They instrument the node itself, not just a single application.
  3. Network plugins (CNI): Calico, Cilium, Flannel all deploy as DaemonSets because every node needs the CNI agent to handle pod networking.
  4. Security agents: Falco (Lab 17) runs as a DaemonSet to monitor system calls on every node. Trivy operator can also run as a DaemonSet for per-node scanning.

Taints, Tolerations, and Node Selectors

By default a DaemonSet only runs on nodes that are schedulable (not tainted). The built-in system DaemonSets such as kube-proxy use tolerations to also run on control plane nodes, which carry taints that repel ordinary workloads. You can restrict a DaemonSet to a subset of nodes using nodeSelector (simple key-value match) or nodeAffinity (richer expressions). A common example is a GPU workload DaemonSet that only runs on nodes labeled accelerator: nvidia.

Update Strategy

DaemonSet supports two update strategies via spec.updateStrategy.type:

  1. RollingUpdate (default): replaces pods one node at a time. Controlled by maxUnavailable (how many pods can be down during the update).
  2. OnDelete: the new pod is only created when you manually delete the old pod. Useful when you need precise control over which nodes get updated first.

Full Annotated DaemonSet YAML (Fluent Bit Log Collector)

The DaemonSet below runs a Fluent Bit log collector on every node, including the control plane, and mounts the node's log directories read-only. Save it as daemonset-fluentbit.yaml:

  name: fluent-bit                        # name of the DaemonSet resource

  labels:
    k8s-app: fluent-bit-logging
spec:
  selector:
    matchLabels:
      name: fluent-bit                    # must match pod template labels
  updateStrategy:
    type: RollingUpdate                   # update one node at a time (default)
    rollingUpdate:
      maxUnavailable: 1                   # at most 1 pod can be down during update
  template:
    metadata:
      labels:
        name: fluent-bit                  # must match selector above
    spec:
      serviceAccountName: fluent-bit      # needs permissions to read pod metadata from API
      tolerations:
      # Run on control plane nodes too (they have this taint by default)
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: fluent-bit
        image: fluent/fluent-bit:3.1-alpine   # pinned major.minor for stability
        imagePullPolicy: IfNotPresent
        resources:
          limits:
            memory: 200Mi               # keep the agent lightweight
          requests:
            cpu: 100m
            memory: 100Mi
        volumeMounts:
        - name: varlog                  # mount host /var/log so we can read container logs
          mountPath: /var/log
          readOnly: true
        - name: varlibdockercontainers  # the actual container log files on the node
          mountPath: /var/lib/docker/containers
          readOnly: true

Job: Run to Completion

A Job creates pods that are meant to finish. A Deployment restarts a pod whenever it exits; a Job treats exit code 0 as success. Once enough pods have succeeded (set by completions), the Job is marked Complete and starts no more. Use Jobs for database migrations, batch processing, report generation, one-time imports, and anything with a defined end.

Key Job Fields

  1. completions: how many successful pod completions are required before the Job is done. Default is 1. Setting it to 5 means the Job will run pods until 5 of them exit with code 0.
  2. parallelism: how many pods to run simultaneously. Default is 1 (sequential). Setting completions: 10, parallelism: 4 processes the work in parallel batches of 4.
  3. backoffLimit: how many times to retry a failed pod before marking the Job as Failed. Default is 6. Each retry uses exponential back-off (10s, 20s, 40s...).
  4. activeDeadlineSeconds: maximum total wall-clock time the Job is allowed to run. If the Job exceeds this, Kubernetes terminates all pods and marks the Job as Failed regardless of retries remaining.
  5. restartPolicy: must be either Never or OnFailure for Jobs (not Always, which is for long-running workloads). Never means a failed pod is left running so you can inspect its logs, and a new pod is created for the retry. OnFailure means the same pod container is restarted in place.
Prefer restartPolicy: Never for debugging. When a pod fails with Never, the old pod stays around so you can run kubectl logs <failed-pod> to see the error. With OnFailure, the container is restarted in place and the previous log output is lost once the container exits.

Full Annotated Job YAML

The Job below runs one pod that computes digits of pi and then exits. Save it as job-pi.yaml:

kind: Job
metadata:
  name: pi                                # the Job name; also used to find its pods
spec:
  completions: 1                          # we need 1 successful pod to call this Job done
  parallelism: 1                          # only 1 pod runs at a time
  backoffLimit: 3                         # retry up to 3 times before marking failed (overrides default 6)
  activeDeadlineSeconds: 120              # kill the entire Job if it runs longer than 2 minutes
  template:
    spec:

        image: perl:5.40-slim             # pinned slim variant to reduce attack surface

        - perl
        - "-Mbignum=bpi"                  # load the bignum bpi module
        - "-wle"                          # print line to stdout and exit
        - "print bpi(2000)"               # compute pi to 2000 decimal places
        resources:
          requests:
            cpu: 200m
            memory: 64Mi
          limits:
            memory: 128Mi

CronJob: Scheduled Jobs

A CronJob is a controller that creates a new Job on a repeating schedule defined in standard Unix cron syntax. Every time the CronJob fires, it spawns a Job, which in turn spawns pods. The CronJob itself is just a schedule wrapper: all the actual execution logic lives in the Job template inside it.

Cron Schedule Syntax

The schedule field uses five space-separated fields:

The table below lists the schedules you are most likely to write:

Schedule Meaning
*/5 * * * *Every 5 minutes
0 2 * * *Every day at 2:00 AM
0 0 * * 0Every Sunday at midnight
0 9 * * 1-59:00 AM on weekdays only
@hourlyShorthand for 0 * * * * (supported by Kubernetes)

Important CronJob Fields

  1. successfulJobsHistoryLimit: how many completed (successful) Jobs to keep around for inspection. Default is 3. Older Jobs are automatically deleted. Set to 0 to delete immediately after success.
  2. failedJobsHistoryLimit: how many failed Jobs to keep for debugging. Default is 1. Failed Jobs are valuable for troubleshooting, so you usually want to keep at least a few.
  3. concurrencyPolicy: what to do if a new Job fires while a previous run is still going:
    1. Allow (default): multiple Jobs can run simultaneously. Fine for independent tasks.
    2. Forbid: skip the new run if the previous one is still running. Good for tasks that must not overlap (database backups).
    3. Replace: cancel the running Job and start a fresh one. Useful when the new run supersedes the old one.
  4. startingDeadlineSeconds: if the CronJob controller misses its scheduled time (because the controller was down), and the missed time exceeds this many seconds, the run is skipped entirely. Without this field, a controller that was offline for hours could fire many catch-up runs simultaneously on restart.

Full Annotated CronJob YAML

The CronJob below fires every two minutes and refuses to start a second run while the previous one is still going. Save it as cronjob-hello.yaml:


apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello                             # the CronJob resource name
spec:
  schedule: "*/2 * * * *"                # fire every 2 minutes for this demo
  concurrencyPolicy: Forbid               # do not start a new run if the last one is still running
  successfulJobsHistoryLimit: 3           # keep 3 finished successful Jobs (default is 3)
  failedJobsHistoryLimit: 2              # keep 2 failed Jobs for debugging (default is 1)
  startingDeadlineSeconds: 60            # skip if controller missed fire time by more than 60s
  jobTemplate:                           # this is the Job that gets created on each schedule tick
    spec:
      backoffLimit: 2                    # retry failed pods up to 2 times per Job run
      template:
        spec:
          restartPolicy: OnFailure       # restart the container in place on failure
          containers:
          - name: hello
            image: busybox:1.36          # tiny image with shell utilities
            imagePullPolicy: IfNotPresent
            command:
            - /bin/sh
            - -c
            - |
              echo "CronJob fired at: $(date)"
              echo "Running on node: $NODE_NAME"
            env:
            - name: NODE_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName   # inject the pod's node name via downward API
            resources:
              requests:
                cpu: 50m
                memory: 32Mi
              limits:
                memory: 64Mi

Key Takeaways

  1. Deployment is the default, and the other four controllers exist for what it cannot do. Reach past a Deployment only when the workload needs a stable identity, one Pod on every node, or a defined end.
  2. StatefulSet is the only controller that gives a Pod a permanent name. web-0 comes back as web-0 with the same PVC and the same per-pod DNS record from the headless Service, which is how database replicas and Kafka brokers address each other.
  3. A StatefulSet's PVCs outlive the StatefulSet. Deleting the StatefulSet leaves data-web-0 and data-web-1 behind on purpose, so the cleanup step has to delete the claims itself.
  4. A DaemonSet has no replica count. The controller runs one Pod per matching node and adds one automatically when a node joins, and a toleration is what lets an agent onto a tainted control plane node.
  5. A Job is finished when enough of its Pods exit 0. Set restartPolicy: Never so a failed Pod stays around for kubectl logs, and set backoffLimit to bound how many times Kubernetes retries.
  6. A CronJob is a schedule wrapper around a Job. Each firing creates a new Job, concurrencyPolicy: Forbid keeps two runs from overlapping, and startingDeadlineSeconds stops a restarted controller from launching a catch-up storm.
