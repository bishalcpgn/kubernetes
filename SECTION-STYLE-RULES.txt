===========================================================================
 SECTION STYLE RULES
 The style & formatting reference for the Kubernetes training guide.
===========================================================================

 This is the single source of truth for how content in the split HTML guide
 is authored and styled. If you are contributing, the fastest way to match
 the style is to find a similar existing section in html/*.html and copy its
 pattern. This file explains the "why" behind those patterns.

 Last updated: 2026-08-29
 Origin: finalized on Section 2 (Core Working Concepts), applied to chapters
 0-21, then updated after the guide was split into Section 0-3 pages and
 after the heading-colour, font, and figure refresh. Revised again after the
 writing-and-flow pass that removed the command-step generator script, set a
 60-character cap on step titles, and defined the target voice in rule 6h.


===========================================================================
 QUICK START (the rules you'll use 90% of the time)
===========================================================================

 1. Content lives in index.html and html/*.html. No inline style="..."
    anywhere.
 2. Every <h3> needs a unique id (the right-rail menu is built from them).
 3. A heading is never followed immediately by a code box - add one intro
    sentence first.
 4. Callouts are <blockquote class="...">, never hand-written <div>.
 5. Use <ol class="sec2-indented"> for lists; wrap tables in
    <div class="table-wrap">.
 6. The page adds the A/B/C badges, copy buttons, and callout styling on
    load. The i/ii/iii command steps are NOT automatic: write the
    <div class="cmd-step"> markup yourself (rule 3), keep the title under
    60 characters, and put longer comments inside the box (rule 3a).

 Everything below is the detail behind these.


===========================================================================
 0. WHERE THINGS LIVE
===========================================================================

  Hub / table of contents ..... index.html
  Content pages ............... html/section-0-setup.html
                                html/section-1-foundations.html
                                html/section-2-production-operations.html
                                html/section-3-devsecops-deep-dive.html
                                html/appendices.html
  Layout CSS .................. css/app.css   (the ".styled-section" block)
  Base theme, tokens, lists ... css/style.css  (this is also where the
                                light/dark palette lives; there is no
                                separate theme file)
  Page-build JS ............... js/app.js     (builds sections + sidebar,
                                enhances code blocks, converts <blockquote>
                                into callouts, builds the right-rail menu and
                                the prev/next footer)
  Section-styling JS .......... an inline <script> at the bottom of
                                every HTML page (holds STYLED_IDS; marks
                                styled sections and adds the sec2-indented
                                class). The A/B/C badges are pure CSS. The
                                i/ii/iii command badges are authored by hand
                                in the HTML: see rule 3.

  Hard rules:
   - Keep index.html at the repo root as the entry page.
   - Keep guide content pages in html/, CSS in css/, and JS in js/.
   - Use "Section 0" through "Section 3" for the major guide groups. Use
     "chapter" for numbered content pages 0-21 when you need to distinguish
     them from those major groups.
   - From index.html, link content pages as html/<page>.html#id.
   - From html/*.html, load shared assets as ../css/... and ../js/app.js.
   - All CSS lives in css/, all JS in js/ (or the shared inline STYLED_IDS
     script). No inline style="..." in HTML files.
   - Don't add a new one-off class when a universal class already exists.

  How the page is assembled (good to know):
   js/app.js wraps each <h1>/<h2> (and the content under it) into a
   <section class="page-section" id="...">. It wraps every
   <pre class="codehilite"> in a <div class="code-block"> (the language
   header + Copy button), and converts every <blockquote> into a styled
   <div class="callout callout-TYPE">. The inline script then runs on window
   'load' (after app.js) and adds the A/B/C + i/ii badges and indentation.

===========================================================================
 2. HEADINGS & BADGES
===========================================================================

  Heading colour (all the same magenta-pink):
   - h1, h2, h3, and h4 in a styled section are all #BE185D in light mode
     and #f48fb1 in dark mode. This keeps the heading hierarchy visually
     unified. The single page <h1> ("Section N: Title") sits above the
     chapter sections, so it is coloured via ".md-content h1" rather than
     ".styled-section > h1".

  A / B / C badges (on <h4>):
   - Each <h4> in a styled section gets a pink circular letter badge
     (A, B, C ...). It's pure CSS (counter on h4, reset on h3), no JS, so
     the sequence restarts at every <h3>.
   - You don't add anything, just write the <h4>.

  <h3> styling:
   - Pink heading text with a 2px amber underline (border-bottom). No left
     border and no background gradient. Automatic.

  Every <h3> needs a unique id (see rule 9 - the right-rail menu depends
  on it). Use a slug of the text: lowercase, non-alphanumeric -> "-",
  trimmed. Example:
      <h3 id="install-the-cli">Install the CLI</h3>

  Heading spacing (style.css): h1 = 1.25rem, h2 = 1rem, h3 = .8rem,
  h4 = .5rem margin-bottom, so an intro paragraph never jams against it.


===========================================================================
 3. COMMAND STEPS  (i / ii / iii ...) - authored by hand
===========================================================================

  A sequence of bash commands is numbered i, ii, iii ... with a dotted
  connector line. There WAS a script that generated these; it was removed,
  because its output had been baked into the HTML and had drifted. You now
  write the markup yourself:

      <div class="cmd-step">
        <div class="cmd-label"><span class="cmd-roman">i</span><span
          class="cmd-step-title">Watch the rollout until it completes</span></div>
        <pre class="codehilite"><code class="language-bash">kubectl rollout status deployment/web

# Output: "deployment web successfully rolled out" when every new
# replica is Ready.
</code></pre>
      </div>

  Rules:
   - Use a cmd-step only for a real SEQUENCE (2 or more commands). A single
     command gets a plain unwrapped <pre class="codehilite">.
   - The roman numeral restarts at i in every <h4> subsection.
   - THE TITLE IS AT MOST 60 CHARACTERS, and it says WHY the step exists,
     not what the command is. "Watch the rollout until it completes", never
     "Run kubectl rollout status". A reader scanning only the badges should
     be able to follow the flow without reading a single command.
   - Anything that does not fit in 60 characters is not a title. It is a
     comment, and it belongs inside the box: see rule 3a.
   - YAML and text blocks never get a cmd-step. Neither does a bash box
     nested inside an <li>/<ol>.


===========================================================================
 3a. WHERE COMMENTS GO IN A CODE BOX  (and why the blank line matters)
===========================================================================

  Explanatory comments go at the END of the box, after a blank line:

      <pre class="codehilite"><code class="language-bash">kubectl get pods -w

# Output: one line per pod, refreshing as status changes.
# Ctrl-C to stop watching.
</code></pre>

  This is not cosmetic. js/app.js splitBashIntoBoxes() splits a bash <pre>
  on blank lines into one box per group, then merges any group that starts
  with '#' back into the group ABOVE it. So:

   - A trailing comment group after a blank line MERGES into the command
     box. A command and its output render as ONE box. This is what you want.
   - A LEADING comment group has no group above it to merge into, so it
     becomes its own orphan comment box floating above the command.

  If a comment really must come first (a precondition the reader has to act
  on before running anything), keep it leading but do NOT put a blank line
  after it, so it stays glued to the command.

  Column-aligned comment blocks (flag tables) depend on their whitespace.
  Never reflow one into a paragraph:

      # --ignore-daemonsets      DaemonSet Pods belong on every node
      # --delete-emptydir-data   acknowledges emptyDir contents are lost


===========================================================================
 4. INDENTATION  (class "sec2-indented") - automatic
===========================================================================

  Everything inside an <h4> block is indented to line up with the heading
  TEXT (to the right of the A/B/C badge). The JS adds "sec2-indented" to
  each direct child.

  The detail (you rarely touch this):
   - Plain elements (p, ol) use padding-left.
   - Bordered boxes (code blocks, tables, callouts) use margin-left instead,
     so the box border lines up rather than sticking out to the far left.
   - Callouts keep their icon-gutter padding restored on top of the margin.


===========================================================================
 5. LISTS
===========================================================================

  Numbered lists (the default for steps/enumerations):
      <ol class="sec2-indented">
        <li>First step.</li>
        <li>Second step.</li>
      </ol>
   - Renders small dark-blue 1/2/3 circles, deliberately subordinate to the
     pink A/B/C badges.
   - Prefer numbered lists over bullets for steps; we standardized on
     numbered.

  Nested sub-steps (i / ii / iii under a numbered item):
      <ol type="i" class="nested-roman"> ... </ol>
   - Plain lower-roman numerals, no circles, indented under the parent.

  Visual hierarchy:
      A/B/C            pink   (subsections, biggest)
      i/ii             pink   (command steps)
      1/2/3            blue   (ordered lists, smaller)
      nested i/ii/iii  plain roman text (smallest)


===========================================================================
 6. CONTENT PATTERNS  (how to write the HTML)
===========================================================================

  a) MERGE fragmented command boxes. Several consecutive bash boxes that are
     really one sequence => one box, with a blank line between logical
     groups. Keep "# comment" guide lines inside the box, not pulled out
     into paragraphs.

  b) A heading never jumps straight into a code box. Every <h3>/<h4>
     immediately followed by a <pre> gets one short intro <p> first, saying
     what the box is about:
         <h3 id="...">3.5 kubectl port-forward</h3>
         <p>These commands open a local tunnel to a pod or service.</p>
         <pre class="codehilite"><code class="language-bash">...
     Skip headings that already have an intro paragraph.

  c) Lists: convert <ul> bullet lists and manually-numbered paragraphs
     ("1. ...", "Purpose 1:") into <ol class="sec2-indented">. Leave any
     <ul> that sits INSIDE a callout/blockquote alone.

  d) Tables: turn ASCII "tables of text" (column grids, "----" / "+----+"
     separators, cheat-sheets) into real HTML tables:
         <div class="table-wrap"><table><thead>...</thead><tbody>...</tbody>
         </table></div>
     Keep genuine diagrams and sample output (request/response flow, box
     diagrams, sample `describe` output) AS language-text code blocks - they
     are illustrative, not tabular. This is a judgement call: read each
     block and decide; don't automate it (both data tables and box-art use
     "+--" and "|").
     Never wrap a table in a <blockquote>: that renders it inside a coloured
     callout box. A table stands on its own, with an optional bold lead-in
     line (<p><strong>...</strong></p>) above it for the title.

  e) Callouts: see rule 7. Always a <blockquote>, never a <div>.

  f) Lab section intros are PLAIN PARAGRAPHS, not callouts. The
     "What we are doing" / "Real-world mapping" / "Why this lab matters"
     intro under a lab's <h2> is one <p> per part:
         <p><strong>What we are doing:</strong> ...</p>
         <p><strong>Real-world mapping:</strong> ...</p>
     Don't box these and don't use <br><br> between them.

  g) Paired YAML + command steps: when a step pairs a YAML manifest with the
     command to apply it, add an i./ii. lead-in:
         <p><strong>i.</strong> The following YAML defines ...</p>
         <pre ...language-yaml> ... </pre>
         <p><strong>ii.</strong> Apply it and verify ...</p>
         <pre ...language-bash> ... </pre>

  h) Writing style. The target voice, taken from the strongest passages in
     the guide (the eBPF explanation in Section 3, the kubectl explanation
     in Section 0): DEFINE the term in the first sentence, state the
     MECHANISM in the second, state the CONSEQUENCE in the third, then stop.

       - SECOND PERSON. Address the reader as "you", never as "we". "You
         create a Deployment" says whose job it is; "we create a Deployment"
         is ambiguous about who acts and drifts into a teacherly register.
         This matches the Kubernetes documentation the reader has open in
         the next tab. The ONE exception is the lab intro pattern in 6f,
         "What we are doing:", which frames shared activity rather than
         issuing an instruction.
       - Every sentence has an explicit subject and a finite verb. No
         verbless fragments. "Five isolated applications on one server." and
         "One binary running dozens of control loops." are both broken.
       - Gloss every new noun on first use, in the same sentence. A reader
         must never meet a term the guide has not yet defined.
       - At most one rhetorical question per subsection. A chain of them
         ("Need more RAM? It crashed.") reads as telegraph, not prose.
       - A short verdict clause ("That is its whole job.") is good as a
         paragraph CLOSER and bad as a paragraph OPENER.
       - In list items use "<strong>Term:</strong> explanation" when the
         continuation is a clause, and "<strong>Term.</strong> Full
         sentence." when it is a sentence. Never leave a bold label followed
         by an orphaned stub.
       - Brevity is not the goal; a reader finishing the paragraph with the
         concept is. Do not cut the "why" to save a line.
       - US English spelling.
       - NEVER use em-dashes ("—") anywhere: prose, headings, step titles,
         figure labels, or captions. Use a colon, period, comma, or
         parentheses. Inside an SVG figure, a middot ("·") reads well as a
         separator.
       - Straight quotes (' "), never curly ones. This is not just style: a
         curly quote used as an HTML or SVG attribute delimiter (class=",
         x=", viewBox=", ...) breaks parsing and can blank out an entire
         figure. Curly quotes also break shell snippets such as a jsonpath.
       - En-dash in a range becomes a plain hyphen (45-60).

  i) No dark terminal "OUTPUT" boxes. Fold sample output back into the
     preceding bash box as "# Output:" comment lines. A command and its
     output render as ONE box; js/app.js keeps a "#" output group attached
     to the command above it rather than splitting it into a second box.

  j) Command-step titles describe intent, not the command. The label next to
     an i/ii badge should say WHY the step exists ("Watch the rollout until
     it completes"), not echo the command ("Run kubectl rollout status").
     A reader scanning the badges should follow the flow without reading the
     commands themselves.

  k) Section overview page. Each content page opens with a single <h1>
     ("Section N: Title"), then one intro <p> describing the section, then a
     <ul> listing what the reader will do (one <li> per chapter or lab),
     before the first <h2>. See html/section-0-setup.html for the template.

  l) Every language-yaml block gets a lead-in <p>. Never drop the reader
     straight into raw YAML. There are two cases and they read differently:

      - The block IS a file the reader saves and applies. Name the file and
        end with "Save it as <code>nginx-deployment.yaml</code>:".
      - The block is an illustrative fragment with no filename. Do NOT say
        "save it as"; the reader has nowhere to put it. Say what the snippet
        shows: "The Service below selects Pods by label rather than by IP:".

     Tell them apart by reading the commands nearby. If something later runs
     "kubectl apply -f foo.yaml", the block is the file foo.yaml.


===========================================================================
 7. CALLOUTS  (info / warning / danger / success)
===========================================================================

  There is ONE way to write a callout: a <blockquote>. js/app.js converts it
  into a styled box on load. NEVER hand-write <div class="callout">.

  Colour comes from the blockquote's class (default is info):
      <blockquote>                  -> info
      <blockquote class="warning">  -> warning
      <blockquote class="danger">   -> danger
      <blockquote class="success">  -> success

  The TITLE is a LEADING <strong> (the first thing in the blockquote, or a
  leading <p><strong>). A <strong> in the middle of a sentence stays as body
  emphasis. Example:
      <blockquote class="danger"><strong>Back up etcd in production</strong>
      etcd holds all cluster state ... </blockquote>

  Don't use a generic title like "INFO" or "WARNING" - the colour and icon
  already signal the type. A callout with no title is fine (just omit the
  leading <strong>).

  DEPRECATED: html/section-0-setup.html also uses a "gradient-border" family
  (<blockquote class="gradient-border gc-red">, gc-black, ...). The CSS is
  real (css/style.css), but Section 0 is the only page with that look, so it
  reads as an inconsistency rather than a deliberate variant. Do not use it
  in new content; prefer the four types above. One of those blockquotes also
  hand-writes class="callout", which js/app.js adds anyway - never do that.


===========================================================================
 8. CODE STYLING  (automatic, style.css)
===========================================================================

  - Inline code in prose (p code, li code): a subtle grey chip.
  - Inline code in a table cell (td code): plain monospace text, no chip -
    table cells often hold full commands, and chips there look cluttered.
  - Code inside a <pre> block: no chips on the syntax tokens.

  Theme accent (--accent / --link) is green (#16a34a light, #34d399 dark):
  it colours links, focus rings, the active sidebar item, and callout
  borders. The heading and A/B/C badge colour is a separate magenta-pink
  (#BE185D). Numbered-list circles are dark blue on purpose, to sit below
  the pink badges in the visual hierarchy.

  Fonts:
   - Code (inline <code> and code blocks): JetBrains Mono, via --font-mono.
   - SVG figure labels: Caveat, the hand-drawn Excalidraw look. Code-like
     values inside a figure (image names, ports, file paths) stay monospace
     via the "kf-mono" class. Figure-bearing pages must load Caveat in their
     Google Fonts <link>, or the labels fall back to a serif font.


===========================================================================
 9. "ON THIS PAGE" RIGHT-RAIL MENU  (js/app.js)
===========================================================================

  - Built automatically from each section's <h3> headings.
  - EVERY <h3> MUST HAVE AN id, or it won't appear in the menu. If none of a
    section's <h3>s have ids, that section gets no menu at all. (This bit us
    once - sections 14-21 were authored with bare <h3>s and had no menu until
    ids were added.) Keep ids unique across the current HTML file.
  - A scrollspy highlights the active subsection as you scroll.
  - The label drops a leading "N.N" or "Section X:" prefix but KEEPS
    "Step N:", because a lab's steps are an ordered sequence.

  LAB STEPS ARE <h3>, NEVER <h4> UNDER A WRAPPER.
   Do not write a generic "Step-by-Step Lab" <h3> and hang the real steps
   off it as <h4>. The rail is built from <h3> only, so every step under
   such a wrapper is unreachable: the reader gets one useless entry and no
   way to jump to a step. This bit us twice, hiding 52 steps across seven
   labs. Each step is its own <h3 id="step-N-...">.
   A framing <h3> is fine ONLY when it carries its own prose, such as the
   "What we are doing" intro on an embedded mini-lab; its steps are still
   <h3>.


===========================================================================
 9a. EVERY CHAPTER ENDS WITH KEY TAKEAWAYS
===========================================================================

  Every numbered chapter closes with:

      <h3 id="<slug>-key-takeaways">Key Takeaways</h3>

      <blockquote class="success">
        <ol class="sec2-indented">
          <li><strong>The claim.</strong> One sentence on why it matters.</li>
        </ol>
      </blockquote>

  Rules:
   - It is the LAST thing in the chapter, after Cleanup.
   - It needs its own <h3>, or it never reaches the rail (rule 9).
   - NO leading <strong> inside the blockquote. js/app.js would lift it into
     a callout title, duplicating the <h3> directly above it.
   - Four to six items. Each is a claim the reader must still be able to act
     on a week later ("A Service finds Pods by label, never by IP"), not a
     topic list ("We covered Services"). Introduce no new concept here.


===========================================================================
 10. ADDING OR EDITING A SECTION  (checklist)
===========================================================================

  1. Choose the right file:
       - index.html for the guide home and table of contents only
       - html/section-0-setup.html for setup
       - html/section-1-foundations.html for chapters 1-9
       - html/section-2-production-operations.html for chapters 10-13
       - html/section-3-devsecops-deep-dive.html for chapters 14-21
       - html/appendices.html for appendices
  2. If it's a new styled chapter, give its <h2> an id and add that id to
     STYLED_IDS on every HTML page.
  3. If the new chapter should appear in the left sidebar, add it to
     GUIDE_NAV in js/app.js. Use file names relative to html/ for content
     pages, for example section-1-foundations.html.
  4. Give every <h3> a unique id.
  5. Per subsection:
       - merge fragmented bash boxes (6a)
       - add an intro <p> before any heading that jumps into a code box (6b)
       - <ul> / manual numbers -> <ol class="sec2-indented"> (6c)
       - ASCII reference grids -> HTML tables, by hand (6d)
       - callouts as <blockquote class="TYPE"> with a leading <strong> (7)
       - tables stand alone, never inside a <blockquote> (6d)
       - fold OUTPUT boxes into bash as "# Output:" comments (6i)
       - write informative i/ii step titles under 60 chars (3, 6j), with
         longer commentary inside the box after a blank line (3a)
       - add the right lead-in before every YAML block (6l)
       - fix em-dashes / smart quotes, and read it against the target
         voice (6h)
  6. The page auto-applies the A/B/C badges, indentation, and callout
     styling on load. Command steps are hand-authored (rule 3).
  7. Preview, review, and fix any alignment edge cases.

  VALIDATION before you commit:
   - no inline style="..." in the body
   - no hand-written <div class="callout"> (callouts are <blockquote>)
   - tags balanced (pre/code/div/ol/table)
   - no duplicate ids in the same HTML file
   - every <h3> has an id
   - no em-dashes and no curly/smart quotes anywhere (a curly quote in an
     attribute blanks out the whole figure)
   - no <table> wrapped in a <blockquote>
   - no <h2>/<h3> inside a <details class="deep-dive">, and every
     deep-dive has a visible concept sentence above it
   - every <span class="cmd-step-title"> is 60 characters or fewer
   - no bash box that opens with a '#' comment group followed by a blank
     line (it renders as an orphan comment box; see rule 3a)
   - no unescaped placeholder inside a <pre>: write &lt;node-name&gt;, not
     <node-name>, or the browser parses it as a tag and drops it
   - every <h1>/<h2>/<h3>/<h4> sits on ONE source line (a wrapped heading
     puts newlines into the right-rail menu label)
   - read the page start to finish WITHOUT opening a single deep-dive. If
     any concept is missing, the disclosure is wrong (rule 12)
   - SVG <marker> ids unique within the file and every url(#id) resolves
     (duplicate "arr" ids make all arrows share the first marker)
   - figures: no text baseline below its box; figure pages load Caveat
   - internal links use the current folder layout:
       index.html -> html/<page>.html#id
       html/*.html -> #id for same-page links, or <other-page>.html#id for
       another content page, or ../index.html#id for the hub


===========================================================================
 12. DEEP-DIVE DISCLOSURE  (progressive disclosure for optional depth)
===========================================================================

  Beginners get lost in long theory. When a subsection carries more depth
  than a first-time reader needs, keep the CONCEPT visible in the prose and
  move the MECHANISM, edge cases, or reference tables into a collapsible
  block:

      <details class="deep-dive">
        <summary>How the scheduler picks a node<span class="dd-tag">Optional depth</span></summary>

        <p>...</p>
      </details>

  Rules:
   - The concept never lives only inside the dropdown. Always leave at least
     one visible sentence above it saying what the thing is and why it
     exists. A reader who never opens a single dropdown must still meet
     every concept in the guide.
   - <summary> is always the FIRST child. Its text describes what is inside,
     phrased as the question the reader would ask.
   - The <span class="dd-tag"> pill is the affordance that marks the content
     as skippable. Keep the wording "Optional depth" unless there is a
     reason to differ.
   - NEVER put an <h2> or <h3> inside a deep-dive. The right-rail menu is
     built from <h3> ids (rule 9), and a heading hidden inside a collapsed
     block produces a menu entry that scrolls to nothing. <h4> is fine but
     usually unnecessary.
   - Prefer theory, reference tables, and "why it works this way" content.
     Do NOT hide a command sequence a reader is meant to run: badged i/ii
     steps stay visible.
   - Styling lives in css/app.css (the ".deep-dive" block). The chevron is
     drawn with CSS borders, so no icon font or glyph is needed, and the
     block is forced open when printing.

  Good split, from 1.4:

      <h4 id="kube-scheduler">kube-scheduler: Placing Pods on Nodes</h4>
      <p>The scheduler watches for Pods that have no node yet and picks one
        for each. That is its whole job.</p>          <- concept, visible
      <details class="deep-dive">
        <summary>How the scheduler picks a node: filtering and scoring
          <span class="dd-tag">Optional depth</span></summary>
        ...                                            <- mechanism, hidden
      </details>


===========================================================================
 11. CONTRIBUTION UI  (GitHub icon + per-section footer)
===========================================================================

  Repo: https://github.com/bishalcpgn/Kubernetes

  - Header GitHub icon: a fixed top-right link (id "githubLink") next to the
    theme toggle, opening the repo.
  - Per-section footer: js/app.js buildSectionFooters() adds a prev/next
    pager and an "Edit this page on GitHub" link to each content section. It
    is built from the section list, so the prev/next chain stays correct
    automatically when sections are added or removed.
  - js/app.js detects whether it is running from index.html or html/*.html
    and builds sidebar links plus GitHub edit links with the correct relative
    paths. Keep that behavior in mind if files move again.
